# The Bot SDK is published packages: a headless Bot core, features, and adapters

Supersedes ADR 0020 (one core SDK with plugins) and ADR 0017 (no public HTTP contract). Amends ADR 0005, ADR 0011 and ADR 0027. Charted in Wayfinder [#853](https://github.com/Daanish2003/bot-sdk/issues/853); each point below links to the ticket that holds its detail.

The SDK is no longer copied into Hosts. It is **public npm packages under `@botsdk`** that others install and use on their own stack. Four things in the old design made that hard:

- The Better Auth-style plugins mixed infrastructure with features.
- The SDK owned the HTTP layer and called `getUser(request)` itself.
- Every Host got every table.
- One 15.5K-line `bot` plugin reached the others through roughly 110 `sdk.plugin("x")` lookups.

Bot behaviour does not change.

- **A Bot core, features, and adapters** ([#858](https://github.com/Daanish2003/bot-sdk/issues/858)).
  - **The core is the Bot:** Conversations, Turns, Triggers and the Router, Routines, Check-ins, Helpers, Demonstrations, Auto-review, Secrets, SendToUser, context engineering, Models, Channels and the Computer service.
  - **Adapters** fill flat config slots for infrastructure: `database`, `runner`, `computer`, `blobs`, `pubsub` and `channels`.
  - **Features** are optional capabilities: Memory, Skills, Knowledge and MCP Connections.
  - A feature is one `defineFeature({ id, needs, schema, contract, api, tools, prompt, afterTurn, jobs, userData })` object. It declares the core services it needs and receives them typed.

    _Amended 2026-10-30 ([#1013](https://github.com/Daanish2003/bot-sdk/issues/1013), approved by the owner): `defineFeature` also takes an optional `resetBot(botId, userId, context)` hook. `bots.reset` calls it for each enabled feature once the reset commits. The call is best-effort: a failure is logged and the reset stands. Memory implements it by deleting the Bot's memory directory when the user has a Computer, so the core never learns where a feature keeps its files._

    _Amended 2026-11-02 ([#1185](https://github.com/Daanish2003/bot-sdk/issues/1185), spec [#1166](https://github.com/Daanish2003/bot-sdk/issues/1166), for owner review on its PR): `assignments` joins the core services a feature can declare in `needs`. It offers `create`, `read` and `cancel`, and each feature gets its own, which acts only on its owner's Bots and on Assignments that feature made. An Assignment made by a feature names one of the feature's `jobs`, and the core queues that job, with the public `assignmentEnded` payload, in the transaction that ends the Assignment, so the core still never calls a feature directly. A feature's text reaches the Bot as untrusted data, following ADR 0021, and never counts as the user's word in Auto-review. These go beyond the two seams approved for spec 2._

    _Amended 2026-11-03 ([#1188](https://github.com/Daanish2003/bot-sdk/issues/1188), spec [#1167](https://github.com/Daanish2003/bot-sdk/issues/1167), decided by the owner on that spec): `representativeLoop` joins the core services a feature can declare in `needs`, beyond the two `defineFeature` seams the spec had approved. Its `run` plays `runLoop` in the feature job's own context and accepts only a Representative's identity (its owner, the Representative, the Customer and the Model), so a feature can't run a Bot's loop. That loop has no Computer and no spill, no Auto-review, the tools its caller passes and no others, the `representative` usage kind on the owner's Quota, which it checks once before starting, and a thread and cache key per Customer._

    _Amended 2026-11-03 ([#1194](https://github.com/Daanish2003/bot-sdk/issues/1194), spec [#1167](https://github.com/Daanish2003/bot-sdk/issues/1167), decided by the owner): the `assignments` service gains `move({ userId, id, botId })`. It moves one of the feature's own Assignments that hasn't ended to another of the owner's Bots, keeping its status and log, as a feature that lets the owner choose a Bot needs. It adds a log row, skips the old Bot's unread hand-over, tells the old Bot if it had read it, and wakes the new Bot. An Assignment that ended is CONFLICT; another owner's Assignment or Bot, or one another feature made, is NOT_FOUND. This goes beyond the seams already approved._

    _Amended 2026-11-03 ([#1202](https://github.com/Daanish2003/bot-sdk/issues/1202), decided by the owner): the `assignments` service's `create` takes the caller's transaction, as the Bot's own `assign_work` does, so a job step's Checkpoint commits with the Assignment and a replay never makes a second one. What the feature writes beside it, such as a Representative's hand-off row, commits with it too. It returns the Assignment's `id` and the `conversationId` to hint, and the caller wakes the runner and hints the thread once the transaction commits, as with `releaseApprovals`. A refusal comes before anything is written, so the caller may catch it and commit. It takes the Conversation's lock, so any lock of the caller's that others take before a Conversation's comes first. `read`, `cancel` and `move` keep their own transactions._

    _Amended 2026-11-03 ([#1186](https://github.com/Daanish2003/bot-sdk/issues/1186), decided by the owner): the `assignments` service's `create` takes an optional `turnId`, the id of the Bot Turn that started the work, which a feature has as `turn.id` in `tools` and `afterTurn`. The core works out the chain from that Turn, with the logic a Bot's own `assign_work` uses, so a feature can't state its own depth and a Bot → feature → Bot loop stops at the chain limit: past it is CONFLICT, and a Turn that is unknown or not the owner's is NOT_FOUND. Work with no Turn behind it, such as a webhook, starts at depth 1. A Representative's hand-off has no Bot Turn behind it, so it starts at depth 1 too. The Assignment takes the depth and no parent: a feature names none, and only its job hears of the end, so no Bot would wake to carry on a parent it blocked. It takes the lock of the Turn's Bot's 1:1 Conversation as well as the target's, in order._

    _Amended 2026-11-03 ([#1218](https://github.com/Daanish2003/bot-sdk/issues/1218), decided by the owner): the core supplies the Turn in a feature's tools. The `assignments` service in the `context` that `tools` is given is built for that Turn, or for the Turn that started a Helper, so `create` counts from it and leaving out `turnId` can't escape the chain limit. If the tool names a Turn too, that Turn must be the owner's and the deeper of the two counts, so naming one can't lower the depth. The Turn is carried by the service rather than by request-scoped state, so concurrent Turns can't mix and a job the runner starts inside a tool's call can't inherit one. A replay lists the tools for the same Turn and so counts the same. Three limits stand. A job has no live Turn, so it keeps passing `turnId` itself, with the id its payload carries, and without it starts at depth 1. A service kept from `api` or from a job's context knows no Turn, so a tool must use the one it's given. `afterTurn` still passes `turn.id` itself. Parents are not added: a feature's Assignment stays depth-only with its own budget until real use shows a need, and the end paths don't change. Whether a Representative's hand-off needs a limit moved to [#1171](https://github.com/Daanish2003/bot-sdk/issues/1171); it stays at depth 1._

    _Amended 2026-11-03 ([#1195](https://github.com/Daanish2003/bot-sdk/issues/1195), spec [#1167](https://github.com/Daanish2003/bot-sdk/issues/1167), decided by the owner on that spec): `releaseApprovals` joins the core services a feature can declare in `needs`, beyond the seams the spec had approved. It offers `post`, `answer` and `drop`, each in the caller's transaction. `post` puts a link-only `release_approval` card in a Bot's Conversation, naming the page the feature gives it; `answer` closes it with the owner's yes or no, given on the Representative's page, and wakes the Bot with a Trigger the core words itself, so a feature's text never reaches the Bot as an answer; `drop` closes it and wakes no one, for a Bot reset or the owner choosing another Bot. The card holds the Approval's state, so the service adds no core table and a Host without the feature carries nothing. Channels get a link and no yes or no. It expires 7 days after it is posted, read from the time it holds rather than by a job as ADR 0030's Approvals are, and the draft stays and can still be approved from the page, which then wakes no one._

    _Amended 2026-11-04 ([#1305](https://github.com/Daanish2003/bot-sdk/issues/1305), spec [#1171](https://github.com/Daanish2003/bot-sdk/issues/1171), approved by the owner): `MessagingAdapter` gains an optional `MessagingReach`, declaring what the platform limits (reply window, length, who may start a chat), which the Outbound gate reads for the Channel a message goes by. An adapter that declares nothing is limited by nothing._

    _Amended 2026-11-08 ([#1355](https://github.com/Daanish2003/bot-sdk/issues/1355), spec [#1174](https://github.com/Daanish2003/bot-sdk/issues/1174), approved by the owner while slicing): `MessagingAdapter` gains an optional `webhook(account, { headers, body }, call)`, declared instead of `listen` by an adapter whose platform only posts to a webhook (Telnyx). The `channel` plugin serves one public route per such adapter, `POST <basePath>/channels/<platform>/<accountId>`, which reads the account, has the adapter check the request's signature over the raw body and turn it into updates, and answers 202 before handing them to the same inbound path a listener's take, the stranger hook on a held account included. A refused request answers 400 and stores nothing. Each update id is claimed in the runtime's `counters` for a day, so a platform's retry is dropped on any process; the in-process dedupe a listener relies on can't see a retry that lands on another process. No new table._

    _Amended 2026-11-04 ([#1264](https://github.com/Daanish2003/bot-sdk/issues/1264), spec [#1169](https://github.com/Daanish2003/bot-sdk/issues/1169), approved by the owner): `factApprovals` joins the core services a feature can declare in `needs`, a sibling of `releaseApprovals` with the same `post`, `answer` and `drop`, each in the caller's transaction. `post` puts a link-only `fact_approval` card in a Bot's Conversation, worded by the core from the fact's key and value and the Bot's reason, naming the page the feature gives it; `answer` closes it with the owner's yes or no, given on the Facts page, and wakes the Bot with a Trigger the core words itself; `drop` closes it and wakes no one, for a Bot reset. The card holds the Approval's state, so the service adds no core table and a Host without the feature carries nothing. Channels get a link and no yes or no. It expires 7 days after it is posted, read from the time it holds. A sibling rather than a wider `releaseApprovals`, because a Release's card and answer name a Representative and a Release number, and a fact has neither; the two share only how a link-only card closes._

    _Amended 2026-11-04 ([#1288](https://github.com/Daanish2003/bot-sdk/issues/1288), spec [#1170](https://github.com/Daanish2003/bot-sdk/issues/1170), approved by the owner): the `assignments` service gains `redact(tx, { userId, ids })`, for a feature deleting whoever its Assignments came from. In the caller's transaction it replaces their text with `[Redacted]` in the Assignment, its log, its Triggers and the Turns on it, for the child Assignments too, and in what the Bot's Conversation holds of it, and keeps each Assignment as a redacted record; one that hasn't ended is cancelled with its children, so no Bot waits on it. An Approval still open from a Turn wholly on them is denied, ADR 0030's exception. It ignores any id that isn't the feature's own for that owner, and repeating it changes nothing. It takes the locks of the Conversations it writes to up front in id order and returns them, for the caller to wake the runner and hint once `tx` commits. No new table or column: the text itself says it's redacted. A core service rather than the feature's own writes, because features never touch core tables._

    _Amended 2026-11-04 ([#1299](https://github.com/Daanish2003/bot-sdk/issues/1299), spec [#1171](https://github.com/Daanish2003/bot-sdk/issues/1171), approved by the owner): `defineFeature` also takes an optional `stopTurns(userId, context)` hook, and a feature's context gains `isUserBlocked(userId)`, the Host's Ban check. A Ban's `stopTurns` calls each enabled feature's hook after the core stops its Turns and before it stops Helpers and Demonstrations, so a feature stops its own running Turns as the core stops a Bot's. A hook that throws is logged and the rest of the Ban's stop still runs. A feature reads `isUserBlocked` before it starts a Turn, so none starts during a Ban. Neither adds a core table or column. A hook and a context method rather than the core cancelling the feature's jobs, because only the feature knows which of its jobs are Turns and what a stopped one leaves on its own rows._

    _Amended 2026-11-04 ([#1300](https://github.com/Daanish2003/bot-sdk/issues/1300), spec [#1171](https://github.com/Daanish2003/bot-sdk/issues/1171), approved by the owner): `pages` joins the core services a feature can declare in `needs`, beyond the seams the spec had approved. Its one method, `send`, runs in the caller's transaction and raises a Page: a direct alert to the owner with no Conversation, recording its cause and whether it's routine or an emergency. A Page isn't a Message, because the push and email paths are keyed to Bot Messages in Conversations, so it has a core table (`page`, its schema approved on that spec) and its own `page.deliver` job, one per Channel, through `sdk.channels`. It goes at once to web push and the owner's Linked identities, then to email after 10 minutes unless acknowledged. It makes no model call and never reads the Quota, so it goes out when the Quota is spent. The owner reads and acknowledges Pages through the core's `pages` RPCs, which a feature doesn't contribute, and acknowledging stops whatever hasn't been sent. A Page belongs to no Bot, so a Linked identity is reached through the first of the owner's active Channel accounts on that platform that delivers it, and its email comes from `pages@` on the email Channel's domain, which no Bot's address can be. It also has `sendDaily`, which raises the Page unless one of the same cause went to that owner in the last day, acknowledged or not, so a condition that keeps recurring alerts at most once a day. The table's rows are the user's: exported with them and deleted with them. _Amended 2026-11-10 ([#1317](https://github.com/Daanish2003/bot-sdk/issues/1317), approved by the owner): `pages.list` returns `{ pages, truncated }` instead of a bare array: at most 50 Pages, emergencies first and each newest first, with `truncated` true when more waited (a boolean, not a total, as the inbox's other lists report it). The inbox and the settings Pages section each show one line when it is true. `PagesService` is unchanged._

    _Amended 2026-11-05 ([#1312](https://github.com/Daanish2003/bot-sdk/issues/1312), spec [#1171](https://github.com/Daanish2003/bot-sdk/issues/1171), approved by the owner): the `assignments` service gains `markOverdue(tx, { userId, id })`, for a feature flagging an Assignment of its own that has run past its due time. In the caller's transaction it sets the Assignment's `overdueAt` to now and returns `{ marked }`, true only for the first call on one that is still open; an Assignment that has ended, was flagged already, or isn't the feature's own for that owner returns false and changes nothing. The flag is never a status, so the Bot's work goes on. No new table or column: `overdueAt` was reserved on the Assignment already. A core service rather than the feature's own write, because features never touch core tables._

  - Features never call each other and never add columns to core tables. They contribute no RPC routes. They can serve other routes: `routes`, which get the core context until spec 3 replaces them, and the public routes below.

    _Amended 2026-11-05 ([#1331](https://github.com/Daanish2003/bot-sdk/issues/1331), spec [#1173](https://github.com/Daanish2003/bot-sdk/issues/1173), approved by the owner): `channelAccounts` joins the core services a feature can declare in `needs`, so a feature can hold a Channel account, which the core still stores, encrypts and listens on. `save` takes a `hold(tx, id)` callback that records the feature's holder in the save's transaction, `removeIn(tx, ids)` deletes only feature-held accounts, and `changed(ids)` tells the listeners. `defineFeature` also takes an optional `channelAccountOwner(tx, id, context)` hook naming the user whose holder has an account, so a save moves an account only between one user's holders. An account no enabled feature names can't be taken._

    _Amended 2026-11-05 ([#1339](https://github.com/Daanish2003/bot-sdk/issues/1339), spec [#1173](https://github.com/Daanish2003/bot-sdk/issues/1173), approved by the owner): `pubsub` joins the core services a feature can declare in `needs`, so a feature can publish and follow its own change hints: `representative` uses it for a public stream per web chat session, whose hints a Conversation's `threads.hintChanged` can't reach. It's the instance's `PubSub`, at most once and with no replay, so a feature names its own channels under its id, carries hints rather than data, and recovers a lost hint on reconnect. No new table or slot._

    _Amended 2026-11-05 ([#1337](https://github.com/Daanish2003/bot-sdk/issues/1337), spec [#1173](https://github.com/Daanish2003/bot-sdk/issues/1173), approved by the owner): `counters` joins the core services a feature can declare in `needs`. It is the SDK's fixed-window `CounterStore` (`hit(key, windowMs)`, and since [#1363](https://github.com/Daanish2003/bot-sdk/issues/1363) `reset(key, windowMs?)`, so a messaging webhook can release an update's id when storing it fails), memory in process or Redis when the Host runs `redisRuntime`, so a feature's limits hold across processes as the core's do. A feature chooses its own keys and windows. It adds no table. The Representative uses it to limit web chat's public routes per session and per IP. The IP is the Host's to supply, through the Representative option `clientIp(request)`, because the SDK reads no forwarded header by default and anyone could send one to choose which IP is counted. Left out, no per-IP limit applies and the per-session limit still does._

    _Amended 2026-11-03 ([#1189](https://github.com/Daanish2003/bot-sdk/issues/1189), spec [#1167](https://github.com/Daanish2003/bot-sdk/issues/1167), approved in the spec): `defineFeature` gains two narrow seams beyond the routes above. Both are for features that serve strangers._

    _**Public routes (built in #1189).** An optional `publicRoutes: [{ method, path, handle }]`. `createHttpHandler` serves each under `basePath` with no signed-in user, before `getUser` runs. `handle(request, { context, params, basePath })` gets only the feature's own context (`FeatureContext`, with the services in its `needs`), never the core's `sdk` and never a user. A method and path that another route has, public or not, throws when the instance is built. A feature's existing `routes` are unchanged, and they still get the whole core context and a signed-in user. The original line saying features contribute no routes was wrong, because `routes` already existed; the line above is the correction. Web chat uses these routes (#1173)._

    _**The stranger hook (built in [#1334](https://github.com/Daanish2003/bot-sdk/issues/1334), when [#1172](https://github.com/Daanish2003/bot-sdk/issues/1172) closed).** Its shape: an optional `onStranger(message, context)`, where `message` is the inbound Channel message (the Channel, the account, the sender's platform identity and whether the Channel verified it, and the text and attachments) and `context` is the feature's own context. The core calls it for an inbound message on a Channel account the feature holds, ahead of the Linked identity check, so everyone there is a stranger to the core and link codes do nothing. It returns nothing: the feature decides what the message becomes, and the core starts no Bot Conversation and no Turn for it. Inbound dedupe stays the core's, namespaced by platform and account. A throw is logged and the update is dropped, as for other inbound failures._

    _Amended 2026-11-05 ([#1334](https://github.com/Daanish2003/bot-sdk/issues/1334), spec [#1173](https://github.com/Daanish2003/bot-sdk/issues/1173)): building the hook added what it needed. The core drops anything not from a private chat before it calls the hook, as it does for a Bot. `MessagingAdapter` gains an optional `verifiesSender`, which is where the hook's "whether the Channel verified it" comes from: true when the platform authenticates senders (Telegram), and left out when they can be spoofed. The `channelAccounts` service gains `send(id, { chatId, text, resume })`, so a feature's job sends through an account it holds, where rejected credentials mark the account and stop its listener and a retry resumes after the parts already sent, and `reach(platform)`, the adapter's declared limits for the Outbound gate. The `representative` feature keeps which account a thread last heard from and how far a send got in its own tables. A message during its owner's Ban is still kept, so an opt-out or emergency isn't lost, but no Turn answers it and delivery sends only what is meant for a Customer regardless._

  - `defineFeature` is public, so third parties write features exactly as we do.
- **Memory, Skills and Knowledge sit on the Computer** ([#864](https://github.com/Daanish2003/bot-sdk/issues/864)). They have no store of their own, because the Bot edits these files itself (ADRs 0022, 0025). Any `ComputerProvider` works. An unmet `needs` throws at construction.
- **Headless first, HTTP optional** ([#860](https://github.com/Daanish2003/bot-sdk/issues/860)).
  - Domain methods take `userId` explicitly, for example `sdk.bots.send({ userId, botId, text })`.
  - `createHttpHandler(sdk, { getUser, basePath, rateLimits })` is an optional fetch handler over them. It uses nested oRPC routers, serves the webhook, email and screen routes and the SSE change hints, and has a `toNodeHandler` helper. The screen socket is exported as crossws hooks.
  - The browser client is typed by per-feature oRPC **contracts**. Those contracts are public interface, versioned by semver (this supersedes ADR 0017).
- **Users are opaque ids** ([#863](https://github.com/Daanish2003/bot-sdk/issues/863)).
  - A `users: { isBlocked?, verifiedEmail? }` slot lets the SDK ask the Host about a user. Quota and linked credentials stay in `models`.
  - Bans are checked only on Triggers that don't come from the user, as before.
  - `sdk.users.delete` and `sdk.users.export` compose each feature's `userData`.
- **Postgres only** ([#861](https://github.com/Daanish2003/bot-sdk/issues/861)).
  - Drizzle stays internal. The `database` slot takes a connection string or a pg-compatible `Pool`.
  - The core and each feature ship SQL migrations, and `migrate()` or the `botsdk` CLI applies only the enabled ones (`--print` outputs the SQL).
  - The fixed schema is `botsdk`, starting from a fresh baseline.
- **The durable runner's seam is an Executor** ([#862](https://github.com/Daanish2003/bot-sdk/issues/862)).
  - Only the wake-up and run of a due job varies, through `start`, `notify` and `stop`.
  - The replay engine, job history, leases and transactional enqueue stay core, so Checkpoints stay exactly-once.
  - The adapters are the in-process poller (the default) and Inngest.
  - `defineJob` is public, `replaceIfNotStarted` replaces the Router's reads of the job tables, and Trigger.dev goes.
- **The core's internal modules** ([#865](https://github.com/Daanish2003/bot-sdk/issues/865)).
  - The modules are conversation, triggers, turn, agent-loop, context, tools, routines, helpers, demonstrations and safety, plus the folded-in services.
  - Each module has one entry point, and a lint rule enforces one dependency direction.
- **Packages** ([#859](https://github.com/Daanish2003/bot-sdk/issues/859)).
  - The packages are:
    - `@botsdk/client` (contracts and shared types)
    - `@botsdk/bot` (the core, plus the `/http` subpath)
    - `@botsdk/react`
    - one package per feature
    - one package per adapter, carrying its driver
    - `@botsdk/testing`
  - They are released in one Changesets `fixed` group, built with tsdown, ESM-only, with trusted publishing.
  - The Host installs the `@tanstack/ai-*` providers it registers.
- **UI from a shadcn registry** ([#866](https://github.com/Daanish2003/bot-sdk/issues/866)).
  - `@botsdk/react` (`BotSdkProvider`, with React Query as a peer) needs the HTTP layer.
  - Registry items pin the same version, and Hosts own the files after `shadcn add`.
  - The docs and the registry are served from GitHub Pages.
- **The Host's wiring** is shown in the [prototype](https://github.com/Daanish2003/bot-sdk/blob/prototype/867-host-wiring/docs/prototypes/867-host-wiring.md) ([#867](https://github.com/Daanish2003/bot-sdk/issues/867)).

## Considered Options

- **Keep the Better Auth-style plugins and fix the schema** with a generator: plugins stay the wrong tool for infrastructure, and the locator coupling stays (#854, #858).
- **A generic CRUD storage adapter**: it can't keep `SKIP LOCKED`, advisory locks or `pg_trgm` (#855).
- **A swappable durable-execution engine** (the step and dispatch ports): it would need idempotency keys and an outbox, and would lose prompt abort (#856, #862).
- **One package with subpaths for everything**: every Host would install every driver and parser (#859).
- **A strangler migration**: it doubles the code and tests while behaviour is frozen (#868).
- **Keep copying source (ADR 0005)**: outsiders can't adopt a library they have to copy.

## Consequences

- ADR 0020 is superseded. ADR 0017 is superseded.
- ADR 0005's copy model, the "Host owns `ui/`" rule and `createChat` are superseded. "Auth comes from the Host", "Postgres is required" and "the SDK ships its migrations" still hold.
- ADR 0011's runner interface, its "a Host can't register its own jobs", its Trigger.dev adapter and "the runner is a plugin" are superseded. The history-replay amendment of 2026-10-17 still holds.
- ADR 0027's plugin list becomes the core and features above.
- The work ships as eight specs, in place and green after each one (#868): core and features; the runner seam; headless and HTTP; storage; packages and build; registry, docs and release; the tarball example Host; the Inngest Executor.
- The owner creates the `botsdk` npm org before the first publish.
- New dependencies: `inngest` (adapter package only), `crossws`, tsdown, Changesets and Astro Starlight (docs workspace).
