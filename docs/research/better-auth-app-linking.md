# Linking apps with extra scopes in Better Auth 1.7.7

Research for [#1403](https://github.com/Daanish2003/bot-sdk/issues/1403) (child of map [#1396](https://github.com/Daanish2003/bot-sdk/issues/1396)). Researched 2026-11-18 against the installed **better-auth 1.7.7** (`pnpm-workspace.yaml:31`, catalog `better-auth: 1.7.7`), its docs (v1.7, "latest" per [better-auth.com/llms.txt](https://better-auth.com/llms.txt)), and each vendor's OAuth docs.

Source paths below are the compiled files in the pnpm store, which carry the `//#region src/...` names of the TypeScript sources:

- `BA` = `node_modules/.pnpm/better-auth@1.7.7_*/node_modules/better-auth/dist/`
- `CORE` = `node_modules/.pnpm/@better-auth+core@1.7.7_*/node_modules/@better-auth/core/dist/`

## Question

What do Better Auth 1.7.7 and each app's OAuth allow for linking an app to a user who is already signed in, so that its token can power Connector tools?

1. `linkSocial` with extra scopes for a provider the user already signs in with (Google: Gmail, Calendar, Drive; GitHub: repo). Does it add scopes to the existing `account` row or make a second one, and does `getAccessToken` then return a token that carries them?
2. Linking a _different_ account of the same provider than the sign-in one, given `allowDifferentEmails: true`.
3. `genericOAuth` configs for Slack (user token), Notion and Linear: endpoints, PKCE, refresh tokens, token lifetime.
4. Google for a personal app: refresh-token expiry in Testing mode, and what publishing needs for Gmail's restricted scopes when the developer is the only user.

## Summary

1. **Same provider and same account: the existing row is updated, not duplicated.** Its `scope` becomes the union of the old and new scopes, and its tokens are replaced by the new grant's tokens. `getAccessToken` returns that row's token. For Google the token carries every granted scope, because Better Auth sends `include_granted_scopes=true` by default. **There are two catches.** (a) Today's Google config never asks for `access_type=offline`, so the row has **no refresh token**, and the Connection would die after about an hour. (b) A later _sign-in_ with the same Google or GitHub account overwrites the row's tokens (but not its `scope`) with whatever the sign-in grant returned.
2. **A different account of the same provider gets a second `account` row** (same `providerId`, different `accountId`). `allowDifferentEmails: true` lets it through, as long as the provider says the email is verified. Two side effects: that second Google account becomes a **sign-in method** for the user, and `getAccessToken` needs the row's id, since it can't pick a row by provider (the same lookup `chatgpt.ts` already does).
3. **In 1.7.7, `genericOAuth` providers are ordinary social providers**, linked with `linkSocial` (the same path the ChatGPT link uses). Slack's user token works through `oauth.v2.user.access`. Notion needs `authentication: "basic"` and a custom `getUserInfo`. Linear needs its scopes sent comma-joined. Details are in the table below. **Slack's errors come back as HTTP 200 `ok:false`, and Better Auth doesn't treat that as a failure**, so a failed Slack refresh doesn't produce `FAILED_TO_GET_ACCESS_TOKEN`.
4. **Testing mode: grants and refresh tokens expire 7 days after consent.** (The exception, scopes limited to name, email and profile, doesn't cover Gmail.) Google's docs exempt a personal-use app (fewer than 100 users) from verification, so an _In production_, unverified app can be used by the developer: there is an "unverified app" warning and a lifetime cap of 100 users, and refresh tokens no longer expire after 7 days. **Unverified:** whether the console lets you publish with restricted scopes and no verification submission (see "Not verified").

A design option this research points to: **register a Connection as its own `genericOAuth` provider id** (e.g. `google-workspace`, pointed at Google's endpoints) rather than adding scopes to the `google` sign-in row. It gets its own `account` row, so sign-in never overwrites its tokens, and its link-only rules can follow the ChatGPT pattern. The cost is one more redirect URI to register. This is a design choice for the spec, not a finding.

## 1. `linkSocial` with extra scopes, same provider

### What the code does

- `POST /link-social` takes `scopes`, `loginHint` and `additionalParams`, and passes `c.body.scopes` to `provider.createAuthorizationURL` (`BA/api/routes/account.mjs:75-131`, `:245-253`). The state carries `link: { userId, email }` (`:237-244`).
- The callback sees `link` in state and calls `linkOAuthAccount` with `scope: tokens.scopes?.join(",")` taken from the token response (`BA/api/routes/callback.mjs:150-164`).
- `linkOAuthAccount` looks the row up by `(providerId, accountId)` with `findAccountByKey` (`BA/oauth2/link-account.mjs:48`).
  - **Found, same user:** it updates _that row_. It sets `scope` to `mergeScopes(existing.scope, scopes)` (the union, keeping the stored order: `CORE/oauth2/utils.mjs:47-51`) and replaces `accessToken`, `refreshToken`, `idToken` and the expiry times. Fields that are `undefined` are dropped first, so a grant without a refresh token **keeps the old refresh token** (`BA/oauth2/link-account.mjs:49-61`).
  - **Found, other user:** the link fails with `ACCOUNT_ALREADY_LINKED_TO_DIFFERENT_USER` (`:50`).
  - **Not found:** it creates a new row (`:62-68`).
- The Better Auth docs say the same: "This will trigger a new OAuth flow that requests the additional scopes … your account will have the new scope in the database" ([Google: Requesting Additional Google Scopes](https://better-auth.com/docs/authentication/google#requesting-additional-google-scopes); [OAuth concept](https://better-auth.com/docs/concepts/oauth#requesting-additional-scopes)).

### What `getAccessToken` returns

- It selects by Better Auth **row id** (`accountId`) or by the account cookie, not by provider (`BA/api/routes/account.mjs:309-315`, `:326-344`).
- It refreshes only when `accessTokenExpiresAt` is within 5 s **and** the row has a refresh token **and** the provider has `refreshAccessToken` (`:367-368`).
- A refresh writes new tokens but **never updates `scope`** (`:371-377`). The returned `scopes` are the stored ones (`:398`).
- When there is no refresh token, it hands back the stored access token **even if it has expired** (`:396`). Only a thrown refresh error turns into `FAILED_TO_GET_ACCESS_TOKEN`, which is the signal `packages/auth/src/chatgpt.ts:39-43` maps to `needs-reconnect`.

### Google specifics

- Better Auth adds `include_granted_scopes=true` unless `includeGrantedScopes: false` (`CORE/social-providers/google.mjs:84`). Google: "the new access token will also cover any scopes to which the user previously granted the application access" ([Google web-server OAuth, incremental authorization](https://developers.google.com/identity/protocols/oauth2/web-server#incrementalAuth)). So the merged `scope` column matches what the token can do.
- **No refresh token today.** `access_type` is only sent when `options.accessType` is set (`CORE/social-providers/google.mjs:79`, `CORE/oauth2/create-authorization-url.mjs:36`). `packages/auth/src/index.ts:163-169` doesn't set it. Google only returns a refresh token with `access_type=offline`, and only on the first authorization unless `prompt=consent` is sent ([Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server); [Better Auth: Always get refresh token](https://better-auth.com/docs/authentication/google#always-get-refresh-token)).
  - A per-call fix is possible: `access_type` and `prompt` are not reserved keys, so `linkSocial({ additionalParams: { access_type: "offline", prompt: "consent" } })` passes the schema (`CORE/oauth2/authorization-params.mjs:10`). The URL builder applies `additionalParams` after the provider's own settings (`CORE/oauth2/create-authorization-url.mjs:54-57`).
- **Sign-in after linking overwrites the tokens.** When a user signs in again with an account that is already linked, the tokens are rewritten (by default, `updateAccountOnSignIn !== false`) and `scope` is "intentionally omitted. Updated only via linkSocial" (`BA/oauth2/link-account.mjs:203-226`). For Google with `include_granted_scopes=true`, the new access token still covers the Gmail scopes (per the Google quote above), so this is probably harmless. The old refresh token is kept, because sign-in sends no `access_type=offline` and so gets no refresh token (undefined fields are dropped, `:208-215`).
- PKCE: the Google provider requires a code verifier (`CORE/social-providers/google.mjs:62`), and Better Auth always sends S256 (`CORE/oauth2/create-authorization-url.mjs:38-42`).

### GitHub specifics

- Default scopes are `read:user user:email` plus `options.scope` plus the call's scopes (`CORE/social-providers/github.mjs:15-17`). `linkSocial({ provider: "github", scopes: ["repo"] })` asks for all three. The same GitHub user id updates the same row (as above).
- GitHub's token response lists scopes comma-joined (`scope=repo%2Cgist`, [Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)). Better Auth splits on whitespace (`CORE/oauth2/utils.mjs:12-15`), so it stores the comma string as one entry. Because the column is comma-joined anyway, `parseStoredScopes` still splits it correctly (`BA/api/routes/account.mjs:17-20`).
- OAuth-app tokens don't expire unless the app opts in to expiring tokens (8 h access, 6-month refresh). Without that opt-in there is no refresh, and `getAccessToken` just returns the stored token ([Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)).
- Limit: **ten tokens per user/application/scope combination**. Past that, GitHub revokes the oldest unused or least recently used token (same doc). Sign-in and the repo link ask for different scope sets, so they count separately.
- **Sign-in after linking:** "Users who have already authorized the app … the flow completes automatically with the scopes they previously granted" (same doc). That example omits `scope`, though. Whether a sign-in that asks for fewer scopes gets a token that keeps `repo` is **not stated**, and Better Auth would then overwrite the repo-scoped token (see "Not verified").
- The scope a user actually granted can be narrower than the request; check `X-OAuth-Scopes` ([Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)).

## 2. A different account of the same provider

- A different Google account has a different `sub` (`accountSubject: profile.sub`, `CORE/social-providers/google.mjs:56`). So `findAccountByKey` finds nothing and a **second row** is created with the same `providerId: "google"` (`BA/oauth2/link-account.mjs:48`, `:62-68`).
- Checks that apply on the link path:
  - The email must be verified, or the provider must be in `trustedProviders` (`:43`). Google sends `email_verified` in the ID token (`CORE/social-providers/google.mjs:130`).
  - A different email is allowed only with `allowDifferentEmails: true` (`:47`), which is set in `packages/auth/src/index.ts:175-181`.
  - The same Google account already linked to _another_ user is refused (`:50`).
  - `disableSignUp` doesn't apply to the link path: the callback branches to `linkOAuthAccount` before any sign-up check (`BA/api/routes/callback.mjs:155-165`).
- Side effects:
  - **The second account can now sign the user in.** A later `/sign-in/social` with it finds the row by `(providerId, accountId)` and signs in as the row's owner (`BA/oauth2/link-account.mjs:80-105`). The repo's `hooks.before` blocks this only for ChatGPT (`packages/auth/src/index.ts:275-280`).
  - **Picking the token:** `getAccessToken` needs the row id (`BA/api/routes/account.mjs:309-315`). `listAccounts` returns every row with its `accountId` (the provider's id) and `scopes` (`:64-73`), so the Connection must store or pick the row id. A lookup by `providerId` alone, like `chatgpt.ts:26-31` ("the newest"), would be ambiguous between the sign-in row and the Connection row.
  - **Unlinking:** the repo's `/unlink-account` guard counts only `chatgpt` rows as link-only (`packages/auth/src/index.ts:283-292`). A link-only Connection row under `google` would count as a sign-in method. That is true anyway, given the previous point.
- Both cases go through the same code: there is no Better Auth option to make a linked account link-only per provider, other than our own hooks.

## 3. `genericOAuth` for Slack, Notion and Linear

### How `genericOAuth` works in 1.7.7

- Each config becomes a social provider, placed before the built-ins. A duplicate id shadows the built-in with a warning (`BA/plugins/generic-oauth/index.mjs:61-67`, `:270-272`).
- The plugin has **no endpoints of its own**. Linking is `authClient.linkSocial({ provider: "<id>" })` ([Generic OAuth: Link Account](https://better-auth.com/docs/plugins/generic-oauth#link-account)). This is what `apps/web/src/components/account-page.tsx:677` does for ChatGPT. `linkSocial`'s `provider` accepts any string (`CORE/social-providers/index.mjs:78`).
- PKCE defaults to **on** (`pkce ?? true`, `BA/plugins/generic-oauth/index.mjs:181`, `:206`).
- Authorization URL scopes are the call's scopes plus `config.scopes`, **space-joined** (`:182-186`; no `scopeJoiner` is passed). `scope` is reserved, so `authorizationUrlParams` can't override it (`CORE/oauth2/create-authorization-url.mjs:9-18`, `:54-57`).
- Config options: `getToken` replaces the code exchange (`:201`). `authentication: "basic"|"post"` applies to both the exchange and the refresh (`:214`, `:254`). `accessTokenExpiresIn` fills in a missing `expires_in` (`:217`, `:258`; `CORE/oauth2/utils.mjs:39-42`). `refreshTokenParams` (`:247`). **There is no option to replace the refresh request itself** (`BA/plugins/generic-oauth/types.d.mts`, option list).
- The default user info: the `id_token` claims if they include `sub` and `email`, otherwise `GET userInfoUrl` with `emailVerified: email_verified ?? false` (`:37-60`). The account id is `sub` for OIDC and `id` otherwise (`:146`). `emailVerified: false` makes the link fail unless the provider id is in `trustedProviders` (`BA/oauth2/link-account.mjs:43`). So Notion and Linear need a custom `getUserInfo` or `trustedProviders`.
- **Token endpoint errors:** the code exchange and the refresh throw only on a non-2xx response (`CORE/oauth2/validate-authorization-code.mjs:64-70`, `CORE/oauth2/refresh-access-token.mjs:64-69`). A 200 whose body reports an error becomes tokens with `accessToken: undefined`. `getAccessToken` then falls back to the stored token (`BA/api/routes/account.mjs:396`) **without** raising `FAILED_TO_GET_ACCESS_TOKEN`.
- Better Auth also has **built-in** `slack`, `notion` and `linear` social providers (`CORE/social-providers/{slack,notion,linear}.mjs`). They don't fit as they are:
  - built-in Slack is "Sign in with Slack" (OIDC `openid.connect.*` endpoints, `slack.mjs:7`, `:23`), which gives no user token with API scopes;
  - built-in Notion sends the refresh with `client_secret_post` (`notion.mjs:39-48`; the default when `authentication` isn't `basic`, `CORE/oauth2/token-endpoint-auth.mjs:5-7`), while Notion's docs say HTTP Basic;
  - Notion and Linear both report `emailVerified: false` (`notion.mjs:65`, `linear.mjs:76`), so linking fails without `trustedProviders`.

## 4. Google for a personal app

- **Testing mode:** "A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of 'Testing' is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile" ([Google OAuth 2.0 overview, Refresh token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)). Also: "Authorizations by a test user will expire seven days from the time of consent", with up to 100 test users ([Manage App Audience](https://support.google.com/cloud/answer/15549945)). With Gmail, Calendar or Drive scopes, a Testing-mode Connection needs a reconnect every week.
- **Other limits:** at most 100 refresh tokens per Google Account per client id. A token unused for six months stops working ([Refresh token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)).
- **Publishing:** with _In production_ status the app is open to any Google account. Unverified sensitive or restricted scopes show the "unverified app" screen, and a **lifetime cap of 100 users** applies ([Manage App Audience](https://support.google.com/cloud/answer/15549945)).
- **Verification exemption:** "If the app is for your personal use (fewer than 100 users)" verification isn't needed ([When is verification not needed](https://support.google.com/cloud/answer/13464323)). Otherwise, restricted scopes (Gmail is listed) need secure data handling and an annual assessment by a Google-empanelled assessor ([Restricted scope verification](https://support.google.com/cloud/answer/13464321)).
- **So, for one developer-user:** publish to _In production_, don't submit for verification, and click through the unverified-app warning. Refresh tokens then follow the normal rules, not the 7-day rule. **Unverified** whether the console's Publish step blocks or nags on restricted scopes before a verification submission. That has to be tried in the console.
- Gmail's restricted scopes include `gmail.readonly`, `gmail.modify` and full `https://mail.google.com/`. **Unverified** here: the exact per-scope classification (Google's scope list wasn't fetched for this ticket).

## Not verified

- Whether a GitHub sign-in that asks only for `read:user user:email`, after `repo` was granted, returns a token that keeps `repo`. Better Auth overwrites the row's token on sign-in (`BA/oauth2/link-account.mjs:208-226`), so if not, the Connection silently loses `repo` until it is linked again. The fix in config would be `account.updateAccountOnSignIn: false` or a separate provider id.
- Slack: whether `oauth.v2.user.access` returns `refresh_token` and `expires_in` at the top level when rotation is on (its reference example shows neither; the rotation page shows them at the top level for `oauth.v2.access`). Also whether non-rotating user tokens never expire, and whether its `id_token` carries `email`.
- Notion: access-token lifetime, PKCE acceptance, and whether a refresh with `client_secret_post` would also work.
- Linear: whether a space-joined `scope` is accepted, and the refresh error status.
- Google: whether the console lets an unverified app with restricted scopes be published without starting verification; and the exact restricted or sensitive class of the Calendar and Drive scopes we'd pick.
- Nothing here was run end to end against a live provider. All Better Auth behaviour comes from reading the 1.7.7 source.
