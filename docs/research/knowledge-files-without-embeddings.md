# How shipped agents answer from a user's files without embeddings

Research for [Research: How shipped agents answer from a user's files without embeddings](https://github.com/Daanish2003/bot-sdk/issues/726) (child of [Wayfinder: Bot step 11, Knowledge](https://github.com/Daanish2003/bot-sdk/issues/422)). Researched 2026-10-22.

## Question

How do shipped agents give an agent a user's files to answer from, without embeddings? For Claude Projects, Claude Code, ChatGPT and Codex, Cursor, OpenClaw and Hermes, and what Anthropic and others have published on agentic file search versus RAG: where the files live, how the agent learns they exist, how it searches, how it cites, and where it breaks down.

## Answer

- **Every coding agent surveyed now answers from files with no embeddings in the loop.** Claude Code uses glob, grep and Read (A1, CC2); Codex uses `rg` and `rg --files` through its shell (O2); Cursor turned its embedding index down in July 2026 in favour of grep-based retrieval (CU1, CU4).
- **The shared pattern has three layers** (A1, A3, CC1, O1, OC1, H1): (1) a small pointer or instruction file is injected into the prompt at session start (`CLAUDE.md`, `AGENTS.md`, `MEMORY.md`, `SOUL.md`), capped in size; (2) the agent sees only names and paths for everything else; (3) it finds and reads the rest on demand with list/find, grep and paged reads. Anthropic calls this "just-in-time" retrieval and "progressive disclosure".
- **Anthropic's published guidance:** start with agentic search and add semantic search only "if you need faster results or more variations"; semantic search is "usually faster … but less accurate, more difficult to maintain, and less transparent" (A2). Runtime exploration "is slower than retrieving pre-computed data" (A1). Under 200,000 tokens, "just include the entire knowledge base in the prompt" with caching (A4).
- **The chat products for non-technical users still use retrieval**, not shell search: Claude Projects puts all knowledge in context until it nears the window, then switches to a `project_knowledge_search` tool (CP1); ChatGPT's mechanism for project files isn't documented, and the API equivalent is vector-store `file_search` (O3, O4). Both switch to running code in a sandbox for spreadsheets and data files (CP3, O5).
- **The always-on agents (OpenClaw, Hermes) put a few small files in the prompt and search the rest.** OpenClaw's `memory_search` is hybrid vector + BM25 but falls back to keyword-only when embeddings are unavailable (OC1); Hermes searches past sessions with SQLite FTS5 only, no embeddings (H1).
- **Citations are file paths, sometimes with line numbers.** Codex's prompt asks for `path:line` references (O2); Claude Code's Grep returns file and line (CC2). None of the shell-search agents has a structured citation object; the API retrieval tools (OpenAI `file_citation`) do (O3).
- **Where it breaks:** binary formats (Read refuses `.xlsx`, `.zip`, `.parquet`; text extraction drops PDF images on most ChatGPT plans) (CC2, O4); single huge files (paged reads, 256 KB / 25,000-token caps) (CC2); pointer files that outgrow their cap get truncated (CC1, O1, OC1, H1); very large trees make plain `rg` slow, more than 15 s in Cursor's monorepos (CU2); and paraphrased or conceptual questions where no keyword matches, which is what Cursor's semantic-search evals measured (CU3) before Cursor dropped it anyway (CU4).

## Product by product

### Claude Code (and the Claude Agent SDK)

- **Where files live:** the working directory on disk. Instructions in `CLAUDE.md` / `AGENTS.md`; auto memory in `~/.claude/projects/<project>/memory/` as a `MEMORY.md` index plus one topic file per memory (CC1).
- **How it learns they exist:**
  - `CLAUDE.md` files above the working directory load in full at launch (up to 4 MiB; "target under 200 lines"); `@path` imports expand at launch, up to four hops deep (CC1).
  - `CLAUDE.md` in subdirectories loads only once Claude reads or edits a file there (CC1).
  - `MEMORY.md` is an index, "one line per memory", of which only the first 200 lines or 25 KB load; topic files are read on demand, and Claude Code warns the model when the index nears the cap (CC1).
  - Skills: only each skill's `name` and `description` are pre-loaded; `SKILL.md` and its linked files are read with Bash when relevant, so bundled context is "effectively unbounded" (A3).
  - Everything else: nothing in the prompt. "File paths, stored queries, web links" serve as lightweight identifiers, and "folder hierarchies, naming conventions, and timestamps" are themselves signals (A1); "the folder and file structure of an agent becomes a form of context engineering" (A2).
- **How it searches:** Glob (capped at 100 results, newest first), Grep on ripgrep with `files_with_matches` / `content` / `count` modes, and Read (CC2). On macOS/Linux Glob and Grep are off by default and Claude uses `find` and `grep` (embedded `bfs` and `ugrep`) through Bash (CC2). Large logs and uploads are handled with `grep` and `tail` (A2).
- **How it cites:** file path plus line number from Grep's `content` mode (CC2); no structured citation.
- **Where it breaks:** Read returns at most 25,000 tokens per call and refuses a whole file over 256 KB, so big files are read in pages or grepped (CC2). PDFs over 10 pages are read 20 pages at a time and need `pdftoppm` (CC2). Binary extensions (`.xlsx`, `.parquet`, `.zip`) are refused; the error points to a skill or a script that parses the format (CC2). Bash output over ~30,000 characters is saved to a file with a 2,000-character preview (CC2).

### Claude Projects (claude.ai)

- **Where:** uploaded to the project's knowledge base (CP2).
- **How it learns they exist / searches:** below the context limit, project knowledge is processed in context; when it "approaches or exceeds the context window limits", RAG mode turns on automatically and Claude "uses a project knowledge search tool" to pull relevant parts, for up to 10x capacity, paid plans only (CP1). The retrieval method isn't documented.
- **Data files:** with code execution on, Claude runs Python in a sandbox on uploaded CSV/TSV/XLSX (XLSX needs it), 30 MB per file (CP3).
- **Citations:** not documented (CP2).

### ChatGPT

- **Where:** uploaded files in a chat, project or GPT; 512 MB per file, 2M tokens per text file, about 50 MB for spreadsheets, 10 files per custom GPT (O4).
- **How it searches:** not documented for Projects. Only Enterprise has visual retrieval for PDFs; other plans use text-only retrieval that discards images (O4). The API's equivalent, `file_search`, searches vector stores "through semantic and keyword search" and returns `file_citation` annotations with `file_id` and `filename` (O3). Spreadsheets go to Code Interpreter, which copies input files into a container automatically (O5).
- **Not relevant to us beyond the contrast:** this is the embedding path the owner ruled out.

### Codex

- **Where:** the repository on disk.
- **How it learns they exist:** `AGENTS.md` files from the global Codex home, then from the project root down to the working directory, at most one per directory, concatenated root-first; loading stops at `project_doc_max_bytes`, 32 KiB by default; `AGENTS.override.md` replaces `AGENTS.md` in its directory (O1).
- **How it searches:** shell. "When searching for text or files, prefer using `rg` or `rg --files` respectively because `rg` is much faster than alternatives like `grep`. (If the `rg` command is not found, then use alternatives.)" (O2).
- **How it cites:** "File References … Use inline code to make file paths clickable", optional `:line[:column]`, "Do not provide range of lines" (O2).

### Cursor

- **Then:** an embedding index; Cursor's own eval found semantic search added 12.5% accuracy on average (6.5–23.5% by model) and 2.6% better code retention on codebases of 1,000+ files, used alongside grep, not instead of it (CU3).
- **Now:** staff, July 2026: "the older dedicated semantic search path was rapidly no longer helping in a meaningful way"; "Semantic/embeddings indexing is being turned down in favor of grep-based retrieval"; the search path has "no embeddings involved anywhere in it" (CU4). The docs now say Cursor "does not store embeddings of your codebase for search" (CU1).
- **How it searches:** Instant Grep, a local regex index (trigram / sparse n-gram posting lists) built because `rg` took more than 15 s on large monorepos; the index must be "very fresh" so the model can read its own writes (CU2). Broad searches can go to an Explore subagent with its own context window and a faster model, which returns a summary (CU1).
- **Takeaway:** the agent that measured semantic search's benefit most carefully still dropped it once models got better at grep (CU4). Speed at scale, not recall, is what made it build an index (CU2).

### OpenClaw

- **Where:** a workspace directory, `~/.openclaw/workspace` by default, which is the working directory for file tools (OC1).
- **How it learns they exist:** `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md` and `MEMORY.md` (main private session only) are injected at session start, capped at 20,000 characters per file and 60,000 in total; truncated files carry a marker and the prompt says to read the affected files directly (OC1). Daily `memory/YYYY-MM-DD.md` notes are read on demand (OC1).
- **How it searches:** `memory_search`, hybrid vector + BM25 over SQLite, falling back to "keyword-only ranking when embedding setup or a request fails" in `auto` / `local` mode; `provider: "none"` turns embeddings off (OC1). Other workspace files go through the ordinary read and exec tools.
- **How it cites:** indexed snippets keep "section context and source line references" (OC1).

### Hermes Agent (Nous Research)

- **Where:** `~/.hermes/memories/` for `MEMORY.md` (2,200 chars) and `USER.md` (1,375 chars), injected as a frozen snapshot at session start (H1). Past sessions in SQLite `~/.hermes/state.db` (H1).
- **How it learns they exist:** project context files (`.hermes.md`, `AGENTS.md`, `CLAUDE.md`, `.cursorrules`; first match wins) load at startup, capped between 20,000 and 500,000 characters by model, truncated 70% head / 20% tail; context files in subdirectories load as tools touch them, capped at 32,000 characters; every context file is scanned for prompt injection and blocked if flagged (H1).
- **How it searches:** `session_search` with SQLite FTS5 full-text search, returning "actual messages from the DB — no LLM summarization, no truncation" (H1). Users can inline files with `@file:path:10-25` or a folder listing with `@folder:` (capped at 200 entries); binary files are rejected; an expansion over 50% of the context window is refused (H1).

## What this means for Bot Knowledge

Inferences for the grilling tickets, not findings:

- **Placement:** every shell-search agent keeps the files as plain files in the agent's working tree, which matches "Knowledge is plain files on the Computer".
- **Discovery:** the agents that work without embeddings put a short, capped index in the prompt (a `MEMORY.md`-style one line per file, or `AGENTS.md`), never the file contents, and warn the model when the index is truncated. Knowledge needs a decision on whether the Bot gets such a listing or only a pointer to the directory.
- **Search:** `rg` / `grep`, `find` / `ls`, and paged reads are enough for every coding agent surveyed; Cursor's one data point says an index is for speed on very large trees, not quality.
- **Binary formats are the real gap:** PDFs, spreadsheets and Office files need either conversion to text on upload or a script/skill that reads them at question time (Claude Code's error points to exactly that). This is the case most likely to need an owner question.
- **Citations:** a path (plus line) is what these agents cite; evals can check that an answer names the right file.
- **Eval cases suggested by the breakdowns:** a fact found only by a keyword in one of many files; a paraphrased question with no shared keyword; a file bigger than one read; a PDF or spreadsheet; a truncated index.
