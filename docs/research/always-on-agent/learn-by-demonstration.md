# How agents learn a task from a demonstration

Research for [#706](https://github.com/Daanish2003/bot-sdk/issues/706) (child of map [#421](https://github.com/Daanish2003/bot-sdk/issues/421), Bot step 10, Skills). Feeds the grilling ticket [Learning by watching #710](https://github.com/Daanish2003/bot-sdk/issues/710). Researched 2026-10-21, code read at `093d4135` (main).

Claims marked **[inferred]** are my reading, not something a source states. Everything else cites its source.

## Question

How do shipped agents learn a task from a demonstration (lecture slide 10: "show it how you do a task on its computer and it saves the steps as a skill it can reuse")? What do they capture, when does capture start and stop, and how does the capture become reusable instructions? What can our E2B Computer record during a takeover of a Screen, and at what cost?

## Answer

1. **The shipped pattern is the same everywhere.** The user starts recording explicitly, does the task once, and stops explicitly. A model then drafts reusable instructions from the capture, and the user can refine them. The closest match to our design is OpenAI's **Record & Replay** (Codex and the ChatGPT desktop app, June 2026). It drafts a **skill** that says when to use it, the inputs it needs, the steps, and how to check the result. Replay is a new chat that names the skill and gives the new inputs, and it runs through Computer Use and browser actions [O1][O2].
2. **What they capture is mostly undisclosed.** OpenAI says only "the actions and window content needed to learn the workflow" [O1]. Anthropic's Claude in Chrome says only "perform the steps", and the result is saved as a shortcut [A1]. Google said Mariner's "teach and repeat" "learns plans for similar tasks" from one demonstration [G1]. The open-source recorders do show what they capture. **workflow-use** records DOM events (click, input, change, keydown, focus, navigation) with XPath, a CSS selector and the element's label, plus an rrweb session and a screenshot per event. It masks password fields [W1][W2].
3. **Narration is text and comes first.** OpenAI's tips are to state the goal and the inputs that will vary before recording, to keep the demo short, and to refine the skill afterward for hidden preferences such as naming conventions, defaults and decision points [O1]. workflow-use takes an optional "goal" text with the recording [W3]. None of the primary sources describes voice narration.
4. **Our Computer has no recording today, but three capture paths are already in the template.** A Screen is Xvfb + x11vnc + noVNC + Chromium with DevTools, plus `xdotool` and `scrot` (`plugins/computer/template/`). The Computer-use Helper already drives Chromium over CDP with `playwright-core` and takes `scrot` screenshots. The cheap paths are browser events through that CDP connection, and screenshots per event or on an interval. Neither needs a new dependency. Video needs `ffmpeg`, which our template doesn't install. That is a template change and a new dependency, so the owner decides (AGENTS.md §6).
5. **Privacy pulls against capture.** Our takeover tells the user "Type passwords and codes here yourself; the Bot never sees them" (`core/shared/i18n/en/bots.ts:75`). Operator likewise "does not collect or screenshot information entered by the user" in takeover mode [O3]. Today's takeover is for secrets. A demonstration is the opposite case, where the Bot is meant to watch. #710 has to decide whether "watch me" is a separate mode from takeover. If capture ever runs during a sign-in, it must mask password fields, as workflow-use does [W2], and stop screenshotting during it **[inferred]**.

What I take from this for #710 **[inferred]**:

- Every shipped product has an **explicit start and stop**, and the user can stop by saying so in chat (OpenAI). None records all the time.
- **The output is text the user can edit**, not a raw macro. OpenAI's output is literally a skill with "when to use" first, which matches our Skill definition in `CONTEXT.md` and slide 11's `SKILL.md` "Use this when…". workflow-use and OpenAdapt compile to deterministic programs because they replay with no model. We replay with a Computer-use Helper, so prose steps are enough.
- **Variables are named during drafting.** OpenAI asks for "inputs" and workflow-use for an `input_schema`. The skill draft should list what changes per run.
- **Review is a refine loop in chat** (OpenAI) or a person admitting the draft (OpenAdapt). None found saves silently.

## What our Computer can record during a takeover

How it works today (code read, not run):

- A **Screen** is slot N on display `:N`: `Xvfb :N` at 1280x800x24, `x11vnc` on 5900+N started `-viewonly`, websockify/noVNC on 6080+N, and Chromium with `--remote-debugging-port` 9222+N on a per-Bot profile (`packages/bot-sdk/plugins/computer/template/ai-chat-screen`). The template installs `xvfb x11vnc novnc websockify xdotool scrot x11-utils chromium` and **no ffmpeg** (`.../template/Dockerfile`). It is built with 1536 MiB for four Screens at about 215 MiB each.
- **Take control** runs `x11vnc -display :N -R noviewonly`, and Give back runs `-R viewonly` (`ai-chat-screen view|control`, called through `screenControl` in `packages/bot-sdk/plugins/bot/server/screen-view.ts`). The user's input then reaches X through x11vnc. The Host only proxies the noVNC page and its socket with a signed view token, and it does not look at the RFB bytes (`screenSocketHooks`).
- The takeover opens only from a Computer-use Helper's ask card (`packages/bot-sdk/plugins/bot/ui/computer-card.tsx`). While it is open, the Helper is `waiting` and holds the Screen (`heldScreen` accepts `running` or `waiting`).
- The Helper's **Browser tool** connects with `chromium.connectOverCDP` to the Screen's DevTools port (`plugins/bot/server/browser-tools.ts:130`). It reads pages as `page.ariaSnapshot({ mode: "ai" })` plus URL and title. Its **Desktop tool** runs `xdotool` and then `scrot -o` after a 0.5 s settle (`plugins/bot/server/desktop-tools.ts`). Screenshots go to the blob store as PNGs with a row each (`plugins/bot/server/screenshots.ts`).
- We use plain `e2b` 2.55.0, not `@e2b/desktop`. E2B's Desktop SDK has **no recording API**. It offers `screenshot()` (`scrot --pointer`), xdotool input, and `stream.start/stop` (x11vnc + noVNC, `viewOnly` option) [E1][E2]. Its desktop template installs `ffmpeg`, but the SDK doesn't use it [E3]. Our template follows the same design without a desktop environment.

## Open points for #710

These are not answered here:

- Does "watch me" open a Screen without a running Computer-use Helper? Today a Screen opens only while a Helper holds it.
- Is capture on for the whole takeover, or only between "start" and "stop" inside it? How does a sign-in during a demo stay out of the capture?
- Who drafts the Skill (the Bot in its Turn, a Helper, or a separate pass)? Slide 32 says screenshots go to a Helper and the main context gets what it found.
- Does the user see and confirm the draft? Every shipped example lets the user refine it before reuse.
