# Research: Self-hostable sandbox (Firecracker locally and on your own cloud)

Ticket: [#407 Self-hostable sandbox: Firecracker locally and on your own cloud](https://github.com/Daanish2003/ai-chat/issues/407) (child of map [#383](https://github.com/Daanish2003/ai-chat/issues/383)). Hosted vendors were covered in [#387](https://github.com/Daanish2003/ai-chat/issues/387) ([write-up](https://github.com/Daanish2003/ai-chat/blob/research/agent-computer-sandbox/docs/research/always-on-agent/agent-computer-sandbox.md)).
Researched: 2026-10-16, from project repos and docs, Microsoft, Apple, Lima, Docker and cloud provider docs. Facts only; no pick.

## Question

What does it take to run the agent's computer self-hosted, on a user's own machine and on an owner's own cloud? Where is KVM (and so Firecracker) available; which self-hostable sandbox projects exist and what do they offer for memory + disk snapshot/restore, wake latency, virtual displays / Chrome / VNC, licence, ops burden and a TypeScript client; and what does a Docker-only fallback keep?

## Answer in one paragraph

Firecracker needs read/write `/dev/kvm` on an x86_64 or aarch64 Linux host. That is available on Linux bare metal; on Windows 11 inside WSL 2 (`nestedVirtualization` defaults to `true`); on macOS only inside a Virtualization.framework Linux VM with nested virtualization on, which Apple and Lima document for M3 or later on macOS 15 or later (Docker Desktop's docs say nothing about it); in a Docker container given `--device /dev/kvm` (or `--privileged`) on a KVM host; on AWS (nested virtualization on virtual C7i/M7i/R7i/C8i/M8i/R8i and related families since Feb 2026, or `.metal`), GCP (most Intel types; not E2, Arm or AMD except N4D) and Azure (series such as Dv5 list "Nested Virtualization: Supported"); and on bare-metal rentals such as Scaleway Elastic Metal from EUR 27.99/month. Of the self-hostable projects, **memory + disk pause/resume with a TypeScript client** is documented by E2B's open-source runtime (Apache-2.0, single node via Docker Compose or Terraform on GCP/AWS/Azure, same `e2b` SDK) and CubeSandbox (Apache-2.0, E2B-SDK-compatible, auto-pause/resume; also runs on ordinary cloud VMs without `/dev/kvm` via a PVM kernel). microsandbox (Apache-2.0, beta, TS SDK) documents snapshot/restore of a running sandbox and runs on macOS, Linux and Windows. Arrakis (AGPL-3.0) ships VNC + Chrome and snapshot/restore but has only a Python SDK and was last pushed 2025-06. Daytona's open-source repo (AGPL-3.0) stopped being maintained in June 2026; its runner is Docker-based. Kata Containers has no checkpoint/restore; gVisor has `runsc checkpoint` (memory + state) usable through `docker checkpoint`; Cloud Hypervisor and Firecracker are VMMs with snapshot APIs but nothing above them. A Docker-only fallback keeps disk via volumes and `docker commit` (which excludes volumes); memory needs CRIU via the experimental `docker checkpoint`, which CRIU's own docs show working for an in-container VNC/X server, with caveats.

## 1. Where KVM, and so Firecracker, is available

Firecracker: "Firecracker supports x86_64 and aarch64 Linux"; it "requires read/write access to `/dev/kvm` exposed by the KVM module" ([getting started](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md)). The getting-started guide does not mention nested virtualization or running inside a container.

### E2B runtime (self-hosted)

- "the complete backend that powers E2B Cloud": API, per-node orchestrator that "drives Firecracker VMs (create, pause, resume, kill, checkpoint)", client proxy that "auto-resumes sandboxes", `envd` inside each VM, template builder; Apache-2.0 ([e2b-dev/infra](https://github.com/e2b-dev/infra); runtime repo [e2b-dev/runtime](https://github.com/e2b-dev/runtime)).
- E2B Embed: "runs the whole E2B stack, every feature included, on a single machine"; Docker Compose on a Linux host, Terraform on GCP, AWS or Azure, or one Kubernetes node; "Same SDK, same API as E2B Cloud"; "No E2B account and no license key needed". Limits: "Embed is one machine, by design"; "Plain HTTP ... with no TLS of its own" ([embed README](https://github.com/e2b-dev/runtime/blob/main/embed/README.md)).
- Host: Linux x86-64 or arm64 with KVM and 4 KiB pages; Ubuntu 24.04 recommended, kernel 6.8+ (6.10+ on arm64, for userfaultfd write-protect), cgroup v2; `/dev/kvm` and `/dev/net/tun`; 12 GiB RAM and 20 GiB disk recommended; `HUGEPAGES=2048` reserves 4 GiB for sandboxes; a pause needs free disk for the sandbox's whole memory. Compose services run `privileged: true` ([compose README](https://github.com/e2b-dev/runtime/blob/main/embed/compose/README.md), [compose.yaml](https://github.com/e2b-dev/runtime/blob/main/embed/compose/compose.yaml)).
- Pause/resume semantics and the desktop template are in the #387 write-up (E2B Cloud docs).

### CubeSandbox

- "built on RustVMM and KVM. It supports both single-node deployment and easy scaling to multi-node clusters. It is compatible with the E2B SDK"; "under 60ms with less than 5MB of memory overhead"; benchmark footnote: 60 ms single, P95 90 ms, P99 137 ms under 50 concurrent creations, bare metal ([README](https://github.com/TencentCloud/CubeSandbox)).
- Lifecycle: `paused` = "Snapshot persisted to disk. **Zero** CPU/memory cost. Full state preserved"; `on_timeout: "pause"`; auto-resume on request ([lifecycle](https://github.com/TencentCloud/CubeSandbox/blob/master/docs/guide/lifecycle.md)). v0.5 added AutoPause/AutoResume and ARM64; v0.7 cross-node pause/resume with an S3 backend (preview) (README release notes).
- Requires x86_64 Linux with KVM, or the PVM kernel path for cloud VMs without `/dev/kvm` ([PVM deploy](https://github.com/TencentCloud/CubeSandbox/blob/master/docs/guide/pvm-deploy.md)). First open-sourced in 2026 (README).

### microsandbox

- "easy, fast, programmable and local-first microVM runtime and library"; beta; macOS on Apple Silicon, Linux with KVM, Windows with WHP; snapshot create/restore of a running sandbox, `--cow-mem`; SDKs incl. TypeScript (`npm i microsandbox`); Apache-2.0 ([repo](https://github.com/zerocore-ai/microsandbox)). Whether a snapshot includes memory is implied by `--cow-mem`, not spelled out.

### Arrakis

- "self-hosted solution to spawn and manage Sandboxes for code execution and computer use" on Cloud Hypervisor; "Each sandbox runs Ubuntu inside with a code execution service and a VNC server running at boot", "Chrome pre-installed"; snapshot-and-restore restores processes and files; Linux only ("`cloud-hypervisor` only works with `/dev/kvm`"); Python SDK, REST, MCP ([README](https://github.com/abshkbh/arrakis)). AGPL-3.0; last push 2025-06-02 (GitHub API).

### Daytona (open source)

- "This repository is no longer maintained. As of June 2026, Daytona's core development has moved to a private codebase." It stays usable under its licence, AGPL-3.0 ([repo](https://github.com/daytonaio/daytona), [LICENSE at v0.190.0](https://github.com/daytonaio/daytona/blob/v0.190.0/LICENSE)).
- Docker Compose: API, proxy, runner, SSH gateway, Postgres, Redis, Dex, registry, MinIO, MailDev, Jaeger, PgAdmin; "not safe to use in production" ([docker/README](https://github.com/daytonaio/daytona/blob/v0.190.0/docker/README.md)).
- The OSS runner's code is in `apps/runner/pkg/docker` (container create/stop/commit/backup); no VM backend in that tree (read from the repo listing; inference that memory pause is absent).
- Hosted Daytona offers BYOC "custom regions": your runner nodes, Daytona's control plane ([BYOC](https://www.daytona.io/docs/en/bring-your-own-compute.md)).

### Kata Containers, gVisor

- Kata: hypervisors QEMU, Cloud Hypervisor, Firecracker, Dragonball, all KVM ([virtualization design](https://github.com/kata-containers/kata-containers/blob/main/docs/design/virtualization.md)); no checkpoint/restore ([limitations](https://github.com/kata-containers/kata-containers/blob/main/docs/Limitations.md)); VM templating clones a template VM for faster creation ([VM templating](https://github.com/kata-containers/kata-containers/blob/main/docs/how-to/what-is-vm-templating-and-how-do-I-use-it.md)).
- gVisor: checkpoint writes multiple files incl. a pages (memory) file; Docker restore must be into the same container (`--checkpoint-dir` unsupported); target needs the source's CPU features; with host networking, connected sockets get `ECONNRESET` after restore ([checkpoint/restore](https://gvisor.dev/docs/user_guide/checkpoint_restore/)).

### Firecracker and Cloud Hypervisor (bare VMMs)

- Firecracker snapshots: memory file + microVM state file + user-managed disks; diff snapshots "still in developer preview"; memory file mapped `MAP_PRIVATE` (lazy page-in) or served by a UFFD handler; restore must match hardware and software; "Network connectivity is not guaranteed after resume"; open vsock connections close; high restore latency on cgroups v1 ([snapshot support](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)). Boot ≤ 125 ms to guest `/sbin/init` with a minimal kernel and rootfs ([SPECIFICATION](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)). Devices: network, file-backed block, vsock, entropy, pmem, memory hotplug; no display device ([README](https://github.com/firecracker-microvm/firecracker/blob/main/README.md)). A display would be a virtual X server (e.g. Xvfb) inside the guest, as E2B, Daytona and Arrakis do.
- Cloud Hypervisor: `ch-remote pause`, `snapshot file:///dir`, `--restore source_url=...`; restored VM starts paused; `memory_restore_mode` `copy` / `ondemand` / `copyonwrite`; copy disk images separately ([snapshot_restore](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/snapshot_restore.md)).

## 3. Docker-only fallback

| Mechanism                              | What persists                                                                              | Caveats                                                                                                                                                                                                                                   | Source                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Named volumes                          | Files in the volume across container restarts and recreation                               | No process or memory state                                                                                                                                                                                                                | [Docker volumes](https://docs.docker.com/engine/storage/volumes/)                   |
| `docker commit`                        | Container filesystem changes and settings, as a new image                                  | "Commits do not include any data contained in mounted volumes"; pauses the container by default                                                                                                                                           | [docker commit](https://docs.docker.com/reference/cli/docker/container/commit/)     |
| `docker checkpoint` (CRIU)             | Process state as "a collection of files on disk"; restore with `docker start --checkpoint` | "This command is experimental"; needs CRIU ≥ 2.0; seccomp only on very recent kernels; containers with a terminal (`-t`) fail                                                                                                             | [docker checkpoint](https://docs.docker.com/reference/cli/docker/checkpoint/)       |
| CRIU limits                            | —                                                                                          | Cannot dump tasks that opened character/block devices (except null, zero, TUN); "impossible" for apps connected to a real X server; external connections need `--external` / `--tcp-established`; SysV IPC needs the IPC namespace dumped | [What cannot be checkpointed](https://criu.org/What_cannot_be_checkpointed)         |
| CRIU with an in-container VNC/X server | CRIU documents dumping and restoring `Xvnc` + a window manager + apps                      | Needs IPC and PID namespaces, detached session/terminal, `--tcp-established`; the VNC client freezes during dump and may time out                                                                                                         | [CRIU VNC](https://criu.org/VNC)                                                    |
| gVisor under Docker                    | Memory + state via `runsc checkpoint`                                                      | See gVisor above                                                                                                                                                                                                                          | [gVisor checkpoint/restore](https://gvisor.dev/docs/user_guide/checkpoint_restore/) |

Not found: any first-party CRIU or Docker document showing Chrome checkpointed and restored.

- Whether the E2B desktop template builds and runs on a self-hosted E2B node.
- Whether Docker Desktop (Mac or Windows) exposes `/dev/kvm` to containers.
- Hetzner dedicated server prices (page did not render them).
