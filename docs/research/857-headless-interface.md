# Research: headless SDK interfaces with an optional HTTP layer

Ticket: [#857](https://github.com/Daanish2003/bot-sdk/issues/857), a child of map [#853](https://github.com/Daanish2003/bot-sdk/issues/853).
Researched: 2026-10-25, at HEAD 57e2e4f3. Vocabulary follows `CONTEXT.md` (Host, Bot, Turn, Conversation).

## Question

How do libraries offer a headless, in-process interface plus an optional HTTP layer, and keep the client typed without a merged RPC router? For each library: how the Host mounts it, how auth context reaches it, how it streams, and how its framework adapters are shaped. Which shape lets a Host call `bots.send(userId, …)` directly and use HTTP only if it wants to?

## Today (verified in this repo)

- `createBotSdk()` returns `{ handler, plugin, migrate, start, stop, deleteUser, exportUser, rotateKeys }` (`packages/bot-sdk/core/server/create-chat.ts`).
- `handler` is one `(Request) => Promise<Response>`. Under `basePath` it serves the public plugin routes first. Every other request goes through `getUser(request)` and answers 401 without a user. Then `/rpc/*` goes to one oRPC `RPCHandler` over the routers that `mergeRouters` combines, and the rest goes to the private plugin `routes` (core: `GET /events`, which is SSE, and `GET /export`).
- The Host mounts four more handlers itself, each a plugin API method: `sdk.plugin("bot").webhookHandler` (`apps/web/src/routes/api/routines/webhook/$token.ts`), `sdk.plugin("bot").screenHandler` (`routes/api/screens/$.ts`), `sdk.plugin("bot").screenSocket` as a Nitro `defineWebSocketHandler` (`apps/web/server/routes/api/screens/[token]/websockify.ts`), and `sdk.plugin("channel").inbound("email", request)` (`routes/api/channels/email.ts`).
- In-process domain calls already exist, partly: `sdk.plugin(id)` returns whatever a plugin's `init` put in `api`, but the Turn-starting operations a Host would want (send a message, list Conversations) live only as oRPC procedures that need `{ user, sdk }` context.
- The client (`core/client/chat-client.ts`) types `rpc` as `RouterClient<UnionToIntersection<PluginRouters[keyof PluginRouters]>>`. Client plugins fill `PluginRouters` by declaration merging, so the client type is the merged router. `fetch` is already swappable ("the Host's handler when the Host runs the SDK in process").
- `useChat`'s transport is TanStack AI's `ChatClient` connection. The installed `@tanstack/ai-client@0.39.0` exports `fetchServerSentEvents`, `fetchHttpStream`, `stream(factory)` and `rpcStream(call)`. `stream` is documented as "a direct stream connection adapter (for server functions or direct streams)" that takes a function returning `AsyncIterable<StreamChunk>` (`node_modules/@tanstack/ai-client/dist/esm/connection-adapters.d.ts`, lines 465-528).

## Survey

### Better Auth: `auth.api.*` beside `auth.handler`

- **Headless API.** "When you create a new Better Auth instance, it provides you with an `api` object. This object exposes every endpoint that exists in your Better Auth instance", from plugins or the core. You call them as functions with `{ body, headers, query }`. They return plain objects, and `returnHeaders: true` or `asResponse: true` gets you the headers or the `Response`. Errors throw `APIError`. ([docs/concepts/api](https://better-auth.com/docs/concepts/api))
- **One definition, two surfaces.** Endpoints are built on better-call, "a tiny web framework that lets you call REST API endpoints as if they were regular functions and allows us to easily infer client types from the server" ([docs/concepts/api](https://better-auth.com/docs/concepts/api)). A plugin declares `endpoints: { name: createAuthEndpoint(path, opts, fn) }`, and the same object becomes both `auth.api.name` and the HTTP route ([docs/concepts/plugins](https://better-auth.com/docs/concepts/plugins)).
- **Auth context.** In-process, the caller passes the request `headers` and the endpoint reads the session from them (`auth.api.getSession({ headers })`). Middleware "only runs on `api` requests from a client. If the endpoint is invoked directly, the middleware will not run", while hooks run either way ([docs/concepts/plugins](https://better-auth.com/docs/concepts/plugins)). "Server-side requests made using `auth.api` aren't affected by rate limiting" ([docs/concepts/rate-limit](https://better-auth.com/docs/concepts/rate-limit)). So the HTTP-only concerns (rate limits, request middleware) live on the HTTP path, not in the domain call.
- **Typed client without a merged router.** Each client plugin carries a type-only `$InferServerPlugin: {} as ReturnType<typeof myPlugin>`. The client turns endpoint paths into camelCase methods (`/my-plugin/hello-world` becomes `myPlugin.helloWorld`), and `getActions($fetch)` adds hand-written methods ([docs/concepts/plugins](https://better-auth.com/docs/concepts/plugins)). The client type is assembled per plugin from the plugins array. No router object exists on the client. Our `BotSdkClientPlugin["~router"]` already copies this pattern. The difference is that we then intersect the routers into one oRPC client.
- **Framework adapters.** `toNextJsHandler(auth | handler)` accepts `{ handler }` or a bare `(Request) => Promise<Response>` and returns `{ GET, POST, PATCH, PUT, DELETE }`, all the same function ([source: integrations/next-js.ts](https://github.com/better-auth/better-auth/blob/main/packages/better-auth/src/integrations/next-js.ts)). For Pages Router and Node frameworks, `toNodeHandler` adapts it to Node `req`/`res` ([docs/integrations/next](https://better-auth.com/docs/integrations/next#create-api-route)). Adapters are a few lines over one web-standard handler.
- **Streaming.** Not applicable. Better Auth has no streaming endpoints.

### Mastra: server adapters and `@mastra/client-js`

- **Headless.** In-process calls go through the instance: `mastra.getAgentById('test-agent')`, then `agent.generate(...)`, or `agent.stream(...)` with `for await (const chunk of stream.textStream)` ([docs/agents/overview](https://mastra.ai/docs/agents/overview)). `mastra.getAgent('name')` also exists ([reference/core/getAgent](https://mastra.ai/reference/core/getAgent)).
- **Mounting.** Mastra is mounted by framework adapter packages (`@mastra/hono`, `@mastra/express`, `@mastra/fastify`, `@mastra/koa`, `@mastra/elysia`, `@mastra/nestjs`, `@mastra/next`, `@mastra/tanstack-start`). The Host builds its own app, then runs `new MastraServer({ app, mastra })` and `await server.init()`. `init()` registers context middleware, auth middleware, user middleware and the routes (`/api/agents`, `/api/workflows`, …) under a configurable `prefix`. ([docs/server/server-adapters](https://mastra.ai/docs/server/server-adapters))
- **Auth.** Auth is configured on the Mastra instance and required on all routes by default, with per-route overrides through `customRouteAuthConfig` (`'GET:/api/health': false`). A request context is attached to every request by the context middleware. ([docs/server/server-adapters](https://mastra.ai/docs/server/server-adapters)) _Unverified_: how a handler reads Host-specific values from that context. The page doesn't say.
- **Client typing.** `new MastraClient({ baseUrl, headers, credentials, retries })`, and agents are addressed by string id ([reference/client-js/mastra-client](https://mastra.ai/reference/client-js/mastra-client)). Nothing on the page says the client is inferred from the server. Its types look hand-written and generic (`GetAgentResponse`). _Unverified that there is no inference._
- **Streaming.** `agent.stream()` on the client returns a response whose body is read with `processDataStream({ onChunk })`, or raw with `getReader()` ([reference/client-js/agents](https://mastra.ai/reference/client-js/agents)). _Unverified_: the exact wire format (SSE or NDJSON). Neither page names it.
- **Lesson.** An adapter per framework is a lot of packages to maintain. Mastra takes that on because it registers routes into the Host's router. A single fetch handler avoids it.

### AI SDK UI: the message stream protocol and `useChat`

- **Protocol as the contract.** The UI message stream is SSE: `data:` lines of JSON parts (`start`, `text-start`/`text-delta`/`text-end`, `tool-*`, `data-*`, `finish`, …), ending with `data: [DONE]`. A custom backend sets the response header `x-vercel-ai-ui-message-stream: v1`. ([docs/ai-sdk-ui/stream-protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol))
- **Any route.** `useChat` POSTs to `/api/chat` by default through `DefaultChatTransport({ api, headers, body, credentials, prepareSendMessagesRequest })`. Auth reaches the route as the Host's own cookies or headers (for example `headers: () => ({ Authorization: … })`). ([docs/ai-sdk-ui/transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport))
- **No HTTP at all.** `new DirectChatTransport({ agent })` calls the agent's `stream()` in-process, without an endpoint, and has no stream reconnection ([docs/ai-sdk-ui/transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport)). TanStack AI, which this repo uses, has the same idea in `stream(factory)` and `rpcStream(call)` (see "Today").
- **Lesson.** A documented wire protocol plus a pluggable transport means the server side is "anything that emits these chunks". The library doesn't need to own the route.

### Hono RPC

- **Typing.** Export `type AppType = typeof route`, and `hc<AppType>(baseUrl)` infers inputs from validators and outputs from `c.json()`. Large apps must chain handlers and sub-routers (`app.route('/authors', authors).route('/books', books)`) to keep the inference. ([docs/guides/rpc](https://hono.dev/docs/guides/rpc))
- **Cost.** "When using RPC, the more routes you have, the slower your IDE will become." The fixes are to compile the client type ahead with `tsc`, split the client per sub-app, and match Hono versions on both sides ([docs/guides/rpc](https://hono.dev/docs/guides/rpc)).
- **In-process.** `hc` accepts a custom `fetch` ([docs/guides/rpc](https://hono.dev/docs/guides/rpc)), and `testClient(app)` gives a typed client over an app instance ([docs/helpers/testing](https://hono.dev/docs/helpers/testing)). _Unverified on those pages_: that `testClient` skips the network, though it is built for tests.
- **Fit.** The type comes from one Hono app, which is the merged router again, and it ties the SDK to Hono. Not a fit for a Host-agnostic SDK.

### oRPC contract-first (our current RPC library)

- **Contract with no server code.** `oc.input(schema).output(schema).errors({...}).meta(...)` builds a procedure contract with no `.handler` ([contract-first/define-contract](https://orpc.dev/docs/contract-first/define-contract)). The server runs `implement(contract)`, optionally with `.$context<...>()`, and then `.router(...)` gives "full type-checking and runtime contract enforcement" ([contract-first/implement-contract](https://orpc.dev/docs/contract-first/implement-contract)). _Unverified on those pages_: the name of the client type derived from a contract (`ContractRouterClient`). The pages don't show it.
- **In-process.** `call(procedure, input, { context })` runs one procedure, and `createRouterClient(router, { context })` gives a typed in-process client whose context can be per call ([client/server-side](https://orpc.dev/docs/client/server-side)). This is the "headless" path oRPC offers. It still carries the procedure shape (`client.ping(input)`), not a domain shape.
- **Streaming.** A handler that is an `async function*` streams over SSE ("event iterator"). `signal` aborts on disconnect, and `withEventMeta` with `lastEventId` supports resuming ([event-iterator](https://orpc.dev/docs/event-iterator)).
- **WebSocket.** `RPCHandler` from `@orpc/server/websocket` with `handler.upgrade(ws, { context })`, and an `RPCLink` from `@orpc/client/websocket` ([adapters/websocket](https://orpc.dev/docs/adapters/websocket)).
- **Lesson.** With a contract per feature, a client can be typed per feature without importing server code and without one merged router. The HTTP handler can still nest the routers by key (`{ bot, models, … }`), which needs no intersection type.

### TanStack Start server functions

- **Typed without a router.** `createServerFn().handler(...)` is called like a function from loaders, components and "other server functions". The build swaps the implementation for an RPC stub on the client. ([guide/server-functions](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions))
- **Auth.** `createMiddleware({ type: 'function' }).server(({ next }) => next({ context: { userId } }))`, attached with `.middleware([...])`, and the handler reads `context.userId`. Global request middleware goes in `src/start.ts`. ([guide/middleware](https://tanstack.com/start/latest/docs/framework/react/guide/middleware))
- **Streaming.** A server function may return a typed `ReadableStream<T>` or be an `async function*` ([guide/streaming-data-from-server-functions](https://tanstack.com/start/latest/docs/framework/react/guide/streaming-data-from-server-functions)).
- **Fit.** "Server functions are meant to be called by your TanStack Start application." For external callers the docs point to server routes ([guide/server-functions](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)). A library can't ship them for a Host on another stack. But a Start Host can wrap our headless calls in its own server functions and feed them to TanStack AI's `stream()`, with no SDK HTTP at all.

### Liveblocks, Convex, Inngest

- **Liveblocks.** Liveblocks is a hosted service. The Host writes one small auth route: `new Liveblocks({ secret })` from `@liveblocks/node`, then `liveblocks.prepareSession(user.id, { userInfo })`, `session.allow(room, ["*:write"])` and `const { status, body } = await session.authorize()`, returning `new Response(body, { status })`. The client gets `authEndpoint="/api/liveblocks-auth"`. ([authentication/access-token](https://liveblocks.io/docs/authentication/access-token), [access-token/nextjs](https://liveblocks.io/docs/authentication/access-token/nextjs)) **Lesson**: the Host owns auth entirely. The library only needs a user id and grants, never the Host's session.
- **Convex.** Convex is a hosted backend. Functions are referenced through generated code (`api.messages.list`). `ConvexHttpClient.query(...)` serves one-off calls, and `ConvexClient.onUpdate(...)` serves subscriptions ([client/javascript/node](https://docs.convex.dev/client/javascript/node)). `ConvexClient` "subscribes to Convex query functions and executes mutations and actions over a WebSocket", and auth is `setAuth(fetchToken)`, an async function that returns a JWT ([api ConvexClient](https://docs.convex.dev/api/classes/browser.ConvexClient)). **Lesson**: typing by generated function references, not by a router type. There is nothing for a Host to mount.
- **Inngest.** `serve({ client, functions })` comes per framework from `inngest/<framework>`. On Next.js it returns `{ GET, POST, PUT }`. On Express and Hono it is one handler mounted at `/api/inngest` (`app.use(...)`, `app.on([...], ...)`). On Lambda, Workers, Bun and Elysia it is one function. `streaming: true` streams the response back to Inngest for longer timeouts. ([learn/serving-inngest-functions](https://www.inngest.com/docs/learn/serving-inngest-functions)) Application code sends events with `inngest.send({ name, data })`, and services without an SDK use the HTTP Event API ([docs/events](https://www.inngest.com/docs/events)). _Unverified_: whether `inngest.send` posts to Inngest's event API under the hood. The page doesn't say. **Lesson**: the domain call (`send`) is separate from the mounted handler, and the handler serves the platform, not the end user.

## What this means for the Bot SDK

The shape that lets a Host call `bots.send(userId, …)` directly is **Better Auth's: one headless instance whose domain methods are the primary interface, with the HTTP handler as an optional transport built from the same definitions.** Concretely:

1. **Domain methods first, with the user as an argument.** `sdk.bot.send({ userId, conversationId, message })`, `sdk.conversations.list({ userId })` and so on, callable in-process with no `Request`. Liveblocks and Inngest show that a library only needs a user id, never the Host's session. This differs from Better Auth, which reads headers, and keeps our "no imposed auth" criterion (a). `getUser` moves to the HTTP layer only.
2. **HTTP-only concerns stay on the HTTP path.** Per-user rate limits, the 401 and route matching live in the optional handler, as Better Auth keeps middleware and rate limits off `auth.api` ([plugins](https://better-auth.com/docs/concepts/plugins), [rate-limit](https://better-auth.com/docs/concepts/rate-limit)). A Host that calls in-process applies its own.
3. **The HTTP layer is a thin adapter over the domain methods.** It can keep oRPC. Procedures become one-line wrappers that read `context.user.id` and call the domain method. Routers nest by feature key (`{ bot, models, … }`) instead of being intersected, so no merged router type is needed. The four extra handlers (webhook, screens, email inbound, screen socket) stay `(Request) => Response` functions and a socket handler on the feature's API, mounted by the Host, as today.
4. **The typed client stays per feature.** Either keep Better Auth's `$InferServerPlugin`-style type-only link per client plugin (already our `"~router"`), or move to oRPC contracts per feature so the client never imports server code ([define-contract](https://orpc.dev/docs/contract-first/define-contract)). Hono RPC is out: one merged app type, Hono-only, and slow at scale ([rpc](https://hono.dev/docs/guides/rpc)).
5. **Streaming has two faces.** In-process, a domain method returns an `AsyncIterable` of the Turn's chunks and the Conversation events. Over HTTP the same iterable is served as SSE (oRPC event iterator or our `/events` route). The React side then picks a TanStack AI connection: `fetchServerSentEvents(url)` for our handler, or `stream(() => hostServerFn(...))` when the Host wraps the headless call itself (installed `@tanstack/ai-client@0.39.0`, `connection-adapters.d.ts`). This mirrors AI SDK's `DefaultChatTransport` and `DirectChatTransport` ([transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport)).
6. **Framework adapters stay tiny.** Ship a `toNextJsHandler`-style helper (method map over one fetch handler) and a Node `req`/`res` adapter, as Better Auth does. Avoid Mastra's package-per-framework model. The only non-fetch surface is the screen WebSocket, which needs a per-runtime adapter (today Nitro's `defineWebSocketHandler`; oRPC's `upgrade(ws, { context })` shows a portable `ws`-style shape).

## Open points for the map

- Whether the client is typed by a type-only server link (Better Auth) or by contracts (oRPC). This belongs to the "typed client and UI distribution" item on #853.
- How the in-process Turn stream relates to the runner. A Turn is a runner job (ADR 0011), so `send` likely returns an id plus a subscription, not the model stream itself. This needs checking against `core/server/chat/conversation-events.ts` when it is specified.
- Not researched: Hono's `streamSSE` and WebSocket helpers, Mastra's exact stream wire format, Inngest's `send` transport.
