# Research: How Better Auth's schema DSL and `generate` work

Ticket: [#436 How Better Auth's schema DSL and generate work](https://github.com/Daanish2003/ai-chat/issues/436) (child of map [#411](https://github.com/Daanish2003/ai-chat/issues/411)).
Researched: 2026-10-16, against **Better Auth 1.7.7**, the version in this repo's `pnpm-lock.yaml` (`better-auth@1.7.7`, `@better-auth/core@1.7.7`, `@better-auth/drizzle-adapter@1.7.7`). Sources: the published 1.7.7 packages under `node_modules/.pnpm` (core ships its `src/`), the GitHub tag [`v1.7.7`](https://github.com/better-auth/better-auth/tree/v1.7.7), and the v1.7 docs ([CLI](https://better-auth.com/docs/concepts/cli), [Plugins](https://better-auth.com/docs/concepts/plugins)).

## Question

How do Better Auth's plugin schema DSL and its `generate` CLI work, and what would a Drizzle-only version need for the Bot SDK's field DSL ([ADR 0020](../adr/0020-one-core-sdk-with-plugins.md), proposed; decision in [#435](https://github.com/Daanish2003/ai-chat/issues/435))?

## Answer

- **The DSL is plain data.** A field is `{ type, required, unique, references: { model, field, onDelete }, defaultValue, onUpdate, input, returned, fieldName, index, sortable, bigint, transform, validator }`. Types are only `string | number | boolean | date | json | string[] | number[] | string-literal[]` (the last is an enum). Tables are `{ fields, indexes?, modelName?, disableMigration? }`; table indexes are `{ fields, name?, unique? }` and nothing else.
- **Merge is a spread.** For each plugin, in order, `schema[table].fields` is spread onto the earlier ones; for the four core tables the order is core fields, then plugin fields, then the user's `additionalFields`. Later wins, silently. Indexes are concatenated and de-duplicated. `id` is never declared: it is always added.
- **`generate` writes one file** (default `./auth-schema.ts`, `--output` to change), the whole schema every time, overwritten. Not per plugin. It produces Drizzle table code plus a `defineRelationsPart` block. It does **not** write migrations: for Drizzle you then run your own `drizzle-kit`.
- **`migrate` only works with the Kysely adapter.** It introspects the live database and is **additive only**: create missing tables, add missing columns, add missing indexes. It never drops, renames or changes a type (it only warns on a type mismatch), and refuses to add a required column without a default to a populated table.
- **Types are inferred by walking the `plugins` tuple** and mapping each field's `type`/`required`/`defaultValue`/`input`/`returned` to a TS property, but only for the core models (`user`, `session`, `account`, `verification`, `rateLimit`). A plugin's own tables get no inferred row type; the plugin writes its own.
- **What a Drizzle-only version needs**, for this repo's `chat` schema: real `pgEnum`s, `jsonb` with `$type<T>()`, `uuid` ids and composite primary keys, self-references, `timestamp withTimezone`, `date`, `bytea`, `vector(n)`, generated `tsvector` columns, SQL defaults, and indexes with `using` (gin, hnsw), opclasses, expressions, `desc` and `where`. Better Auth's DSL has none of these (table below). The simplest route is to let a plugin's table carry a raw Drizzle escape hatch instead of growing the DSL to cover Postgres.

## The field DSL

Source: [`packages/core/src/db/type.ts` @ v1.7.7](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/type.ts) and [`packages/core/src/db/plugin.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/plugin.ts).

```ts
type DBFieldType =
  | "string"
  | "number"
  | "boolean"
  | "date"
  | "json"
  | `${"string" | "number"}[]`
  | Array<LiteralString>; // an enum, e.g. ["up", "down"]
```

| Option                        | Meaning (from the source comments)                                                                                                                                                                                              | Default               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `required`                    | Must be set on a new record; generator adds `.notNull()`                                                                                                                                                                        | `true`                |
| `returned`                    | Included in response bodies; `false` removes it from the output type                                                                                                                                                            | `true`                |
| `input`                       | Client may set it on create; `false` removes it from the input type                                                                                                                                                             | `true`                |
| `defaultValue`                | Value or `() => value`. "This will not create a default value on the database level", but the Drizzle generator does emit `.defaultNow()` for a date whose function body contains `new Date()`, and `.default(x)` for a literal | none                  |
| `onUpdate`                    | `() => value`; generator emits `.$onUpdate(fn)` for `date` fields only                                                                                                                                                          | none                  |
| `transform.input` / `.output` | Map the value on write / read                                                                                                                                                                                                   | none                  |
| `references`                  | `{ model, field, onDelete? }`, `onDelete` one of `no action, restrict, cascade, set null, set default`                                                                                                                          | `onDelete: "cascade"` |
| `unique`                      | Column `.unique()`                                                                                                                                                                                                              | `false`               |
| `index`                       | Single-column index (unique index if `unique` too)                                                                                                                                                                              | `false`               |
| `bigint`                      | `bigint` instead of `integer` for `number`                                                                                                                                                                                      | `false`               |
| `sortable`                    | Only affects MySQL (`varchar(255)` instead of `text`)                                                                                                                                                                           | `false`               |
| `fieldName`                   | Physical column name; the key stays the logical name                                                                                                                                                                            | the key               |
| `validator.input` / `.output` | A Standard Schema (Zod, Valibot, ArkType)                                                                                                                                                                                       | none                  |

Table level (`BetterAuthPluginDBSchema`): `fields`, `indexes?: { fields: [string, ...string[]] (max 16), name?, unique? }[]`, `modelName?` (physical table name, defaults to the key), `disableMigration?`. Index fields use the logical keys, resolved to columns later ([`database-index.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/database-index.ts); names are capped at 63 bytes and hashed when generated). There is no way to declare the primary key: every table gets `id` (text, or `uuid` / identity when `advanced.database.generateId` is `"uuid"` / `"serial"`).

A user can rename a plugin's tables and columns without touching its code through `mergeSchema(schema, { table: { modelName, fields: { key: "column" } } })`, which only rewrites `modelName` and `fieldName` (`better-auth/dist/db/schema.mjs`, `mergeSchema`). Plugins call it on their `schema` option (docs: [Organization, Customizing the Schema](https://better-auth.com/docs/plugins/organization#customizing-the-schema)).

## How plugin fields merge onto core tables

Source: [`packages/core/src/db/get-tables.ts` @ v1.7.7](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/get-tables.ts), `buildAuthTables`.

1. Reduce over `options.plugins` in order. For each `[key, table]` of `plugin.schema`: `fields = { ...acc[key]?.fields, ...table.fields }`, `indexes = mergeTableIndexes(acc[key]?.indexes, table.indexes)` (concatenate, drop exact duplicates by `[name, fields, unique]`), `modelName = table.modelName || key`.
2. Split out `user`, `session`, `account`, `verification`; the rest are plugin tables.
3. Each core table is `{ ...coreFields, ...pluginFields, ...options.<table>.additionalFields }`, with an `order` (user 1, session 2, account 3) used to create tables in foreign-key order.
4. Plugin tables and the optional `rateLimit` table are appended.

So a plugin adds a field to a core table by declaring a table with the core table's key. Conflicts are not detected: the last spread wins, including over a core field.

## How `generate` writes a Drizzle schema

- The CLI package is `auth` (bin `better-auth`), run as `npx auth@latest generate` ([CLI docs](https://better-auth.com/docs/concepts/cli); [`packages/cli/package.json`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/cli/package.json)). It loads the Host's `auth.ts`, so plugins and customizations are included. `--adapter drizzle --dialect pg` generates without a database connection.
- Dispatch ([`packages/cli/src/generators/index.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/cli/src/generators/index.ts)): if the adapter has `createSchema`, use it; otherwise the built-in generator for `adapter.id` (prisma, drizzle, kysely). In 1.7.7 the Drizzle adapter's `relations-v2` entry implements `createSchema` and lazily imports [`packages/drizzle-adapter/src/relations-v2/generate-drizzle-schema.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/drizzle-adapter/src/relations-v2/generate-drizzle-schema.ts).
- The generator calls `getAuthTables(options)` and emits **one string of code for every table**, writes it to `file || "./auth-schema.ts"`, `overwrite: true` if it exists, `append: false`. It tries to format it with Prettier if installed.
- Per table: `export const <model> = pgTable("<snake_name>", { id: text('id').primaryKey(), ... }, (table) => [index(...).on(...), uniqueIndex(...)])`, or `<x>Schema.table` when `schemaName` is set (then it also emits `export const <x>Schema = pgSchema("<name>")`).
- Postgres type map: `string` → `text`, `boolean` → `boolean`, `number` → `integer` / `bigint({ mode: 'number' })`, `date` → `timestamp` (no time zone), `json` → `jsonb`, `string[]` → `text().array()`, `number[]` → `integer().array()`, **enum literal array → `text('x', { enum: [...] })`**, not a `pgEnum`. A field that references `id` becomes `text` (or `uuid` / `integer` per `generateId`).
- References: `.references(() => <model>.<field>, { onDelete: '<action>' })`.
- Relations: one `defineRelationsPart({ ...tables }, (r) => ({ ... }))` block (Drizzle relations v2): `one` for each FK on the table, `many` (or `one` if the FK is unique) for each FK pointing at it.
- It does **not** write SQL migrations for Drizzle. The docs: "If you're using Prisma, Drizzle, or another ORM, run `npx auth@latest generate` first, then apply the schema using your ORM's migration tool" ([Rate Limit, Storage](https://better-auth.com/docs/concepts/rate-limit#storage)).

## How `migrate` diffs against a live database

Source: [`packages/better-auth/src/db/get-migration.ts` @ v1.7.7](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/db/get-migration.ts), `getMigrations` (read in the published `dist/db/get-migration.mjs`).

- Only for the built-in Kysely adapter; otherwise it logs "Only kysely adapter is supported for migrations. You can use `generate` command..." and exits.
- Introspects with `db.introspection.getTables()` plus an index map, then for each table: missing → `toBeCreated` (ordered by `order`); present → each missing column → `toBeAdded`; each configured index not in the database → `toBeAddedIndexes`. An existing index with the same name but different columns or uniqueness throws.
- Existing columns are not changed: a type mismatch only logs `Field x in table y has a different type in the database`, and a nullable column declared required only warns.
- Adding a required column with no default to a table with rows throws `UnsafeMigrationError` (or is reported when `throwOnUnsafe: false`).
- Never drops tables, columns or indexes. Returns `runMigrations()` and `compileMigrations()` (the SQL text).
- 1.7 also ships a schema check ([`packages/core/src/db/schema-diff.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/schema-diff.ts), `diffSchema`): it reports `missing-table`, `missing-column` and `unexpected-required-column` (a column Better Auth doesn't write that is `NOT NULL` with no default). For Drizzle it checks the schema object, not the database, and runs at runtime unless `advanced.database.validateSchema: false`; `npx auth check schema` runs it on demand ([CLI docs, Check](https://better-auth.com/docs/concepts/cli#check)).

## How additional-field types are inferred

Source: `type.ts` (above) and [`packages/core/src/db/schema/user.ts`](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/db/schema/user.ts) (session, account, verification, rate-limit alike).

- `User<DBOptions, Plugins> = Prettify<BaseUser & InferDBFieldsFromOptions<DBOptions> & InferDBFieldsFromPlugins<"user", Plugins>>`, where `BaseUser` is `z.infer` of the core Zod schema.
- `InferDBFieldsFromPlugins<Model, Plugins>` recurses over the plugins tuple; for each plugin whose `schema` has `[Model]: { fields }`, it intersects `InferDBFieldsOutput<fields>`.
- `InferDBValueType`: `string` → `string`, `number` → `number`, `boolean` → `boolean`, `date` → `Date`, `json` → `Record<string, any>`, `string[]` → `string[]`, `number[]` → `number[]`, a literal array → the union of its members.
- Output: `returned: false` drops the key; `required: false` without a literal `defaultValue` makes it optional and `| null`. Input: `input: false` drops it; `required: false` or a literal `defaultValue` makes it optional.
- This only works because plugin objects keep their literal schema type (so `required: false` stays `false`, not `boolean`). `json` has no way to name its shape.
- The docs: "if you add additional fields to a `user` or `session` table, the types will be inferred automatically on `getSession` and `signUpEmail` calls" ([Plugins](https://better-auth.com/docs/concepts/plugins)).

## What a Drizzle-only version would need

Inferences from the above, for the field DSL ticket to decide:

- **Keep from Better Auth:** plain-data fields; merge by spreading plugin fields onto core tables in plugin order; type inference over a `plugins` tuple; `references.onDelete` defaulting to `cascade`; `input`/`returned` for the oRPC boundary.
- **Fix what Better Auth leaves loose:** throw on a field-name clash instead of letting the last spread win; let the core and plugins choose their own primary key (uuid, text, composite).
- **Postgres-only types:** add `uuid`, `timestamptz`, `calendarDate`, `bytea`, `enum` (a real `pgEnum` in `chat`), `json<T>` (carrying a TS type), `vector(n)`. Or let a field supply a Drizzle column builder directly.
- **Indexes:** Better Auth's `{ fields, unique, name }` covers only 4 of this repo's ~20 non-trivial indexes. Either add `using`, `opclass`, `where`, `desc` and expressions, or let a table supply Drizzle's `(table) => [...]` extras callback verbatim.
- **Escape hatch:** since the target is Drizzle only, the smallest design is "the DSL for fields a plugin adds to another plugin's or the core's table; plain Drizzle `chatSchema.table(...)` for a plugin's own tables". `generate` then only has to emit the core tables with the added columns, re-export plugin tables, and run `drizzle-kit generate` for migrations, instead of reproducing Postgres in a DSL.
- **Migrations:** Better Auth gives Drizzle users no migrations; this repo needs them (`drizzle-kit` today), plus the `CREATE EXTENSION` steps `migrate.ts` runs first.
