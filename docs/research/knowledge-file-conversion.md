# Turning PDF, DOCX, HTML and CSV into text for a Bot's Knowledge

Research for [Research: Turning PDF, DOCX, HTML and CSV into text](https://github.com/Daanish2003/bot-sdk/issues/727) (child of [Wayfinder: Bot step 11, Knowledge](https://github.com/Daanish2003/bot-sdk/issues/422)). Researched 2026-10-22.

## Question

How can PDF, DOCX, HTML and CSV files become text that `grep` and `read` can use, on a Bot's Computer (the E2B template in `packages/bot-sdk/plugins/computer/template`) or at upload time on the server? Which converters exist, with their licences, install size and output quality? What does the template ship, and what would adding a converter cost? How do scanned PDFs and very large files behave?

## Answer

- **The server already converts all four formats, with no native binary and permissive licences.** `extractKnowledgeText` in `packages/bot-sdk/plugins/assistant/server/knowledge/extract.ts` turns PDF (text layer, pdf.js), DOCX (mammoth, then cheerio), HTML (cheerio) and CSV (csv-parse, each row written as `header: value`) into plain text, after the encryption and zip-bomb checks in `ooxml.ts`. It is self-contained: it does not depend on the chunker, embeddings or tables. Moving it to the Bot-side home is the cheapest path.
- **The template has no converter.** It ships `bash ca-certificates curl git jq tar gzip unzip zip python3 procps fonts-dejavu-core` plus the Screen packages (`xvfb x11vnc novnc websockify python3-jwcrypto xdotool scrot x11-utils chromium`). No poppler, pandoc, pip or Node.
- **`read` can't show a PDF or DOCX**, so converting them is required. HTML and CSV are already UTF-8 text that `read` and `grep` handle as they are; converting them is only a quality gain (no markup, rows that name their columns).
- **Recommendation: convert at upload on the server with the existing `extract.ts`, and write the text beside the original on the Computer.** Optionally add `poppler-utils` (about 6 MB) to the template so a Bot can convert PDFs it fetches itself. Don't add pandoc (about 170 MB) or markitdown (needs pip and a virtualenv). Leave OCR out; a scan fails as `no_text`, as today.

## What the Computer can read today

From `packages/bot-sdk/plugins/bot/server/computer-tools.ts`:

- `decodeText` refuses a file that contains a NUL byte ("is a binary file, which read can't show. Use shell…") and one that is not UTF-8. PDFs and DOCX (a ZIP) always contain NUL bytes, so `read` refuses them. HTML and CSV in UTF-8 read normally.
- One `read` returns at most `maxPageCharacters = 10_000` characters of numbered lines and pages through longer files. `edit` loads at most `maxTextBytes = 5_000_000`. A large converted text file is therefore readable page by page, and `grep` has no size limit of its own.
- Shell commands time out after `defaultCommandTimeoutMs = 60_000` unless the caller passes another limit (`packages/bot-sdk/plugins/computer/server/plugin.ts`). A conversion run on the Computer has to fit that.

## The template

`packages/bot-sdk/plugins/computer/template/Dockerfile` is `debian:bookworm-slim` with one `apt-get install --no-install-recommends` layer (packages listed above) and the `ai-chat-screen` script. Its comments and `packages/bot-sdk/README.md` (section on the Computer template) say:

- The template name is its version: any change to the Dockerfile needs a new name (for example `ai-chat-computer-v3` → `-v4`), and every Computer is rebuilt on its next wake. `apps/web` holds the name in `computerTemplate` (`src/services.ts`).
- It's built with `pnpm dlx @e2b/cli@2.22.0 template create … --memory-mb 1536`. On the local Embed, builds can fail with `mmap memfd: cannot allocate memory` and need the WSL page cache dropped.

E2B's limits ([docs.e2b.dev/sandbox-template](https://docs.e2b.dev/sandbox-template)): up to 10 GiB disk per build on Hobby (20+ GiB on Pro), and a build may run up to 1 hour. No image-size limit is stated. Every package below fits easily; the real costs are a template bump and a rebuild of every Computer.

### Output quality

- **PDF:** pdf.js and pdftotext both read only the text layer. `extract.ts` joins pdf.js text items into lines and collapses spaces, which loses columns and tables. pdftotext's default reading order handles multi-column pages; `-layout` keeps tables aligned. Neither restores headings.
- **DOCX:** mammoth maps Word styles to HTML, and `htmlToText` keeps one line per block and one line per table row. pandoc and markitdown produce Markdown with headings and tables, which reads better but costs size. docx2txt is plain text.
- **HTML:** `htmlToText` drops `script`, `style`, `noscript` and `template`, one line per block. Raw HTML is greppable already.
- **CSV:** `csvToText` writes every row as `header: value, …`, so a grep hit names its columns. A raw CSV is greppable too, but a matched row shows only values; the header is line 1.

## Scanned PDFs

- Neither pdf.js nor pdftotext does OCR. `extract.ts` throws `ExtractionFailure("no_text")` when no text comes out; pdftotext prints nothing but page breaks. ADR 0014 left OCR out on purpose.
- OCR would mean Tesseract (Apache-2.0): `tesseract-ocr` 5.3.0 is 2.1 MB installed, `tesseract-ocr-eng` another 4.0 MB, and it pulls in leptonica, ICU and pango. Pages must first be rendered to images (`pdftoppm` from poppler-utils), or wrapped with OCRmyPDF (MPL-2.0). It is slow per page and would hit the 60-second command limit on long scans. Raise it as an owner question if it's wanted; don't build it by default (map Notes: raise what grep can't handle as a question).

## Very large files

- Uploads are capped at 20 MB today (`maxKnowledgeFileBytes` in `packages/bot-sdk/plugins/assistant/shared/knowledge/kinds.ts`). DOCX archives are checked before inflating: at most 150 MB declared in total, 64 MB per entry, 10,000 entries (`ooxml.ts`).
- pdf.js loads the whole PDF in the server process and walks every page; there is no page or time limit in `extractKnowledgeText`. The only output ceiling today is the chunker's `maxChunks: 5000` (`process.ts`), which goes away with chunking. A Bot-side port needs its own ceiling on extracted text (for example characters out, or pages).
- On the Computer, the converted file's size doesn't matter to `grep`, and `read` pages through it 10,000 characters at a time. pdftotext can be bounded with `-f`/`-l` and the command timeout.

## Trade-offs of where to convert

- **At upload on the server (recommended).** No new dependency, no template change, the same result on every Computer, and failures (`encrypted`, `no_text`, `too_large`) show at upload, where the user can act. Costs: the server does the CPU work in-process, and the extractor has to move out of the assistant plugin with its pdf.js dependency (36.6 MB).
- **On the Computer with `poppler-utils`.** Lets a Bot convert PDFs it downloads itself, not just uploaded Knowledge, at about 6 MB and a template bump. Costs: GPL tools (run as separate programs, not linked), only PDF, and a Bot has to know to run it. It complements the server path rather than replacing it. Adding it is an owner decision (AGENTS.md §6).
- **On the Computer with pandoc or markitdown.** Best Markdown, but 170 MB (pandoc) or a Python virtualenv with a dozen packages (markitdown) in every Computer image. Not worth it for four formats the server already handles.
