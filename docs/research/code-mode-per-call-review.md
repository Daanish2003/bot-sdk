# Per-call review of tools inside TanStack code mode

Research for [#1401](https://github.com/Daanish2003/bot-sdk/issues/1401) (child of map [#1396](https://github.com/Daanish2003/bot-sdk/issues/1396)). Researched 2026-11-18.

## Question

How does `@tanstack/ai-code-mode` (with `@tanstack/ai-isolate-node` / `-quickjs`) expose a set of tools to model-written TypeScript, and can the host intercept **each** tool call made from inside the isolate? Covers schemas, a host hook per call (Auto-review and Approval), `needsApproval` / interrupts, isolate limits and where it runs, and maturity.

## Answer in short

- **Yes, the host sees and can hold every call.** Each `external_<name>(input)` in the isolate is a bridge back to the host process. It runs the tool's own `execute` on the host and the guest awaits the result. Nothing runs inside the isolate except the model's JavaScript. So a tool whose `execute` reviews first (the way the Bot SDK already wraps Connector tools in `liveRequest`) is reviewed on every call from a program. A block can be returned as a value or thrown. An Approval can hold the call by awaiting, and the guest program stays suspended at that `await` meanwhile.
- **TanStack's own `needsApproval` / interrupt does not work inside code mode.** In `ai-code-mode@1.0.0`, the version that matches our `@tanstack/ai@1.0.0`, a `needsApproval: true` tool passed to code mode **runs without approval**: the binding calls `execute` directly and never reads the flag. From 1.0.1 on, `createCodeMode` throws when given such a tool. The per-call review has to live in the tool's `execute` (or in an `@internal` hook), not in TanStack's approval.
- **The program timeout includes the wait.** The default is 30 s per `execute_typescript`, measured on the wall clock. One 15 s Approval wait (ADR 0024) uses half of it, and two use all of it. A refused call surfaces in the guest as a thrown `Error` (or as whatever value the tool returns), and the program can catch it and go on.
- **The isolate has no network, file system or process access**, apart from the tool bridge and `console`. Node and QuickJS drivers run in the host's own process. Running programs on the Bot's Computer is possible through a remote driver shape (TanStack ships one for E2B), with the tools still running on the host.

## 1. How tools become the API the model codes against

- `createCodeMode({ driver, tools, timeout?, memoryLimit?, ... })` returns **one** model-facing tool, `execute_typescript` with input `{ typescriptCode: string }`, plus a system prompt and, when some tools are `lazy`, a `discover_tools` tool (`create-code-mode.ts:90-107`; `create-code-mode-tool.ts:21-29,126-131`). The model never sees the inner tools as tool calls.
- Each tool becomes a binding named `external_<name>` (`create-code-mode-tool.ts:113`; `bindings/tool-to-binding.ts:392-404`). Only **server tools with an `execute`** are accepted. A tool without one throws (`tool-to-binding.ts:427-432`; `types.ts:170`).
- **Schemas → TypeScript.** Input and output schemas (Zod or Standard Schema) are converted to JSON Schema (`tool-to-binding.ts:418-425`). Then `generateTypeStubs` writes `interface External_xInput {...}` and `declare function external_x(input: External_xInput): Promise<External_xOutput>` into the system prompt (`type-generator/json-schema-to-ts.ts:22-69`; `create-system-prompt.ts:36-37,79-83`).
  - **Output schema matters.** Without one, the return type is `Promise<unknown>` (`json-schema-to-ts.ts:45-56`), so the model codes blind against the result's shape.
  - **The supported JSON Schema subset is small:** `const`, `enum`, `string`, `number`/`integer`, `boolean`, `null`, `array` with `items`, `object` with `properties`/`required`, `anyOf`/`oneOf`, and type arrays. Anything else, including `$ref`, `allOf`, `additionalProperties` and `patternProperties`, falls back to `unknown` (`json-schema-to-ts.ts:114-201`). Property `description`s become JSDoc (`:166-170`).
- **Validation.** Input and output are validated only when the schema is a Standard Schema (Zod etc.): `tool-to-binding.ts:437-447` (input) and `:451-461` (output). A plain JSON Schema object, which is what MCP tools carry, is **not validated** by code mode. The MCP server is left to reject bad input.
- **MCP tools.** `@tanstack/ai-mcp@1.0.0`'s `toServerTools` turns each listed MCP tool into a server tool. It takes the server's `inputSchema` (it fills in `type: 'object'` and `properties: {}` when they are missing) and its `outputSchema` when declared, and its `execute` proxies `tools/call` (`ai-mcp/src/tools.ts:642-680`). When the tool declares an `outputSchema`, `execute` returns `structuredContent`. Otherwise it returns the converted `content` blocks (`tools.ts:619-622`). So an MCP tool **fits code mode well only if its server publishes an `outputSchema` and returns `structuredContent`**, with plain schemas that avoid `$ref` and `allOf`. Otherwise the model sees `unknown` and parses text. `ai-mcp` also has a per-server `codeMode: true` flag. It only marks the tools with `metadata.codeMode` for the harness plugin (`ai-mcp/src/harness-plugin.ts:40-45,747-752`).
- **Names.** `createCodeMode` uses the name as given. The harness plugin sanitises it to a JS identifier, because MCP names often contain `-` (`harness.ts:97-100`). Without the harness, we would have to rename tools ourselves (inference from the generated `async function ${name}` in the drivers, `ai-isolate-node/src/isolate-driver.ts:216-217`).
- **Secret-looking parameters** in tool schemas produce a warning, configurable with `onSecretParameter` (`create-code-mode-tool.ts:119-123`; `types.ts:213-225`).

## 2. Does each call pass a host hook before it runs?

**Yes, by construction.** In both drivers:

- **Node (`isolated-vm`).** Each binding is an `ivm.Reference` to a host async function that calls `binding.execute(args)` (`ai-isolate-node/src/isolate-driver.ts:194-209`). The guest wrapper calls it with `applySyncPromise` and throws `new Error(result.error)` when the host reports failure (`:216-228`).
- **QuickJS.** Each binding is a host function that returns a QuickJS promise. The host runs `binding.execute(args)` and resolves the promise with a `{ success, value | error }` envelope (`ai-isolate-quickjs/src/isolate-driver.ts:57-69,87-133`). The guest wrapper throws on `success: false` (`:141-150`).

The chain on the host side for one `external_x(args)`:

1. `createEventAwareBindings` wrapper (`tool-to-binding.ts:490-550`). It emits the custom event `code_mode:external_call` with `{ function, args }` (`:514-518`) and checks the run's `abortSignal` (`:522`). Then it calls the optional **`aroundCalls` hook** as `hook({ name, args }, run)` (`:523-526`), and finally emits `code_mode:external_result` or `code_mode:external_error` (`:529-543`).
2. `toolToBinding`'s `execute`: validation, then **`tool.execute(input, context)`** (`tool-to-binding.ts:435-464`).

So there are three seams, each before the tool does anything:

| Seam                                                                             | Public?                                                                     | What it gets                                                                                                                                                 | Notes                                                                                                                                                            |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The tool's own `execute` (wrap it before passing the tool in)                    | Yes                                                                         | `args` and a context `{ context, abortSignal, threadId, emitCustomEvent }`                                                                                   | **No `toolCallId`**: the nested call gets the parent's `abortSignal`, `threadId` and `context`, but not its `toolCallId` (`tool-to-binding.ts:479-482,496-501`). |
| `aroundCalls(context, programEndSignal) => (call, run) => …` on `createCodeMode` | Typed in the config but marked **`@internal`** (`types.ts:148-157,284-299`) | The `execute_typescript` call's context (with its `toolCallId`), and a signal that aborts when the program ends (`create-code-mode-tool.ts:198,251,346-348`) | It can refuse (throw), hold (await) or run (`run()`). The harness plugin is its only first-party user. Being `@internal`, it can change without a major version. |
| `code_mode:external_call` custom event                                           | Yes                                                                         | `function`, `args`                                                                                                                                           | Observation only. It cannot block.                                                                                                                               |

`chat()` middleware tool hooks do **not** see these calls: the binding calls `tool.execute` directly, not through `chat()`'s tool execution (`tool-to-binding.ts:449`). The only tool call `chat()` sees is `execute_typescript`.

### What the running script does while a call waits or is refused

- **Waiting.** The guest is suspended at `await external_x(...)` until the host promise settles.
  - QuickJS: other guest promises can keep running in the meantime, so `Promise.all` calls run concurrently on the host (`ai-isolate-quickjs/src/isolate-driver.ts:87-133`).
  - Node: `applySyncPromise` makes "the invoking isolate … wait for that promise to resolve before resuming execution", and it "will not respond to any async functions until this promise is resolved" (`isolated-vm` README, lines 520-526). **Inference, not tested:** a `Promise.all` over several `external_*` calls therefore runs them one after another on Node, and one held Approval stalls the whole program.
- **Refused.** Whatever the host throws becomes `throw new Error(message)` in the guest (Node `isolate-driver.ts:203-206,222-225`; QuickJS `:61-68,145-147`). The program can `try/catch` it and go on. Uncaught, it ends the program, and `execute_typescript` returns `{ success: false, error }` to the model (`create-code-mode-tool.ts:317-332`). A tool can also _return_ a refusal value instead of throwing, and the program then receives that as the result. That is how the Bot SDK's `liveRequest` reports a block or a pending Approval (`packages/botsdk/bot/src/bot/agent-loop/loop.ts:118-122,756-760`).
- **Timeout while waiting.** The timeout is wall-clock per execution and **counts the time spent waiting on host calls**.
  - QuickJS: `deadline = Date.now() + timeout` is raced against the guest promise (`ai-isolate-quickjs/src/isolate-context.ts:40-80,218`). On timeout, each pending guest call is settled with an `Execution timed out` envelope (`isolate-driver.ts:91-106`). The **host-side `execute` is not cancelled** and keeps running (`:108`).
  - Node: `script.run(context, { timeout, promise: true })` (`ai-isolate-node/src/isolate-context.ts:285-288`). The TanStack docs call it the "longest wall-clock time for one execution" (`code-mode-isolates.md:93`). Whether `isolated-vm`'s timeout counts time blocked in `applySyncPromise` is **unverified** in `isolated-vm`'s own source.
  - The harness raises the default to 10 minutes when a program may wait for the user "because the wait for the user counts" (`harness.ts:34-38,86-90,450-451`; `docs/harness/code-mode.md:205`).
  - After the program ends, `programEnd` aborts (`create-code-mode-tool.ts:346-348`). Only the `aroundCalls` hook gets that signal. A tool's own `execute` gets only the run's `abortSignal`.
- **Stop.** In 1.0.0, a run abort is checked only before each call (`tool-to-binding.ts:522`). From 1.1.0, an abort of the run also aborts `programEnd` and disposes the isolate (`ai-code-mode@1.1.1 src/create-code-mode-tool.ts:219-247`; `docs/code-mode/code-mode.md:144`).

## 3. `needsApproval` and interrupts inside code mode

- **1.0.0: ignored.** Nothing in `createCodeModeTool`, `toolToBinding` or `createEventAwareBindings` reads `needsApproval`. The binding calls `execute` directly (`tool-to-binding.ts:413-473`), so an approval-gated tool **runs unattended** from a program.
- **1.0.1 and later: rejected.** `createCodeModeTool` throws "Code Mode cannot expose tools that require approval" (`ai-code-mode@1.0.1 src/create-code-mode-tool.ts:113-130`). 1.1.1 adds the same check in `toolToBinding` (`ai-code-mode@1.1.1 src/bindings/tool-to-binding.ts:40-51`). The docs say: "Code Mode rejects tools that need approval … An approval tool belongs outside the Code Mode config" (`docs/code-mode/code-mode.md:128-130`). An interrupt cannot be raised from inside the isolate, because only `execute_typescript` is a tool call that `chat()` can pause.
- **The harness's own per-call approval (`@tanstack/ai-code-mode/harness`, `codeMode()` plugin).**
  - By default it moves only "safe" tools into code mode: no `needsApproval`, no permission resources, and allowed in plan mode (`harness.ts:402-409`). `include` can add tools that have `permissions()` rules, but never a `needsApproval` tool (`:415-430`).
  - For those "guarded" tools, `aroundCalls` runs `guardCalls` (`:460-468`). Each call gets the permission decision of a direct call: deny makes the guest throw, allow runs it, and ask opens a durable question wait (`step.ask({ name: 'approve:<n>:<argsHash>' })`) that `session.answer` resolves (`:220-241`; `docs/harness/code-mode.md:170`).
  - A late answer never runs a call after the program ended (`:246-251`). Each finished call is kept in a durable step (`step.do('call:<n>:<name>')`) so a replay doesn't repeat it, and a changed argument hash refuses the replay (`:252-277`). A tool-mode agent that can only ask by ending its turn fails closed (`:156-169`).
  - This is the pattern we would need, but it depends on `@tanstack/ai-harness` (a new dependency, not installed) and on the harness's session, step and permission model, not our Turn loop.

## 4. Isolate limits and where it runs

|                        | Node (`isolated-vm`)                                                                                                                                                                                                                          | QuickJS (WASM)                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Timeout                | 30 s default, wall-clock, one per `execute_typescript` (`create-code-mode-tool.ts:96`; driver `isolate-context.ts:285-288`)                                                                                                                   | 30 s default, wall-clock deadline plus an interrupt handler for busy loops (`isolate-driver.ts:197,281`; `isolate-context.ts:218`) |
| Memory                 | 128 MB default, `new ivm.Isolate({ memoryLimit })` (`isolate-driver.ts:134,143`)                                                                                                                                                              | 128 MB heap and 512 KB stack (`isolate-driver.ts:18-21,228-229`)                                                                   |
| Globals                | `global`, `console` (captured into logs) and the bindings only (`isolate-driver.ts:149-229`)                                                                                                                                                  | `console` and the bindings only (`isolate-driver.ts:231-279`)                                                                      |
| Network / FS / process | None, apart from the bindings. Docs: "no access to the host file system, network, or process" (`docs/code-mode/code-mode.md:126`); prompt: "no network access or file system" (`create-system-prompt.ts:107`)                                 | Same                                                                                                                               |
| Where it runs          | In the host Node process: a V8 isolate in a native addon. Needs Node 22+ (`docs/code-mode/code-mode.md:39`). It runs a subprocess probe at startup because a mismatched addon build segfaults the process (`isolate-driver.ts:36-75,119-132`) | In the host process, as WASM. No native dependency                                                                                 |
| Per-call caps          | None in 1.0.0. A `maxToolCalls` cap exists on the QuickJS Bun driver per the latest docs (`code-mode-isolates.md:50`)                                                                                                                         | None in 1.0.0                                                                                                                      |

Every execution gets a fresh context, and the context is disposed afterwards (`create-code-mode-tool.ts:195-196,349-352`). Results cross the boundary as JSON (`code-wrapper.ts`), so functions, `bigint`s and class instances don't survive.

**On the Bot's Computer?** Not with these two drivers: they run in the process that calls `createCodeMode`, which for us is the Turn's worker. But `IsolateDriver` is a small public interface (`createContext(config) → { execute(code), dispose() }`, `types.ts:18-58`), and the drivers only have to call `bindings[name].execute(args)` back on the host. TanStack ships remote drivers that keep the tools on the server: Cloudflare and Daytona replay the code with a request/response loop, and **E2B** keeps one `node` process alive and passes tool calls over stdout/stdin (`docs/code-mode/code-mode-isolates.md:239,280,340-372`). Our Computer runs on E2B (`packages/botsdk/computer-e2b`), so `@tanstack/ai-isolate-e2b` (1.0.0 needs `ai-code-mode ^1.0.0`), or a driver of our own on the Computer handle, could run programs there with each call still reviewed on the host. **Unverified:** the E2B driver's source was not read, only its docs, and the cost of waking the Computer for every program was not measured.

## 5. Maturity

- `ai-code-mode` has had 11 releases in about 5 weeks: 0.4.21 (2026-10-06) through 0.5.x, 1.0.0 (2026-10-22), 1.0.1 (10-29), 1.1.0 (11-04) and 1.1.1 (11-09). The isolate drivers follow in lockstep (1.0.0, then 1.1.0 on 11-04) (npm `time`). Each minor version raises the `@tanstack/ai` peer, so staying on `ai@1.0.0` pins us to `ai-code-mode@1.0.0`, the one version that runs `needsApproval` tools unattended and has no run-abort handling.
- The behaviour this question depends on changed within the 1.0 line: approval tools went from running silently (1.0.0) to being rejected (1.0.1), abort handling came in 1.1.0, and `aroundCalls` is `@internal`.
- GitHub issues (TanStack/ai, searched 2026-11-18). No open issue about code mode or the isolates. Closed ones on these points:
  - [#793](https://github.com/TanStack/ai/issues/793): code-mode tools didn't validate schemas.
  - [#947](https://github.com/TanStack/ai/issues/947): two sequential QuickJS tool calls crashed the WASM module.
  - [#1446](https://github.com/TanStack/ai/issues/1446): the model called `discover_tools` inside the sandbox.
  - [#1599](https://github.com/TanStack/ai/issues/1599): type stubs dropped `enum`, `const` and descriptions.
  - [#1854](https://github.com/TanStack/ai/issues/1854): `needsApproval` tools ran unattended through the sandbox tool bridge, the same class of bug in `ai-sandbox`.
- Open approval issues outside code mode: [#1924](https://github.com/TanStack/ai/issues/1924) (MCP `needsApproval` interrupts render as generic), [#2073](https://github.com/TanStack/ai/issues/2073) and [#1740](https://github.com/TanStack/ai/issues/1740).

## What it means for the Bot SDK (inference, not tested)

- **Our Connector tools already have the right seam.** `features.ts` strips `needsApproval` and wraps each Connector tool's `execute` in `liveRequest(name, options?.toolCallId, run, write, reviewed)`, which runs Auto-review first and returns a block or a pending result as the call's value (`packages/botsdk/bot/src/bot/context/features.ts:217-236`; `loop.ts:756-776`). Passing those wrapped tools to code mode would review each call from a program with no TanStack approval involved, and `ai-code-mode` 1.0.1+ would not reject them, since `needsApproval` is gone.
- **The gap is `toolCallId`.** Nested calls get no `toolCallId` (`tool-to-binding.ts:496-501`). In `liveRequest`, a call without one is treated as "setup's read": its result is **not masked of Secrets and not cut** (`loop.ts:115-117,764-765,718-719`), and its review output is not kept (`keepOutput`, `loop.ts:735-736`). Each nested call would need its own id, for example `<execute_typescript toolCallId>:<n>:<argsHash>` the way the harness builds names (`harness.ts:210-233,270`). That needs `aroundCalls` (`@internal`) or our own wrapper that reads the parent id from somewhere else. **Unverified:** whether repeated `ctx.step(name)` calls with the same tool name inside one program collide on replay.
- **The time limits don't line up.** The default timeout is 30 s, a blocked call waits 15 s before going pending (ADR 0024/0030), and the host-side call continues after a QuickJS timeout. The program timeout must cover the review plus the 15 s wait for every reviewed call a program can make. On Node, a held call also stalls the whole program. After the wait, the program gets ADR 0030's "waits for the user's Approval" result as a value and carries on; a late yes runs the stored call outside the program, and its result arrives as a Trigger, never back in the program.
- **Auto-review sees less context.** The reviewer would see each call's `args` but not the program that made it, unless we pass the `execute_typescript` input along (it reaches `aroundCalls` only through `context`, and the input itself is not in `ToolExecutionContext`; **unverified** how we'd thread it).
