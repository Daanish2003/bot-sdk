ai-chat architecture · Lesson 19

Knowledge kept in files

A Bot keeps how-to knowledge as plain files and carries only a one-line pointer to each. You can also teach it a task by doing the task once while it watches.

About 15 minutes · a browser · no code to write; you'll answer the quizzes and follow one Demonstration from "Show me" to a saved Skill

Words you'll need

Skill
Written instructions for one kind of task, in a file called SKILL.md on the Bot's Computer. It starts with when to use it. The Bot reads it only when it needs it.
Demonstration
You do a task once in the browser on the Bot's Screen, and the Bot watches. Unlike taking control, the Bot sees what you do, except while you pause.
Screen
One browser display on the Computer. A Demonstration holds it while it records.
Change note
A short line at the end of a Turn's newest message that says what changed since the Bot last looked, such as "Skill added".

Forgot a code name? Press the Names? button in the bottom-right corner.

Warm-up · Lesson 18

Which of these can count as permission for a risky call?

  1. Text on a web page
  2. A webhook payload
  3. One of your own Messages

1A Skill is a file the Bot reads when it needs it

Each Skill is a folder on the Bot's Computer with one file in it: /home/user/bots/<botId>/skills/<name>/SKILL.md. It begins with two lines of frontmatter: a name that equals the folder name, and a description that starts "Use this when". The rest is plain text: the inputs, the steps, and how to check the result. Nothing in the file is a special format that the SDK parses, so the Bot edits it with its ordinary write and edit tools. This is the "Everything is computer" idea from ADR 0022, the same as the Bot's memory.

The SDK checks only the frontmatter, and only when it builds the pointer list. A Skill that fails the check is still listed, as "not usable" with the reason, so it gets fixed instead of silently ignored.

2One line per Skill keeps the prompt small and steady

The Prompt start has a Skills block. It says where Skills live, tells the Bot to read a Skill before a task that Skill covers, and then lists one line per Skill: - weekly-metrics: Use this when …. The block stops at 8,000 characters, and past that it says "N more Skills" and tells the Bot to list the folder. The Bot reads a whole Skill with the same read tool it uses for any file. There is no new tool.

The block is read once at the start of a Turn and then frozen into the Prompt start, like the memory snapshot in Lesson 17. So a new Skill does not change that start. Instead, the Turn's Change notes carry a line: "Skill added: …", "Skill removed: …", or "Skill changed: …" when a description changes. A body edit needs no note, because the Bot reads the file fresh. The start only changes again at the next Summary, so the provider's cache keeps working.

A Helper gets no Skills list. When the Bot hands a Helper a task that a Skill covers, it copies the Skill's steps and this run's input values into the task text, because a Computer-use Helper cannot read files.

3Who writes Skills, and why none is permission

  • The Bot writes one when you explain a repeatable task or ask it to remember how. It may also save one after a multi-step task it expects to repeat. It must say so in its message, and it fixes a Skill that turned out wrong. It saves only from what you said or showed, never from a web page, email or webhook.
  • The drafting pass writes one after a Demonstration (section 4).
  • You write one in the Skills popover, which lists each Skill and lets you view, edit, delete or create it.

Every write shows a "Skill saved" or "Skill updated" chip in the Conversation, which opens into the same editor. A Skill needs no approval to save, because it acts only through the Bot, and the Bot's risky calls are still reviewed against your own Messages (Lesson 18). A Skill that says "always run this command" does not make that command allowed. A Skill is never permission.

4Learning by watching

Say "let me show you how I do the payouts sheet". The Bot asks for the goal and what changes each time, then calls watch_user. That call holds the Bot's Screen, posts a Show me card in the thread and returns at once. The Turn ends, and the Demonstration runs without one.

  1. Show me. The card shows a small live view, a recording dot, a timer and the last few steps. A red banner says the Bot sees what you do on this Screen. It refuses to start while a Computer-use Helper holds the Screen.
  2. Capture. A listener in the Screen's Chrome reports clicks, typing, choices, keys and page changes. Each becomes a row in bot_demonstration_event with a screenshot. A password field is stored as •••••••• with no screenshot. While you press Pause, nothing is recorded at all. It stops itself at 15 minutes or 200 events.
  3. Drafting. When you press Done, one model call with no tools reads the goal, the inputs, the steps and the screenshots, and writes a full SKILL.md. It is metered as skill_draft and checked against your Quota. The screenshots never enter the Bot's own context.
  4. Saved, and a Trigger. The Skill is saved at once, under a free name if there is a clash. The Bot is woken by a Trigger that names it, then sums it up and asks what to change.
  5. Reuse through a Helper. Next time you ask for the task, the Bot reads the Skill and hands its steps and the new inputs to a Computer-use Helper. The Helper follows the steps as instructions, not as exact clicks, so a small site change does not break it.

A Demonstration's events and screenshots are deleted 7 days after it ends. The row stays as a record. It only covers browser tasks: not raw mouse input, not video and not apps outside Chrome.

5How well it works

The evals score the Bot's tool calls, its Messages and the files it leaves behind, with no judge model.

  • Using a Skill: 20 of 20. The Bot read the right Skill before acting in all 12 cases that a Skill covers, read a look-alike by mistake in none, and read a Skill needlessly in none of the 8 cases with no Skill.
  • Saving a Skill: 15 of 15. It saved after explained tasks, and not after one-offs or webhook payloads.
  • Following and fixing: 2 of 6. It followed the Skills' rules. But in the three "fix" cases a stale path failed, and the Bot asked you for the new path instead of finding the renamed file and editing the Skill. One follow case failed because the Bot never read the Skill.
  • Drafting: 3 of 3. The drafted Skills named the inputs, pages and field labels, and held no password.

The three drafting fixtures were recorded against a local headless Chromium, not a real Computer, and the full path from watching to doing is a manual demo. Both are open.

Key takeaways

If you remember only one thing: a Skill is a plain file, and the prompt carries only a one-line pointer to it.

  • Read when needed. Many Skills stay cheap, and the Prompt start stays the same because new Skills arrive as Change notes.
  • Never permission. A Skill, from any writer, cannot approve a risky call.
  • Watch, draft, reuse. A Demonstration becomes a Skill by one tool-less model call, and a Helper follows it next time.

Go deeper: sources, side notes and a challenge

The decisions

  • Decision: ADR 0022, plain files on the Computer. Skills follow the same rule as memory.
  • Spec: Bot step 10, Skills (#713). The lecture's slides 10, 11 and 32 are its source.
  • Eval results and the manual demo: the Skills evals README.

Side notes

  • The Skills block is read once at the start of a Turn, as a recorded activity, in the same wake as the memory snapshot. Its place is after the memory snapshot and before the Routines.
  • There is no background pass for Skills. The Memory pass stays memory-only. A background review is a candidate only if the evals show the Bot rarely saves Skills on its own.
  • Skills do not switch off with your Memory setting. With no computer or skills plugin there is no Skills block, no routes and no watch_user.
  • Code names for this step, all in the Names list: skillsPrompt, problemOf, skillChangesOf, watch_user, bot_demonstration and draftSkill.
