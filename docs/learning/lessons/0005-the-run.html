The Run and its log

A Run records every chunk on a tape, and every reader plays that tape.

About 14 minutes · a browser · you'll write replay(log, offset) and statusAtEnd(run)

Words you'll need

Chunk
One event that TanStack AI's chat() streams out, for example a piece of reply text (TEXT_MESSAGE_CONTENT) or the end (RUN_FINISHED).
Run log
The list of every chunk of one Run, in order. Readers can only add to its end or read it.
Offset
The position of one chunk in the run log. A reader asks for "every chunk after offset n".
Snapshot
The Run's write of the reply's parts so far into Postgres, once a second.

1One stream, three jobs

Think of a live radio show that is also recorded on tape. The speaker is chat(). The tape is the run log. Listeners never hear the speaker directly: they play the tape, so a late listener can start from the beginning.

startRun does three jobs with one stream. It reads each chunk in a for await loop and appends it to the log. It adds the chunk to a parts builder, which a timer copies to Postgres. When the stream ends, its finally block decides the final status.

The loop runs on its own: startRun doesn't wait for it, and no reader can stop it by going away (ADR 0002). Tools, compaction and the Quota meter also plug in here; they get their own lessons.

2The log and its readers

RunStreams has four methods: open, append, close and read(runId, offset). A read gives the entries after the offset, then waits for new ones until the log closes. START is "-1", so it reads from the first entry.

Look at the last line of handleChat: the POST response is TanStack's resumeServerSentEventsResponse over runStreamDurability(deps.runStreams, assistantMessageId, START). So the person who sent the Message is just the first reader of the tape. A reloaded page reads it the same way (Lesson 6).

3The snapshot tick

Postgres is still the record of history, so the reply must reach it while it streams. A setInterval fires every snapshotIntervalMs (1,000 ms in deps.ts):

  1. It always writes heartbeatAt: new Date(). That is the Run's lease (Lesson 6).
  2. If changed is true, it also writes the parts and their search text, then sets changed = false.
  3. It reads whether a Stop was asked for, in case the Stop signal was missed.

All writes go through one promise chain, so they reach the row in order. A snapshot uses update … where id = messageId; it never inserts.

4The end decides the status

The finally block runs however the loop ended. It asks its questions in a fixed order, because one cause can look like another: the 5-minute cap and a shutdown both abort the same AbortController that Stop uses.

  1. Cap hit (timedOut) → error, "timed_out".
  2. Abort reason is shutdownAbort → error, "interrupted".
  3. Any other abort (Stop) → stopped.
  4. A RUN_ERROR chunk or a throw → error.
  5. A tool call waits for Approval → awaiting_approval, else complete.

Then it saves the ending with whileStreaming, so a row that another process already ended stays as it is. If the log has no end chunk of its own, it appends one, then closes the log. Last, it fires the onRunEnd hook and starts the title.

Key takeaways

If you remember only one thing: the Run writes every chunk to its log before anyone reads it, and every reader, the POST response too, plays the log.

  • The tape, not the speaker. Readers read RunStreams from an offset; START ("-1") means from the first chunk.
  • A tick a second. The timer always writes the heartbeat, and writes the parts only when they changed.
  • Order decides the ending. Timed out, interrupted, stopped, error, awaiting Approval, complete: the first true check wins.

Go deeper: sources, side notes and a challenge

The decision

"The Run appends every chunk to its log before anyone reads it, and the POST response and any later reader both read the log." (ADR 0006)

ADR 0006 rejected "POST reads a local channel, only joiners read the log": it saves about 50 ms of latency but makes two read paths to keep correct.

Side notes

  • Appends are batched: the memory log flushes about every 50 ms (FLUSH_MS), and Redis writes each batch in one MULTI. A closed log stays readable for an hour (CLOSED_LOG_TTL_MS).
  • runStreamDurability adapts our log to TanStack AI's StreamDurability, but only its read works. Its append throws, because the Run appends through RunStreams.append.
  • A stopped or timed-out Run has no RUN_FINISHED of its own. Without the explicit ending chunk, a reader would take the stream as cut off and reconnect.
  • untilAborted stops reading the stream when the signal aborts, even if an adapter ignores the signal (issue #54).
  • A Message can have more than one Run: after an Approval, the next Run's log id is <messageId>:2 (runLogId, ADR 0008).
  • The real readLog throws on an offset that isn't a number, such as "abc"; your exercise can skip that case.
