Runs outlive the client

A Run belongs to the server, not to the browser tab, so four mechanisms keep it safe.

About 13 minutes · a browser · you'll write reap(messages, now, lease), the query the reaper runs

Words you'll need

Join
Read a live Run's log from a point and then follow it until it closes.
PubSub
A signal between processes. It reaches only the listeners present now, at most once.
Lease
The Run's proof that its owner is alive: heartbeat_at, written every second.
Reaper
A timer in every process that ends Runs whose lease has run out.

1Join: a broadcast with a recording

Think of a radio station that records every show. It broadcasts whether anyone listens, and a late listener can play the recording from the start and then hear the live show. The Run is the show, and its log (Lesson 5) is the recording.

  1. The page loads the Active Branch and finds a Message with status streaming. chat-view.tsx takes its id as the Run's id.
  2. useChat sends GET /api/chat/run?runId=…. handleJoin checks that the user owns the Conversation, else 404.
  3. It replays the log from the start (or from Last-Event-ID on a reconnect), then follows it until the log closes.

2Stop: a signal and a note

Stop is an RPC, chat.stop, and it can land on any process. stopRun does two things: it writes cancel_requested_at on the Message, and it publishes "stop" on the PubSub channel run:<id>:cancel. It never writes status, because only the owner process knows how the Run ended.

The signal is at most once, so it can miss. That is why the owner also reads the column on each one-second tick (stopRequested). Either way the owner aborts and saves stopped. If the lease has already run out, no owner is left, so stopRun saves stopped itself.

Quiz

The Stop signal is lost on its way to the owner process. What happens to the Run?

  1. It keeps going until the five-minute cap.
  2. It stops within about one more second.
  3. stopRun saves it stopped right away.
  4. The reaper ends it after thirty seconds.

3The lease and the reaper

If a process crashes, nobody saves its Run, and the Message says streaming for ever. So the owner writes heartbeat_at on every snapshot tick (1 s), even when no text changed. Every process runs the reaper in start() and then every 30 s (lifecycle.ts).

The rule: a streaming Message whose heartbeat_at is empty or older than now − lease ends as error "interrupted". With Process B's Run in the picture:

  1. The last heartbeat is at 40 s, and the lease is 30 s.
  2. At 65 s: 65 − 30 = 35, and 40 is not older than 35, so it stays.
  3. At 75 s: 75 − 30 = 45, and 40 is older than 45, so it is reaped.

reapStaleRuns also marks running tool calls cancelled and ends the log, so a joined tab doesn't reconnect into a Run that is gone.

4Shutdown, and what needs Redis

runtime.ts has the two runtimes. apps/web picks redisRuntime when REDIS_URL is set.

A deploy calls chat.stop(). It answers new Runs with 503, lets local Runs finish for up to 250 s (the drain), then aborts the rest. They save themselves as error "interrupted" and close their logs.

Key takeaways

If you remember only one thing: the owner process alone saves how its Run ended; everyone else leaves a note, sends a signal, or waits for the lease to run out.

  • Join reads the recording. A reloaded tab finds the streaming Message and reads its log from the start.
  • Stop is a note plus a signal. cancel_requested_at catches what the at-most-once PubSub misses.
  • The lease replaces trust. No heartbeat for 30 s means the owner is gone, and the reaper ends the Run as "interrupted".

Go deeper: sources, side notes and a challenge

The decisions

"A Run outlives the client and Stop is an explicit call. But its registry, boot sweep and polling only work in one process, and the Chat SDK runs in several." (ADR 0006, which amends ADR 0002)

Side notes

  • The owner's last write uses whileStreaming: true: it updates the row only while it is still streaming. So a Run that another process already saved stopped is never written over. (The first course noted this race; the code now guards it.)
  • A Message can have several Runs (ADR 0008). The second Run's log id is <messageId>:2 (runLogId), and a join reads message.run_number to find the newest log.
  • Stop on a Message that waits for Approval counts as a denial (routers/chat.ts).
  • Defaults live in defaultLimits in deps.ts: snapshot 1 s, lease 30 s, reaper 30 s, drain 250 s, Run cap 5 minutes. Tests pass smaller ones.
  • The same reaper tick also reaps background jobs and, once an hour, deletes expired Temporary Conversations.

Challenge

With a 30 s lease and a reaper every 30 s, what is the longest time a crashed Run can still show streaming? Work it out, then tell your teacher.
