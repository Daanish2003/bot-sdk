Words you'll need

Handler
One function from a Request to a Response. The Host mounts it on one catch-all route.
BotSdkContext
The bundle of everything the server code uses: the database, the blob store, the runtime, the hooks, the keyring.
Lifecycle
The three calls around the handler: migrate() at deploy, start() at boot, stop() at shutdown.

1One call, everything back

Think of createBotSdk as a shop fitted into a building that the Host owns. The Host gives the address (databaseUrl), the doorman who knows the visitors (getUser), the keys to the safe (keyEncryptionSecrets) and the door the shop sits behind (basePath). Every other option is optional.

Look at apps/web's call in services.ts: its getUser asks Better Auth for the session and returns only { id }. That id is all the SDK ever knows about a user.

2Nothing connects until the first request

In create-chat.ts, createBotSdk checks the options and the plugins and builds the BotSdkContext, but the database pool connects on first use. So the Host can build the Bot SDK at import time, and no connection opens in a build step.

The context is also the test seam. The tests build a fake one with createTestSdk() (test/support/deps.ts): the test database and fakes, so nothing reaches the network. They turn it into a handler with createChatHandler(sdk, …) in over.ts.

3One handler, one ladder

The Host mounts one route, /api/chat/$, for every method. The handler then reads the path and goes down the ladder from the top; the first rung that matches answers:

  1. A Generated image on a Shared link (GET /shared/<token>/generated-images/<id>) answers before anyone asks who you are. The token is the only key.
  2. getUser(request). With no user, everything gets 401 except the two public RPCs, share/get and share/artifactVersion.
  3. /rpc/… goes to oRPC. /run is POST → handleChat and GET → handleJoin.
  4. Then GET only: /events, /export, /generated-images/… and the MCP connect/callback. Anything else is 404.

4Deploy, boot, shut down

  1. Deploy: migrate() creates the chat schema and applies the bundled migrations. apps/web runs it from scripts/migrate.ts (pnpm db:migrate).
  2. Boot: start() throws if byok is false with no hostProviders, if a default Model isn't one of the Host's Models, or if the schema is behind the migrations. Then it starts the reaper (now, then every 30 s) and the job runner.
  3. Shutdown: stop() answers new Runs with 503, gives local Runs up to 250 s to finish, ends the rest as interrupted, and closes the connections.

apps/web calls start() and stop() from one Nitro plugin, chat-lifecycle.ts: start() when the server boots, stop() on SIGTERM.

Key takeaways

If you remember only one thing: createBotSdk returns one handler and three lifecycle calls, and it opens no connection until first use.

  • The Host gives four things. databaseUrl, getUser, keyEncryptionSecrets, basePath; the user is only an id.
  • One ladder. Shared image, then getUser (401), then /rpc, /run, the GET routes, then 404.
  • Three moments. migrate() at deploy, start() at boot (it can refuse), stop() on SIGTERM (503 and drain).

Self-test: cover this box, then say which rung answers GET /api/chat/run?runId=… for a signed-in user.

Go deeper: sources, side notes and a challenge

The README's lifecycle

"server: construct at module load (no side effects) … one catch-all route on your framework, for every chat call and the Shared link read … deploy step, once per deploy … boot and shutdown" (Bot SDK README, "Host lifecycle")

Side notes

  • services.ts keeps the Bot SDK on globalThis.botSdk. The Nitro plugin is bundled apart from the routes and loads its own copy of the module, so without the shared slot there would be two Bot SDKs, and jobs run by the plugin's runner would publish on a pub/sub that the routes don't listen to (#290).
  • scripts/migrate.ts imports migrate from core/server/migrate.ts directly, not sdk.migrate(), because it also migrates Better Auth's tables first and drops the old public chat tables after.
  • createBotSdk and the plugin calls throw early for only a few things: an empty keyEncryptionSecrets, bad mcpServers, and a Host tool named like a built-in one (web_search, fetch_url, search_knowledge, and the Artifact tools when artifacts is on).
  • While stop() drains, sdk.lifecycle.stopping is true, and only POST /run checks it. Joins and RPCs still work, so a reader can watch a Run finish.
  • The returned object also has server-only calls with no route: deleteUser, exportUser, rotateKeys and plugin(id), which reaches a plugin's API (the assistant's runJob, the models' usage and quota reads). The Host decides who may call them.
