The Bot SDK, its core and its plugins

One core holds the shared base. Each feature is a plugin, a plain object that sits on it.

About 13 minutes · a browser · you'll write orderPlugins(plugins), the function that sorts plugins by what they require

1One core, rooms added by the Host

Think of the Bot SDK as a house. The core is the foundation: the database, the blob store, pub/sub, logging, and the Conversation with its Messages and attachments. Every Host gets it. The plugins are rooms the Host adds: models (keys, quota and usage), runner (durable jobs), bot (always-on Bots), computer, memory, knowledge, skills, channel and mcp.

A plugin calls another plugin only when it lists that plugin in requires, as bot lists models and runner. A softer link, uses, orders the plugins without forcing the other one on: bot uses computer, and asks sdk.hasPlugin("computer") before it touches it. The core imports plugin code in one place only, the schema module that composes the tables. Everywhere else it uses import type.

A Host copies the folder with pnpm -F @ai-chat/bot-sdk copy <dest>. Each copy replaces core/ and every plugin folder, but not a plugin's ui/. The root ui/ and extras/ are copied only when missing, and tests are never copied (scripts/copy.ts).

2A plugin is a plain object

A plugin is the BotSdkPlugin type in core/server/plugin.ts. The shape of bot, trimmed, looks like this: 

{
  id: "bot",
  requires: ["models", "runner"],
  uses: ["computer", "memory", "skills", "knowledge", "mcp"],
  router: botPluginRouter,
  init: (sdk) => { …; return { api }; },
  start: startRoutineReconcile,
  deleteUser: { before, after },
  databaseHooks: { conversation: { delete: screenshotsConversationDelete } },
}

Each hook gets a BotSdkContext: the database, the keyring, the event hooks, a guarded fetch and plugin(id). Reading sdk.plugin("models").quota(userId) is typed, because models adds its API to PluginApis by declaration merging. It throws when models is not enabled.

3One schema, composed from parts

A plugin's schema module is plain Drizzle. It exports its own tables and enums, plus, for each core table, the columns and indexes it adds. The Bot plugins add none to core tables: bot brings bot, bot_turn, bot_routine and more, and each row points at its Conversation or its user.

core/server/db/schema.ts joins the parts into one chat schema. A plugin that does need a column on conversation or message gives it under fields.conversation.columns, and the composed table spreads it in. If two parts declare the same table, enum, column or index, the module throws at load and names both. CI runs drizzle-kit generate and fails if the migrations folder changes.

4Every delete goes through one door

Every path that deletes Conversations calls deleteConversations before it removes any parent row. Today that is a user delete: the core's step and the bot plugin's part both use it. It selects the ids, runs each plugin's before in the transaction, deletes the rows, and then runs each after once the commit is done.

A before that throws rolls the delete back. An after that throws is logged, and the other hooks still run. The bot plugin's before collects the blob keys of its Helpers' screenshots, and its after deletes those bytes once the rows are gone.

Key takeaways

If you remember only one thing: the Bot SDK is one core, and every feature is a plugin on it. The shared paths take each plugin's part through one door.

  • The core is the foundation. Plugins call each other only through requires and plugin(id).
  • A plugin is a plain object. init, start and stop run in dependency order, and stop runs in reverse.
  • One door for each shared path. One composed schema, and one deleteConversations that every delete calls.

Go deeper: sources, side notes and a challenge

The decision

"Everything else is a plugin: models, runner, assistant (today's chat), bot (…), memory, knowledge, computer and channels. A plugin declares requires, and the core throws at startup when one is missing." (ADR 0020, amended for the field DSL.) Its plugin list is out of date: ADR 0027 drops assistant and adds mcp.

The ADR also says the core holds the Conversation, because it is to this SDK what user is to Better Auth. Plugin export paths end in /server, /client or /ui.

Side notes

  • Construction checks the plugins in orderPlugins. It throws on a duplicate id, a missing requirement or a cycle. mergeRouters throws when two plugins claim one router key.
  • start() checks that the schema is migrated before any plugin starts. stop() sets stopping, then stops the plugins in reverse, then closes the runtime.
  • deleteUser runs each plugin's before in reverse dependency order, then the core's own delete step. The export is a version 2 document: the core's version and exportedAt, and each exporting plugin's part under its plugin id.
  • Every Bot plugin has fields: {} by type. Giving one a column on conversation means spreading its fields in schema.ts, which is an edit to the core.
