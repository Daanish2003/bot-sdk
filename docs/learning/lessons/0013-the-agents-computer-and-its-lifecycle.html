The agent's computer and its lifecycle

Each user has one Computer. It wakes when a Bot uses it, and a check job puts it to sleep when it is idle, but never in the middle of a Turn.

About 14 minutes · a browser · you'll write nextCheck(...), the rule a sleep check follows each time it runs

Words you'll need

Sandbox
A small virtual machine that runs the Computer, kept apart from the server.
Pause
Freeze the sandbox with its memory and disk saved. Resume starts it again.
Sleep check
A job that decides whether to put the Computer to sleep, or to check again later.
Busy check
A question another plugin answers: "is something still using the Computer?"

1A sandbox that pauses

A Bot should run real commands, but not on the web server. So each user gets one sandbox: a Firecracker microVM on self-hosted E2B. It has its own kernel and its own disk, so a bad command can only hurt that one Computer. All of a user's Bots share it.

Pause saves the sandbox's memory and disk. A process started before the pause is still running after the resume, so sleep is invisible to the Bot. An idle sandbox resumed in about 110–150 ms when measured, so the Bot sees no "starting your computer…" notice. If a wake fails, the tool result says so.

2Operations, then tools

computer exposes operations, not tools. sdk.plugin("computer").forUser(userId) returns a handle with run, readFile, writeFile and list. Each operation wakes the Computer first, and records activity when it starts and when it ends.

bot builds its five tools (shell, read, write, edit, list) from those operations. Helpers and Skills will use the same handle later, so there is one Computer and one lifecycle. Without computer, sdk.hasPlugin("computer") is false, and a Turn has no Computer tools and no mention of them.

3Files live on the server

A snapshot can be lost, and a new template version replaces every sandbox. So the files do not live only in the sandbox ("the virtual machine can then always be rebuilt"). Before each pause, syncFiles lists the files in bots and shared, without .outputs/, and hashes the list. This hash is the fingerprint. If it matches sync_fingerprint, nothing changed and nothing uploads. If not, one tar archive goes to the blob store, up to 100 MB.

A wake rebuilds when the template name changed, or when the provider says the sandbox is gone. It creates a new sandbox, extracts the archive into /home/user, and tells the Bot once that installed programs may be missing. If the extract fails, the wake fails, so a failed restore never hands back an empty Computer. The archive is as fresh as the last good sync: if a sync failed or was over the cap, the rebuild restores an older one.

4Going to sleep, never mid-Turn

Every wake queues one computer.sleep job for 5 minutes later. The runner has no reschedule call, so the job chains: each run either puts the Computer to sleep, or queues the next check at max(lastActiveAt + 5 min, now + 1 min). A check sleeps the Computer only when it is idle (no operation for over 5 minutes) and every busy check says no. bot adds one: a running Turn of this user's Bots that started before last_active_at keeps the Computer awake.

The check holds the row lock on chat.computer from its idle test until it commits. An operation that arrives meanwhile waits at its start update, then sees asleep and wakes the Computer the normal way. A sync failure is logged and the pause goes ahead. A pause failure leaves the row awake and throws, so the runner retries, and onFailed arms a fresh check in 5 minutes.

Key takeaways

If you remember only one thing: the Computer is a sandbox that can always be rebuilt from the server's copy of its files, and it sleeps only when it is idle and nothing is using it.

  • Operations, not tools. The plugin wakes the Computer; bot only builds tools on top.
  • The server keeps the files. One archive per user, skipped when the fingerprint is unchanged, restored on a rebuild.
  • One chain, one lock. A check sleeps, ends, or arms the next one, and the row lock settles a race with a call, and the busy checks cover a running Turn.

Go deeper: sources, side notes and a challenge

The lecture and the decisions

  • Slide 15: the Computer "sleeps a few minutes after the last activity, never mid-turn", and because its files are kept on the server, "the virtual machine can then always be rebuilt". Slides 13, 16, 22, 28, 32 and 33 give the rest: the tools, long outputs going to files, and a tool set that never changes mid-conversation.
  • Spec: Bot step 5, The Computer (#519). Map: #416.
  • Decisions: the agent's computer (#396), the plugin and its seams (#506), Shell and Files tools (#507), putting the Computer to sleep (#508) and syncing and rebuilding (#509). The plugin model is ADR 0020; the runner is ADR 0011.

Side notes

  • The provider seam (provider.ts) is the only place that says "sandbox". It has two adapters: E2B (plugins/computer/e2b, its own subpath so other Hosts never load the e2b package) and a fake for tests, which needs no KVM.
  • A shell call is not re-run after a crash. A shell_start marker is saved first, and a resumed Turn that finds it with no result answers "interrupted by a restart" instead of running the command again. File tools are re-run safely.
  • Outputs over 10,000 characters go to .outputs/<toolCallId>.txt, and the result keeps the first and last 2,000 characters. The cap is applied before the Checkpoint is saved.
  • Two facts were checked on real E2B while building. Pause-on-timeout works on the self-hosted Embed, so the 1-hour backstop pauses a sandbox when the server is dead. The template's root disk is only about 800 MB, so the template stays small.
  • Deleting a user removes the chat.computer row in the delete's transaction, then kills the sandbox and deletes the archive, both best-effort. Deleting a Bot leaves its files.
  • Tests: test/plugins/computer/server/computer.integration.test.ts (the lifecycle, with a fake provider and the runner running due jobs) and test/core/server/routers/bot-computer.integration.test.ts (the tools in a Turn). The hand-run evals against real E2B are in eval/computer/.
