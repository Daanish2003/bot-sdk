handleChat: check, then write

Every check that can say no runs first. Then one locked transaction writes the Messages.

About 13 minutes · a browser · you'll write firstRefusal(state), the order of the gates in handleChat

Words you'll need

Refusal
An answer that says no: an HTTP status and a body { code, params }. It writes nothing.
Error code
A key such as error.replyStreaming. The client turns it into text in the user's language.
Transaction
A group of database writes that all happen, or none of them happen.
Row lock
SELECT … FOR UPDATE: a second transaction that asks for the same row waits until the first one ends.

1A ladder of gates

Think of boarding a plane. The airport checks your ticket, your passport and your bag at the gates, before you sit down. Nobody takes you off the plane later to check your ticket.

handleChat answers POST /api/chat/run the same way. It runs every check that can fail first: the rate limit, the command, the owner, the Model, the Quota, the parent, Approval and the Host's moderate hook. The code says it in one comment: "Everything that can fail runs before the Messages are written."

2A refusal is a status and a code

The server never sends a sentence. It sends a code, and errors.ts holds the English text for each code. A Host can give other text for the same codes, so the SDK works in any language.

On the client, runFetch in rate-limit.ts reads the body of a refused send. A 429 becomes a RateLimitedError with its Retry-After, a 422 from moderation becomes a ModeratedError, and any other { code } body becomes a RefusedError.

3Why the order matters

Cheap checks come first. The rate limit uses only a counter, so a flood of sends costs almost nothing. The Host's moderate hook comes after every validation, because there is no reason to ask the Host about a command that is already wrong.

Some steps can't be undone by "not writing". mcpToolsFor opens connections to MCP servers, so every refusal after it calls mcp?.close(). The adapter is built before the transaction too, so a Model whose adapter throws fails with nothing written; a test checks exactly that.

  4. An assistant Message ending error.

4One transaction, one lock

ADR 0002 allows one Run per Conversation. A plain check "is a Message streaming?" is not enough, because two sends can both check before either one writes. So the transaction first locks the Conversation row with .for("update"). Then it looks for a streaming Message, and finds one if an earlier send committed.

  1. Insert the user Message, unless this is a regenerate (no text).
  2. Insert the assistant Message with status streaming and parts [].
  3. Link the Attachments to the user Message.
  4. Set activeLeafId to the new reply, clear archivedAt, and save the Model.

After the commit, startRun starts the Run (Lesson 5), and the response reads the Run's log as server-sent events.

Key takeaways

If you remember only one thing: handleChat runs every check that can refuse before it writes, then writes all the rows in one transaction that locks the Conversation.

  • Gates, then the plane. A refusal leaves the database as it was, so a failed send never leaves half a Message behind.
  • Codes, not sentences. A refusal is a status plus { code, params }; the client looks the text up in errorMessages.
  • The lock keeps one Run. for("update") queues concurrent sends, so the later one sees the streaming reply and gets 409.

Go deeper: the full list, sources and a challenge

Every refusal, in the order of handle-chat.ts

  1. 429 error.tooManyMessages (with Retry-After)
  2. 400 error.invalidCommand: the body's forwardedProps fails chatCommandSchema
  3. 400 error.regenerateAttachments: no text but Attachments
  4. 404 error.conversationNotFound
  5. 400 error.modelNotAvailable, then 400 error.addKey or error.pickAnotherModel (no usable credentials; unusableModelCode in rpc-error.ts)
  6. 402 quota_exceeded with resetsAt, only on Host credentials
  7. 400 error.parentNotFound, then 400 error.regenerateNeedsMessage
  8. 409 error.approveFirst (ADR 0008), unless the waiting reply is hidden
  9. Attachment errors from attachmentsForSend
  10. 422 moderated from the Host's moderate hook
  11. 400 error.messageTooLong: the new Message alone is bigger than the context budget
  12. In the transaction: 409 error.replyStreaming, or 404 error.attachmentNotFound when lockAttachments finds a file gone

The decision

"One run per Conversation: the server returns 409 while a Message is streaming." (ADR 0002)

Side notes

  • Postgres runs each statement in "read committed" mode by default, so once the second send gets the lock, its next SELECT sees the first send's committed rows (Postgres: row-level locks, transaction isolation).
  • lockAttachments takes a weaker for("key share") lock on the Attachment rows, so the cleanup of unused uploads can't delete them before they are linked.
  • Two refusals don't follow the { code, params } shape: quota_exceeded isn't an error.* key, and the 422 body is { message, code: "moderated", reason }.
  • error.messageTooLong comes after moderate, so the Host's hook can see a Message that is refused later for its size.
  • The tests that pin each refusal are in error-codes.integration.test.ts and handle-chat.integration.test.ts ("a Model whose adapter can't be built, before writing anything").
