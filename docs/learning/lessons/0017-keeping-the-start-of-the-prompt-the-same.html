Keeping the start of the prompt the same

A provider can reuse the start of a prompt only if every byte of it is the same as last time. So a Bot freezes its start, tells it what changed in the newest message, and replaces it only when it writes a Summary.

About 15 minutes · a browser · no code to write; you'll answer the quizzes and read a cache chip

Words you'll need

Prompt start
The beginning of a Bot's prompt: its tools, its system prompt and a first message. It stays exactly the same on every model call until the next Summary.
Change note
A short line in the newest message that says what changed since the Prompt start was built.
Summary
A short account of a Conversation's older Messages. The Bot works from it in their place. Its last 3 Messages to the user stay word for word.
Deferred tool
A tool listed by name in the first message but not sent in tools. The Bot loads it with describe_tool and calls it with run_tool.

1Why the start must not move

A provider caches a prompt by its start. If the first 50,000 tokens are the same as on the last call, they are read from the cache at a lower price. If one byte near the start differs, everything after that byte is new. Slide 31 lays the prompt out for this, from stable to volatile. Slide 32 says to treat a cache miss like a bug.

The Bot's prompt has three parts, in this order:

  1. The Prompt start. The tools sorted by name, then the system blocks (the Bot's rules, the Computer, the memory snapshot and the Routines), then a first message. The first message holds the Bot's environment, the name of every tool and, after a Summary, the Summary.
  2. History. It is only ever added to at the end.
  3. The newest message. The time, then the Change notes, then what woke the Bot.

Before step 8, parts of the start moved. The memory snapshot was ranked again at each Turn's start, and its Notes window slides by the day. Older Triggers were cut to 2,048 characters once they stopped being the newest, so the history shifted too. Nothing marked the prompt for caching on Anthropic, so nothing was cached there.

2Freezing the start, and telling the Bot what changed

The Bot's first Turn builds a Prompt start and stores it in the bot_prompt_start table. The sections are stored with a hash of each one. Every model call, and every replay of a Turn after a crash, sends those stored bytes. The tools are stored too, so a deploy cannot change the definitions a Step sends.

The world still moves. The Turn still reads memory and the Routines every time. It compares them with what the Bot has already seen (the Prompt start plus the notes in earlier inputs) and writes the difference as Change notes, after the time. The notes start with [What changed since your prompt was built]. They cover three things:

  • memory lines added or removed, with their text;
  • Routines created, approved, changed or deleted;
  • tools whose definition changed in a deploy.

The Bot's own file writes during a Turn get no note. It knows what it wrote.

Two more rules keep the history from changing. The exact newest message is stored in bot_turn.input, and later Turns read it back instead of building it again. So the time and the Change notes stay in the history as they were. And the tool list never changes: only a short list of tools is sent in tools, and the rest (Routines, Check-ins, Helper management, and browser, desktop, plugin and connector tools) are Deferred tools, listed by name in the first message. A tool a deploy adds is deferred too, so it can be called through run_tool without a new start.

3Keeping the context small

A small context is cheaper to cache and to read (slide 33). Two rules keep big things out of it. A tool result or Trigger text over 10,000 characters keeps its first and last 2,000 characters, with [... N characters left out ...] between them. The full text goes to .outputs/<id>.txt on the Computer, and the result names the path. The read tool pages at 10,000 characters and returns a nextOffset.

A conversation can still grow. That is what a Summary is for. Writing one builds a new Prompt start: the memory snapshot and the Routines are read again, and the Summary goes at the end of the first message. After the Bot's first Turn, this is the only time the start moves. It happens in two ways:

  • While the user is away. A Turn whose last Step sent more than 100,000 tokens queues a bot.summarize-away job for 10 minutes after the Turn ends, while the cache is still warm. A new Turn cancels it. It is skipped if a Helper, a queued Trigger, or a Check-in or Routine due within 50 minutes is about to wake the Bot anyway. If a Turn started after the newest one it saw, its result is thrown away.
  • Mid-Turn. Before a Step's model call, if the previous Step's input was over 75% of the model's context window, the Turn writes a Summary first. It is a recorded activity, so a crash reuses it and it is billed once. The Turn goes on with the new Prompt start and its own input sent again.

4Telling each provider

The stable start only helps if the provider is asked to cache it. The code in cache-control.ts adds the settings for each provider:

  • Anthropic: a breakpoint on the last system block, one on the first message and an automatic one for the moving end of history. All three last 1 hour, not the default 5 minutes, so a Summary 10 minutes later still reads the cache.
  • OpenAI: a prompt_cache_key of bot:<botId> (a Helper uses helper:<helperId>), so calls land on the same cache.
  • The ChatGPT plan: it sends the same key but is treated as uncached. The probe in #664 found the plan caches nothing.
  • Gemini and the rest: nothing extra.

The meter records cache reads and writes. A cache read costs the Model's cacheReadUsdPerMillion from HOST_MODELS, and a write costs its cacheWriteUsdPerMillion. When the Host has not set one, that price is the input rate. Anthropic prices a 1-hour write at 2× input, so a Host on Anthropic sets the write price itself. The user's own key and the ChatGPT plan still write rows, with cost 0.

The page can also warm the cache (slide 32). It calls bot.warm when the Conversation opens and on the first keystroke of a draft, at most once a minute per tab. A warm is skipped while a Turn runs, while the last model call is less than the cache lifetime minus 5 minutes ago, and for providers with no warming call.

5Reading the cache chip

On every model call the code hashes each section: the tools, each system block, the first message and the history. It compares them, in order, with the Bot's previous call. The first section that differs is flagged, because everything after it is new anyway. The flag is bug if the previous call sent the same Prompt start, and expected if it sent another one. For history, only the newest message may be new.

Under each Turn in the thread, the chip reads Cache 66% · 3 Steps · $x. The percent is the cache-read tokens over the input tokens of all the Turn's Steps. It turns red and reads ⚠ Cache miss: <section> when any Step has a bug miss. Click it to see each Step's prompt as a bar sized by tokens, with every section's short hash.

Here is one Turn with three Steps. The numbers are made up to teach with. They are not a measurement.

  1. Step 1 sent 20,000 tokens and read 0. Suppose the cache is cold, as on the Bot's very first call or after a Summary. The tokens are written to the cache. (A later Turn on the same Prompt start normally reads the cache from its first Step.)
  2. Step 2 sent 20,500 and read 20,000. The Prompt start is the same, and history grew by one message. The 20,000 come from the cache, and the new 500 are written.
  3. Step 3 sent 21,000 and read 20,500. The same again.

The chip: 40,500 read of 61,500 sent is Cache 66% · 3 Steps. Here Step 1 holds the Turn's percent down. That is the cost of a cold write.

A bug miss. Suppose a change puts the current time into a system block. Step 2 now sends a different hash for that block than Step 1 did, and the Prompt start is the same one. The chip turns red: ⚠ Cache miss: <that block>. Expanded, the section row reads #a1b2c3 → #d4e5f6, and the Step says "A bug: that block changed, so everything after it was written again." The fix is to move the time out of the system block into the newest message, where it belongs.

An expected miss. Now suppose the user was away and a Summary was written. Their next Turn starts on the new Prompt start. Its first Step differs from the earlier call, and the Prompt start id is different too. If memory and the Routines did not change, the first section to differ is first_message, which now holds the Summary. The step reads "Expected: first_message changed with a new Prompt start." and the chip stays its normal colour. The next Step is back to reading the cache. If the Summary came 10 minutes after the last Turn, the 1-hour breakpoints are why the Summary call itself still read the old cache.

When there is a Summary, a card also shows in the thread: "Summarized while you were away" or "Summarized mid-Turn". Expand it to read the text and the 3 Messages kept word for word. A warm shows as a one-line note: "Cache warmed" with its cost.

Real-model eval results for this step are not in yet. The cache eval is run by hand on a real Anthropic key and fails on any bug miss (ticket #678). The numbers above are not from it.

Midway through a day, a new memory line is saved. Where does the Bot learn about it?

  1. In a rebuilt system prompt on the next call
  2. In a Change note in the next Turn's newest message
  3. It doesn't, until the next Summary

Quiz 2

Step 4 of a Turn shows a red cache miss on a system block. No Summary was written. Is it a bug?

  1. Yes. The Prompt start is the same, so no section should differ
  2. No. Every Step may miss a little
  3. No. A new Turn always builds a new start

Key takeaways

If you remember only one thing: the start of the prompt is stored and never changes until a Summary, so a provider can reuse it. What changes goes at the end.

  • A stored Prompt start. Tools, system blocks and a first message, sent as the same bytes on every call and every replay.
  • Change notes, not a new start. Memory, Routines and tool changes go into the newest message, which is then stored.
  • A Summary is the only reset. It builds a new start, and the one miss after it is flagged as expected.
  • A hash per section, per call. The first section that changed names the bug.

Go deeper: sources, side notes and a challenge

The lecture and the decisions

  • Slides 24, 31, 32, 33 and 34 of the lecture: tools kept small, the prompt laid out from stable to volatile, cache misses treated as bugs and warming, a small main context, and summarizing while the user is away.
  • Decision: ADR 0022, amended so the memory snapshot and Routines in the Prompt start stay frozen until a Summary.
  • Spec: Bot step 8, Context engineering (#665).

Side notes

  • Section sizes in the chip are estimates, at 4 characters a token. The provider's own read and write counts are laid over them as fractions of the input.
  • The tool schemas are checked to stay under 4,000 characters of description and schema each (slide 24).
  • A deploy cannot break a Step: Steps send the stored definitions, but calls run against the current code, whose schema checks the arguments and answers with what to do next. A removed tool answers "no longer available".

What was left out

The cache is not shared between Bots: each Bot has its own key and its own start. The real-model cache eval is being run by hand, and this lesson has no results from it.
