The command the client sends

The browser asks for a reply. The server decides what the Model reads.

About 12 minutes · a browser · you'll write commandFor(messages, action), the part of a send that changes between send, edit and regenerate

Words you'll need

Command
The small object the browser posts to start a Run (ChatCommand). It names Messages by id and never copies them.
History
The Messages above the new one on its Branch, oldest first.
parentId
The Message the new one continues. null means "start at the root".
forwardedProps
The field in TanStack AI's request body that carries the app's own data.

1A transfer form, not a bank statement

When you send money, you fill in a form: the account and the amount. You never send your balance, because the bank reads it from its own books. The command works the same way. The browser names the Conversation and the parent Message, and the server reads the history from Postgres.

The request does carry TanStack AI's messages list, because useChat always adds it. But handleChat parses only body.forwardedProps with chatCommandSchema and answers 400 error.invalidCommand if it doesn't fit. Then loadPath(deps, conversationId, parentId) (in message-tree.ts) walks the stored tree up from the parent. So a user can't invent a reply the Model never wrote, and edits keep old Branches (ADR 0001).

Quiz

A user edits the request in DevTools and adds a fake assistant reply to messages. What does the Model see?

  1. The fake reply, at the end.
  2. Only the history stored in Postgres.
  3. A 400 error, and no reply.
  4. The fake reply, stored for later.

2What the command holds

command.ts has two more fields: webSearch (the composer's Web toggle) and tools (the MCP Connections switched on, read only for a Conversation's first Message). The file sits in shared, because the browser builds the command and the server checks it with the same zod schema.

3Send, edit, regenerate: two fields change

All three actions post the same command. Only parentId and text change. For an edit or a regenerate, branchFrom takes the Messages above the one you pressed, and the last of those is the parent:

  1. Send: the parent is the last Message on screen, a2.
  2. Edit q2: the Messages above it are [q1, a1], so the parent is a1. The new text goes beside q2.
  3. Regenerate a2: above it are [q1, a1, q2], so the parent is q2, and there is no text.
Quiz

The Branch is q1, a1, q2, a2. You regenerate a1. What is sent?

  1. parentId: "q1", no text
  2. parentId: "a1", no text
  3. parentId: "q1", with text
  4. parentId: null, no text

4Where the command is built

In chat-view.tsx, send and startBranch both call run(parentId, text). run writes the command into a ref, then calls sendMessage (with text) or reload (without). reload takes no body, so the command rides in the connection instead: fetchServerSentEvents(chatUrl, () => ({ body: command.current })), and TanStack AI copies that body into forwardedProps.

When the Run ends, run fetches conversation.get and replaces useChat's messages with the server's Active Branch. The server stays the source of truth.

Key takeaways

If you remember only one thing: the browser sends ids and choices in forwardedProps; the server rebuilds the history from Postgres with loadPath.

  • A form, not a statement. handleChat ignores body.messages, so a client can't forge history.
  • Two fields change. Send, edit and regenerate differ only in parentId and whether text is there.
  • One schema, both sides. chatCommandSchema lives in shared; the browser builds it and the server checks it.

Go deeper: sources, side notes and a challenge

The decision, in the code

"What the client asks for: a command, never history (ADR 0001). History is rebuilt from the database by walking up from parentId. useChat sends it as the AG-UI forwardedProps." (command.ts)

What TanStack AI puts in the body

In the installed @tanstack/ai-client 0.39.0, buildRunAgentInputBody (in node_modules/@tanstack/ai-client/dist/esm/connection-adapters.js) builds { threadId, runId, state, messages, tools, context, forwardedProps, data }. forwardedProps merges the connection's body with the send's data, and data is a copy of it. The shape is the AG-UI protocol's RunAgentInput.

Side notes

  • The URL comes from the Host: apps/web/src/utils/orpc.ts calls createBotSdkClient({ baseUrl: origin + "/api/chat" }), and chat-client.ts makes chatUrl from it: …/api/chat/run.
  • The connection's fetchClient is runFetch (rate-limit.ts). It turns a 429, a moderated 422 and any { code } refusal into typed errors.
  • An edit sends the full list of attachmentIds it keeps; a regenerate sends none, and handleChat refuses one that does (error.regenerateAttachments).
  • The server also checks the parent: an unknown parentId is error.parentNotFound, and a regenerate whose parent isn't a user Message is error.regenerateNeedsMessage. Lesson 4 walks through every check.
