Thin client, thick server, and sync

The server keeps the Bot's thread and numbers each change. A tab sends no data back, and it asks for what came after its number.

About 10 minutes · a browser · no code to write; you'll answer the quizzes and run one manual demo

Words you'll need

Change log
The newest changes to one Conversation's thread, each with a number.
Cursor
The number of the last change that a tab has applied.
Hint
A signal that says "something changed". It carries no data.
Reload
Read the whole thread again with bot.get.

1The apps are thin, the server is thick

A user can open the same Bot in several tabs. Each one must show the same Conversation. The Bot runs on the server, and the database holds the real thread. A tab keeps only a copy, and the copy can fall behind. So the server tells the tabs what changed, and each tab catches up.

2Each change gets a number

Every change to the thread takes the next number of its Conversation. The changes are a new Message, a Turn's status, and a change to a Routine, review, Helper, Check-in, Secret or Summary. The number is last_seq on the Conversation row. The change goes into conversation_change in the same transaction, under the row lock. The changes commit in number order, with no gaps. The log keeps the newest 500 changes of each Conversation.

  1. last_seq is 41. A Turn starts.
  2. The transaction sets last_seq to 42 and writes change 42, a turn.
  3. It commits. A Message is saved next, and it takes number 43.

3A hint carries no data

The server publishes a hint, {"type":"changed"}, on the Conversation's channel. It holds no data. A tab fetches the changes after its cursor with bot.changes, and it applies them in number order. The tab also fetches when its stream reconnects and when the window gets focus. The table shows what the tab does with the numbers it gets.

Cursor and what came back What the tab does
Cursor 41, then 42 and 43 Applies both, in order. The cursor becomes 43.
Cursor 41, and the first change is 44 (42 and 43 missing) Reloads the thread with bot.get.
Cursor older than the log's oldest change Reloads the thread with bot.get.

4A fallback for lost hints

PubSub delivers a hint at most once. If the last hint of a Turn is lost, the tab would show "Working…" for ever. So a tab with a running Turn also fetches every 30 seconds. The lecture does not cover this fallback, so it is a recorded deviation (ADR 0026). ADR 0026 also records the design it replaced: a tab polled bot.get every 2 seconds, and a 15-second refresh caught background work.

Key takeaways

If you remember only one thing: the server numbers each change, and a tab asks for the changes after its cursor.

  • Numbers, not timestamps. One counter per Conversation, bumped under its row lock, so no change can be skipped.
  • Hints carry no data. A lost hint is covered by a fetch on focus, on reconnect and every 30 seconds while a Turn runs.
  • A gap means reload. A missing number, or an old cursor, makes the tab read the thread again.

The lecture

The lecture is not in this repo. ADR 0026 cites its slide 19 as the design this lesson follows.

The decisions

  • Decision: ADR 0026. It rejects a Postgres sequence, because values can commit out of order, and it rejects LISTEN/NOTIFY, as ADR 0006 does.
  • Channels: the ADR says email and later Channels need no change log. They get deliveries, not a view. The Channels eval (packages/bot-sdk/eval/channels) is hand-run, and its README says its results go to a gitignored folder.
  • Rich controls: the catalog in rich-control.ts reserves two kinds that are not built yet, so their fields can come later without breaking the format.
