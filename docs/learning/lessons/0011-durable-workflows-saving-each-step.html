Durable workflows, saving each step

A Turn runs as a job that saves a Checkpoint after each piece of work. After a crash, the job replays its history and carries on.

About 14 minutes · a browser · you'll write replay(history, calls), the check that decides what a resumed job skips

Words you'll need

Checkpoint
The saved result of one piece of a Turn's work, such as one Model call.
History
The Checkpoints of one job, in the order they were saved.
Replay
Running the job's code again from the top, with the history answering each call.
Lease
The claim that one process holds on a running job. It expires if the process stops.

1A Turn that survives a crash

In Lesson 10 the request ran the whole Turn, so a crash threw it away. The lecture wants the opposite. Slide 13's agent "runs a turn, then stops", and it "loads state, works, saves each step".

Now a Turn is one job in the runner, keyed by the Turn's id. The job's code asks for work through ctx.activity(name, fn). It runs fn once and saves the JSON result as a Checkpoint in chat.job_event. After a crash, any process claims the job and runs its code again from the top. While the history has an entry, a call returns the saved result and runs nothing. Past the end, calls run for real.

playTurn saves a "model" Checkpoint for each Model call, a "bill" Checkpoint for its usage, and one Checkpoint for each tool call. A replayed Model call plays its saved chunks, so a resume never calls the Model for a Step it already took.

2One rule: the same calls in the same order

A call has no id. Its place in the order is its identity. On replay, the engine compares each call's kind and name with the entry at that place (createWorkflow). A mismatch throws NonDeterminismError with the seq, the recorded entry and the call. It fails the job for good and runs onFailed, so a broken resume fails loudly and never takes another path.

This gives the authors' rule: code outside ctx.activity runs again on every attempt, so whatever picks the next call must give the same answer. Times and random numbers come from ctx.now() and ctx.random(), which are recorded. Reads and side effects go inside an activity. To change a workflow while older runs are in flight, ask ctx.patched(id). It is true in a new run and in a replay that has its marker, and false in a replay that passes that point without it.

3At least once, or exactly once

A plain ctx.activity(name, () => …) is at-least-once. If the process dies after fn but before the save, the next attempt runs fn again. A ctx.activity(name, (tx) => …) gets the transaction its Checkpoint is saved in. Its writes and the Checkpoint commit together or not at all, so it runs exactly once.

That is why a SendToUser Message is never sent twice. The tool appends its Message inside the (tx) activity, so a crash before the commit leaves no Message and no Checkpoint, and the retry sends it once. The "bill" Checkpoint does the same for usage. A Model call cut off by a crash records nothing, so it bills nothing and runs again with the same input.

4Leases, the reaper and a deploy

A running job heartbeats every 10 s, and every Checkpoint save renews the lease too (jobHistoryStore). Each save is fenced: it writes only while this attempt still owns the row, so a lost attempt can't write over a newer one. If the lease runs 60 s without a renewal, the 30 s reaper (reapStaleJobs) re-queues the job, and any process can claim it. After 3 attempts the job fails and onFailed ends the Turn error / interrupted.

A deploy is gentler. stop() asks each running job to yield. At its next Checkpoint it saves, stops, and its row goes back to queued without counting an attempt, so another process resumes it at once instead of a lease later.

Web no longer runs the Turn. bot.send saves the user's Message, enqueues the job and then follows the Turn from Postgres (followTurn). It re-reads when a "changed" hint arrives and every 2 s, so closing the tab ends only the follow. A new bot.stop cancels the job. A Turn that resumes on another server keeps showing "Working…", with no "Resuming" label.

Key takeaways

If you remember only one thing: a job saves a Checkpoint after each piece of work, and after a crash it replays its history and carries on after the last one.

  • Order is identity. A replay with a different call order fails with NonDeterminismError.
  • Plain activities run at least once. A (tx) activity commits with its Checkpoint, so a Message is sent once.
  • Leases bring work back. The reaper re-queues a silent job, and a deploy hands it back at its next Checkpoint.

Go deeper: sources, side notes and a challenge

The lecture

  • Slide 13, "How does it stay always on?": the agent process "runs a turn, then stops" and "loads state, works, saves each step". Its footer: "Everything that matters is saved, so any trigger can bring it back."
  • Slide 17, "Why the agent runs on the server": "Close your laptop and the work keeps going". Slide 18: "Save everything on the server."
  • Slide 42 lists "Durable workflows" as the first of the eight pieces "every agent product will have". The slides do not name an engine, a history, a lease or a replay rule. Those come from ADR 0011 and its step 2 amendments, not from the lecture.

Side notes

  • The model is Temporal's: a workflow replayed from its history, the determinism rule, and patched. This repo builds it in plain TypeScript on Postgres, without Temporal's sandbox (as DBOS does). The engine imports nothing from the Bot SDK (workflow/engine.ts), so it could become its own package.
  • The bot plugin refuses to start on the Trigger.dev adapter (bot/server/plugin.ts). That adapter records no history, so a retry would start the Turn over and send its Messages again.
  • The 10-Step limit counts the replayed Model calls, so a crash can't reset it. The 5-minute limit counts from the Turn's start on the wall clock, crash time included, and it is a timer that aborts the live Model call, never a branch in replayed code.
  • Quota is checked once, in sendToBot, before the Message is saved, so a resume is never refused halfway. A Turn that resumes past 5 minutes ends timed_out without calling the Model.
  • The crash tests are in test/plugins/runner/server/workflow.integration.test.ts and test/core/server/routers/bot-send.integration.test.ts.

What was left out, and what comes next

Temporal's sandbox is left out, so the determinism rule is a rule authors keep, not one the engine forces. There are no per-activity retry policies, no LISTEN/NOTIFY, and no deprecatePatched. Runs stay off the runner. Later steps add more kinds of history entry (steps 3, 4 and 6 in the spec).
