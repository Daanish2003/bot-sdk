handleChat: check, then write

Every check runs before the first row is written.

Words you'll need

Refusal
An early error Response from refuse(status, message). It ends handleChat before any write.
Transaction
A group of database statements that all happen or none happen. Drizzle opens one with deps.db.transaction(…).
Row lock
.for("update") on a select. Other transactions that lock the same row wait until this one ends.
Streaming row
An assistant Message with status: "streaming" and no parts yet, written before the reply starts.

1The check-in desk

Think of an airport. Every check happens at the desk, and you walk to the plane only when all of them pass. handleChat in handle-chat.ts works the same way, and its own comment says so: "Everything that can fail runs before the Messages are written."

This matters because a half-written send is worse than none. If the streaming row were written and then a credentials check failed, that row would stay streaming, and every later send to the Conversation would get 409.

2One run per Conversation

Two tabs can press Send at the same moment. Without a lock, both could look for a streaming row, find none, and both start a run. So the transaction first locks the Conversation row with .for("update"); Postgres makes any other locker of that row wait until this transaction ends.

  1. A locks the row, finds no streaming Message and inserts its streaming row.
  2. B asks for the same lock and waits.
  3. A commits, so B gets the lock, finds A's streaming row and returns "streaming", which becomes 409.

3What the transaction writes

Look at the left tree. Inside the same transaction, handleChat inserts the user Message (complete) and, under it, the assistant Message (streaming, empty parts) with a createdAt one millisecond later, so it always sorts after its parent. Then it links the attachments and sets the Conversation's activeLeafId, lastMessageAt and model.

Both ids come from uuidv7() on the server; the client's ids are never stored.

4Then, and only then, the stream

After the transaction commits, handleChat calls startRun(deps, { messageId, adapter, messages, webSearch }) and returns toServerSentEventsResponse(chunks). The adapter and the model messages were built during the checks, so the steps that can fail are already behind it. Lesson 4 opens startRun.

Key takeaways

If you remember only one thing: handleChat checks everything first, writes in one locked transaction, and only then starts the run.

  • The ladder. Session, command, ownership, Model, credentials, parent, attachments. The first failure returns its status, and nothing is written.
  • One run per Conversation. The row lock queues sends, so a second send sees the streaming row and gets 409.
  • The writes. User Message, empty streaming reply, attachment links, then activeLeafId moves to the reply.

Go deeper: sources, side notes and a challenge

What the row lock does

"FOR UPDATE causes the rows retrieved by the SELECT statement to be locked as though for update. This prevents them from being locked, modified or deleted by other transactions until the current transaction ends." (PostgreSQL: Explicit Locking)

switchBranch in api/src/chat/store.ts takes the same lock, so a Branch switch can't slip in while a send is being written. See Drizzle: Transactions for the API.

Two attachment locks

lockAttachments uses .for("key share"), a weaker lock, so the orphan cleanup can't delete an uploaded file between the checks and linkAttachments. If a file is gone by then, the send returns 404 "Attachment not found".

Unusual statuses

An invalid command is 400, a missing Conversation is 404, and an attachment problem is 404 (not yours) or 400 (wrong type, over 5 MB, Branch over 20 MB), from attachmentsForSend.
