Branches

Edit and regenerate add a sibling; the arrows jump to the newest leaf.

About 15 minutes · a browser · you'll write siblingPosition and newestLeaf, the two functions behind the ‹ n/m › arrows

Words you'll need

Sibling
A Message with the same parentId as another. All roots are siblings of each other.
Edit
Sending a changed copy of a user Message. The copy is a new sibling of the old one.
Regenerate
Asking for a new reply to the same user Message. The new reply is a sibling of the old one.
Newest leaf
The leaf with the latest createdAt anywhere below a Message.

1Edit and regenerate add a sibling

Think of a road that forks: the old road stays, and a sign shows which road you are on. Both actions use branchFrom(messages, messageId) in chat-core/chat.ts. It returns the parent of messageId on the screen, so the new Message goes under the same parent. Follow Regenerate on a2:

  1. branchFrom(messages, "a2") keeps [q1, a1, q2] on the screen and returns parentId: "q2".
  2. The command has no text, so handleChat inserts only a new reply under q2.
  3. It sets activeLeafId to the new reply. a2 stays, now a sibling.

An edit has text, so handleChat inserts a new user Message under the parent and a new reply under that.

2‹ n/m › counts siblings

siblingPosition(nodes, node) in branches.ts finds every Message with the same parentId, sorts them oldest first, and returns the place of node in that list. Look at q2b in the picture: its siblings are [q2 (m2), q2b (m5)], so it is index 1 of 2, shown as ‹ 2/2 ›, with previousId: "q2" and nextId: null.

"Oldest first" means compareAge: earlier createdAt first, and if two are equal, the smaller id first. The ids are uuidv7, which start with the creation time, so id order follows creation order too.

3Switching jumps to the newest leaf

An arrow names only a sibling, not a whole Branch. So conversation.switchBranch({ messageId }) sets activeLeafId to newestLeaf(nodes, messageId): the newest leaf anywhere below that sibling. Follow it in the picture:

  1. The screen shows q1b → a1c, and q1b shows ‹ 2/2 ›. Press ‹: previousId is q1.
  2. The leaves under q1 are a2 (m3), a1b (m4) and a2b (m6).
  3. The newest is a2b, so activeLeafId = "a2b": the Branch you last worked on there.

A switch is refused while a reply streams. switchBranch in store.ts locks the Conversation row, like handleChat, and returns "streaming", which the router turns into CONFLICT. The screen also turns off the arrows while streaming is true.

Key takeaways

If you remember only one thing: edit and regenerate insert a sibling under the same parent, and switching to a sibling shows its newest leaf.

  • Same parent. branchFrom gives the parent; an edit adds a user Message and a reply, a regenerate adds only a reply.
  • ‹ n/m › is siblingPosition. Siblings sorted by createdAt, then id.
  • Switch = newestLeaf. Refused while a reply streams.

Self-test: cover this box, then say which Messages a regenerate inserts and which an edit inserts.

Go deeper: sources, side notes and a challenge

Sources

  • CONTEXT.md defines Active Branch: "Switching to a sibling makes its newest Branch active."
  • The tests in branches.test.ts use the same tree as this lesson, including the test "is the newest leaf anywhere in the subtree, not the newest child's".

Side notes

  • Regenerate is only allowed when the parent is a user Message: handleChat refuses with "Only a reply to your Message can be regenerated". It also refuses new attachments on a regenerate.
  • handleChat gives the new reply createdAt = now + 1 ms, so it sorts after its own user Message.
  • Switching doesn't bump lastMessageAt, so it doesn't move the Conversation in the side panel.
  • While a reply streams, messageSiblings in chat-core says 1 of 1, because useChat's new Message has no server data yet. The real position comes back when the Active Branch is fetched again.
