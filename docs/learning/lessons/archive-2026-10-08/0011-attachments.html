Attachments

Upload first, send the ids, link them — never copy the file.

About 14 minutes · a browser · you'll write checkSend(model, files, historyBytes), the checks a send makes on its files

Words you'll need

Attachment
A file (image, PDF or text file) that a user uploads and attaches to their Message. It is never copied.
Join table
A table whose rows only link rows of two other tables. Here: message_attachment links a Message to an Attachment.
Orphan
An Attachment that no Message uses, such as a file you uploaded and then never sent.

1Upload first, then send the ids

Think of a coat check. You hand over the coat first and get a ticket; later you show only the ticket. When you pick a file, the composer calls attachment.upload at once. The server checks it (up to 5 MB; an image, a PDF or UTF-8 text) and returns an AttachmentInfo: { id, filename, mediaType, size }.

The send waits until every upload is done, then puts the ids in ChatCommand.attachmentIds. The bytes are in their own table, attachment_blob, so a list of Messages never loads them by accident.

2Linked, never copied

Attachments are not Message parts (ADR 0001). linkAttachments writes one message_attachment row per file: messageId, attachmentId and a position for the order.

An edit is a new user Message beside the old one, so the client sends the full list it keeps. In the picture, the edit kept photo.png and dropped notes.md, which gives one new link row and no copy. A regenerate writes no user Message, so its links stay as they were, and handleChat refuses a regenerate that brings attachments. The foreign key from the link to the Attachment has no cascade, so an Attachment can't be deleted while a Message uses it.

Quiz

You edit a Message that had two attachments. You remove one and add none. What does the send write?

  1. New Message, one link row
  2. Old link row is deleted
  3. Attachment bytes copied once more
  4. New Message, two link rows

3Orphans and the lock

Files that you upload and never send would stay forever, so every upload first runs deleteOrphanAttachments: it deletes Attachments older than 24 hours that no Message links. That opens a race. Look at the picture: a send could link a day-old upload at the same moment that another upload's cleanup deletes it.

So the send transaction calls lockAttachments, which takes a FOR KEY SHARE lock on its rows. The cleanup selects with FOR UPDATE SKIP LOCKED, so it steps over locked rows. If a file is already gone, the lock finds fewer rows and the send answers 404 "Attachment not found".

Quiz

Why does the send lock the Attachments it is about to link?

  1. So the bytes load faster
  2. So two users can share
  3. So cleanup can't delete them
  4. So the Model reads them

4What the Model may read

Before any write, handleChat calls attachmentsForSend. Every Model reads text files; images and PDFs only when its capabilities say so (acceptedKinds). The Branch limit exists because the history goes to the Provider again on every turn. Here is a send that fails:

  1. The Model is a GPT Model: images: true, pdfs: false.
  2. acceptedKinds gives ["text", "image"], and report.pdf is a pdf.
  3. "pdf" is not in the list, so the send answers 400 `${model.label} can't read PDFs` and writes nothing.

A Shared link shows each Attachment only as a filename and type: redactAttachmentsForShare drops the id and size, and the bytes are never public.

Key takeaways

If you remember only one thing: an Attachment is uploaded once and linked by id through message_attachment; it is never a part and never copied.

  • Coat check. Upload first, send attachmentIds. An edit sends the full kept list; a regenerate sends none.
  • Lock before you link. The send's FOR KEY SHARE lock keeps the orphan cleanup away.
  • Check, then write. Owned, readable by the Model, 5 MB each, 20 MB per Branch. A Shared link shows filename and type only.

  • ADR 0001, Consequences: "Attachments are not parts."

Old files and a new Model

The kind check runs only on the new files. If you switch the Conversation to a Model that can't read PDFs, a PDF already in the history is not refused: toModelMessages sends it as a short placeholder, [Attached PDF "x" left out: this Model can't read PDFs]. Text files always go as fenced text.

The two lock modes

PostgreSQL's FOR KEY SHARE conflicts with FOR UPDATE, (PostgreSQL: Row-Level Locks), and with SKIP LOCKED "any selected rows that cannot be immediately locked are skipped" (PostgreSQL: the locking clause).
