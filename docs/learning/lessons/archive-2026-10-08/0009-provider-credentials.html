Provider credentials

The browser can put a key in, but it can never take it out.

About 12 minutes · a browser · you'll write credentialHint(fields) and splitSealed(encrypted)

Words you'll need

Provider credentials
What one user gives to reach one Provider: usually an API key, sometimes with an account or region, or only a host (Ollama).
KEY_ENCRYPTION_SECRET
The server's one secret, from the environment. Every stored credential is encrypted with a key made from it.
AES-256-GCM
An encryption method that also adds a tag, so a changed or moved value fails to decrypt.
Hint
The only part the client sees: the end of the key, such as …abcd.

1Write-only, like a letterbox

A letterbox lets anyone put a letter in, but only the owner with the key can take it out. The credentials router works the same way. Follow one save in the picture:

  1. credentials.save gets { service: "anthropic", fields: { apiKey } }.
  2. checkCredentials makes one cheap call to the Provider. If the Provider refuses the key, the save stops with an error.
  3. saveCredentials encrypts the fields and stores them with the hint …1234.
  4. credentials.list returns only { service, hint, verified }. No procedure returns the key.

2One row, sealed

The user_credentials table has one row for each user and service. Its encrypted column holds the fields as JSON, encrypted with AES-256-GCM. Look at the four parts: a version, a random iv (so the same key encrypts differently each time), the tag, and the ciphertext.

The encryption also binds the row's own userId:service into the tag. So if someone copies a row to another user or service, it fails to decrypt, and decryptCredentials returns null.

Quiz

Someone copies Alice's anthropic row and changes its user_id to Bob. What does Bob's run get?

  1. null: treated as missing.
  2. Alice's key for Bob.
  3. It throws an error.
  4. Bob's own saved key.

3Why the server holds the key

TanStack AI can keep keys in the browser and send them with each request. ADR 0003 rejects that, because a run outlives the client (Lesson 7) and the title is made after the run ends. Look at the timeline: both happen when nobody is connected.

So handleChat calls loadCredentials(deps, userId, model.provider) before it writes anything. If it returns null, the answer is a 400 with addKeyMessage: "Add an Anthropic key or pick another Model".

4If the secret changes

The key that encrypts is made from KEY_ENCRYPTION_SECRET. If an operator changes the secret, old rows no longer decrypt. The code doesn't crash: loadCredentials returns null, and listCredentials leaves those rows out, so the user sees no key and enters it again. Version 1 has no key rotation.

Quiz

An operator changes KEY_ENCRYPTION_SECRET and restarts. What do users see?

  1. They must re-enter their keys.
  2. Old keys keep working fine.
  3. The server refuses to start.
  4. Keys are re-encrypted on boot.

Key takeaways

If you remember only one thing: credentials are write-only. The browser saves them, and only the server decrypts them, when a run or a title needs them.

  • Sealed per row. AES-256-GCM under KEY_ENCRYPTION_SECRET, bound to userId:service.
  • Server-side, on purpose. Runs and titles happen with nobody connected, so the browser can't hold the key (ADR 0003).
  • Can't decrypt means missing. A wrong secret or a moved row gives null, and the user adds the key again.

Go deeper: sources, side notes and a challenge

The decision

"The JSON is encrypted with AES-256-GCM under KEY_ENCRYPTION_SECRET (Varlock), and the client can write credentials but never read them back: it only sees the hint (e.g. "…abcd")." (ADR 0003)

The ADR rejected plaintext in Postgres ("a database dump leaks every user's keys") and server keys in env ("the app should not pay for other users' runs").

Details in the code

encryption.ts derives the 32-byte key with HKDF-SHA256 from the secret, uses a 12-byte random iv, and insists on a full 16-byte tag, because Node would otherwise accept a shortened tag. The userId:service context goes in as additional authenticated data (setAAD). Read Node's createCipheriv docs for the GCM options.

The field shapes are zod schemas per service in services.ts: most need only apiKey, Bedrock adds region, Cloudflare adds accountId, and Ollama needs only host. That file is plain data and zod, because the browser imports it too (Lesson 1).

Some services have no endpoint to check a key, so checkCredentials returns unverified and the row is saved with verified: false.
