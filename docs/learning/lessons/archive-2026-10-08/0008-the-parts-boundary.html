1One shape at home, one adapter

Think of a travel adapter. Your devices keep their own plugs, and one adapter fits the foreign socket. Postgres keeps our plug, the stored parts. TanStack AI has two sockets: UIMessage for the browser and ModelMessage for the Provider.

Look at the three arrows. createPartsBuilder turns stream chunks into stored parts while a run goes. toUIParts turns them into what the screen draws, and toModelMessages turns history into what the Provider reads.

2Why our own shape

TanStack AI is before version 1.0 and changes fast. If the database held its shapes, one library upgrade could make old Messages unreadable. Our shape is a zod union in db/src/message-parts.ts, and parseStoredParts checks every row it reads. An unknown schemaVersion or part type throws, so a bad row fails loudly, not quietly.

  3. They no longer parse correctly.
  4. They get rewritten on read.

3Building parts from the stream

A Provider streams text in small pieces called deltas. Each TEXT_MESSAGE_CONTENT chunk has a messageId and a delta. Follow the chunks in the picture:

  1. a: "Hel": no parts yet, so push { text: "Hel" }.
  2. a: "lo": same id, last part is text, so append: "Hel" + "lo" = "Hello".
  3. b: "Bye": a new id, so push a second part { text: "Bye" }.

A search in the middle of a reply also pushes a part, so text after it starts a new part. That keeps the text before and after a search in order.

4Thinking goes home only

A thinking part can carry a signature: an opaque value the Provider made and wants back, unchanged, on later turns. Another Provider can't read it. So toModelMessages compares providerOf(message.model) with the Provider of this request, and it adds thinking only when they match. The row keeps the thinking either way.

Key takeaways

If you remember only one thing: Postgres keeps our own shape, and only parts.ts translates it to TanStack AI's shapes.

  • One adapter. createPartsBuilder in, toUIParts and toModelMessages out. A library upgrade checks this one file.
  • Checked on read. parseStoredParts validates schemaVersion: 1 and the three part types.
  • Thinking goes home only. It is sent back only to the Provider that wrote it, and never rewritten in the row.

Go deeper: sources, side notes and a challenge

The decision

"Message parts are stored as jsonb in our own zod-validated shape (with a schemaVersion), not TanStack's UIMessage shape, and converted at one boundary module: TanStack AI is pre-1.0 and changing fast, and a library upgrade must not break stored history." (ADR 0001)

The ADR also rejected a message_part table, because parts are always read and written with their Message, so a table would only add joins.

Honest edges of "one file"

parts.ts is the one place that converts stored parts. Other api files still import @tanstack/ai for other jobs: run.ts calls chat(), and sources.ts and share/redact.ts read the UI parts after conversion. The browser draws the UI parts directly, so a change to TanStack's UI shape can still reach chat-react. What it can't reach is the rows.

Search in two forms

When this request offers the web_search tool, a finished search replays as a real tool call plus a tool result. Otherwise it becomes text such as [Searched the web for "…": no results]. A running or cancelled search is left out, because a tool call with no result would confuse the Provider. See withToolCalls and withPlaceholders in parts.ts.
