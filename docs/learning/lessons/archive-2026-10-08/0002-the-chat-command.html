The chat command

The client sends an order, never the history.

About 12 minutes · a browser · you'll write commandFor(action, messages, messageId, text), the parent picker for send, edit and regenerate

Words you'll need

ChatCommand
The small object the client posts to /api/chat: which Conversation, which Message to continue, the text, the Model.
useChat
TanStack AI's React hook. It holds the messages on screen and reads the reply as it streams.
SSE
Server-sent events: one HTTP response that stays open and carries many small chunks, one after the other.
forwardedProps
The field of useChat's request body that carries our own data. The ChatCommand rides in it.

1An order, not the whole meal

Think of a waiter who writes "table 4: one more coffee after the cake" on a slip. The waiter doesn't read the whole meal back to the kitchen, because the kitchen already knows it. The ChatCommand is that slip.

Look at the picture. useChat also puts the messages on screen into the body, because TanStack AI expects that. handleChat ignores them: it parses only forwardedProps, then walks up from parentId in the database (ADR 0001). So a browser can't change history, and parentId says exactly where in the Message tree the new Message goes.

2Three actions, one command

Edit and regenerate don't change a Message. They add a new one beside it, under the same parent, and that makes a new Branch. branchFrom(messages, id) in chat-core finds that parent: it is the Message just before id on screen. Take the screen u1, a1, u2, a2:

  1. Edit u2: the Message before it is a1, so parentId is a1, with the new text.
  2. Regenerate a2: the Message before it is u2, so parentId is u2 and there is no text.

3How the command travels

ChatView.run writes the command into command.current, a React ref, and then calls sendMessage (send, edit) or reload (regenerate). reload() takes no body, so the command can't be passed as an argument. Instead, the connection fetchServerSentEvents(chatUrl, () => ({ body: command.current })) reads the ref each time it posts, and TanStack AI copies body into forwardedProps.

The reply comes back on the same response as SSE chunks, and useChat adds each chunk to the last message on screen.

4Before and after the stream

Before. On the new Conversation page there is no Conversation yet. NewConversationPage calls conversation.create, stores the text with setPendingFirstMessage(id, …) and navigates to /c/$id. There, ChatView takes it once with takePendingFirstMessage and sends it.

After. While a reply streams, useChat's messages are the truth, but their ids are the browser's own. When the stream closes, run's finally fetches conversation.get again and calls setMessages with the server's rows: real ids, status and Branch arrows.

Key takeaways

If you remember only one thing: the client sends a command (conversationId, parentId, text, model), and the server rebuilds the history itself.

  • One shape, three actions. Send continues the last Message. Edit and regenerate go under the parent of the Message they replace; a regenerate has no text.
  • The command rides in a ref. reload() takes no body, so the connection reads command.current and TanStack AI puts it in forwardedProps.
  • The server's copy wins. When the stream closes, the page fetches the Active Branch and replaces useChat's messages.

Go deeper: sources, side notes and a challenge

We use TanStack AI differently from its guide

TanStack AI's streaming guide has the server read messages from the request body: "chatParamsFromRequest reads the AG-UI body that useChat sends." (TanStack AI: Streaming). ai-chat doesn't, because ADR 0001 keeps the Message tree in our own tables. You can see the copy into forwardedProps in the installed client: buildRunAgentInputBody in node_modules/.pnpm/@tanstack+ai-client@0.36.2*/…/dist/esm/connection-adapters.js.

The shape is shared, not copied

ChatView types its ref as ChatCommand, which handle-chat.ts exports with z.input<typeof chatCommandSchema>. So if the server adds a field, the client fails its type check until it sends it. This is one of the import type edges from Lesson 1.

Why "a tick later"

ChatView takes the pending first Message inside a setTimeout. React's StrictMode mounts a component, unmounts it and mounts it again in development; without the timer, the throwaway first mount would take the text and lose it.
