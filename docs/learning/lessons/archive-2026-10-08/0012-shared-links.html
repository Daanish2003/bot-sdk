Shared links

A bookmark into the Message tree, not a copy of it.

About 13 minutes · a browser · you'll write redact(message) and blockedBy(leafId, status)

Words you'll need

Shared link
A public, read-only view of one Branch of a Conversation. A Conversation has at most one (see CONTEXT.md).
Token
The random part of the public URL, /share/<token>. It is 22 characters and is not related to any internal id.
Redact
Remove the private parts of a Message before a viewer sees it.
Allowlist
A list of what may pass. Anything not on the list is removed.

1A pointer, not a copy

Think of a bookmark in a book that nobody rewrites. Messages are never changed once written: an edit or a regenerate adds a sibling (Lesson 6). So the path from a root down to one leaf stays the same for as long as the Conversation exists, and the link can store a pointer instead of copies.

Look at the row in the picture. It has the token, the conversationId (unique, so one link per Conversation), the leafMessageId and a frozen copy of the title. To show the page, loadSharedConversation calls loadPath(conversationId, leafMessageId), which is the same walk the Active Branch uses.

2Sharing again moves the bookmark

upsertSharedLink inserts a row, and if the Conversation already has one, it updates that row instead (onConflictDoUpdate on conversationId). Try it in the toy:

  1. Share: a new row gets token k3Fq… and leaf A2.
  2. Edit Message 2: the Active Branch is now U1 → A1 → U2′ → A2′, but the link still shows A2. The dialog says the Conversation "has moved on".
  3. Share again: the same row now has leaf A2′, so the old URL shows the new Branch.

Sharing is refused when the Conversation is empty, or when the newest Message is streaming or error. A stopped reply can be shared.

Quiz

You share, regenerate the last reply, wait for it to finish, then share again. What happens?

  1. Same token, the leaf moves.
  2. New token, old one revoked.
  3. Two tokens, both stay live.
  4. Nothing changes; links are frozen.

3What a viewer sees

A viewer gets the Branch with private things removed. redactForShare keeps only part types on an allowlist: text, tool-call and tool-result, so a reply's searches and Sources still show. Thinking and file contents are not on the list, so they go. redactAttachmentsForShare turns each attachment into { filename, mediaType }, and drops its id and size.

An allowlist fails safe. If a later PR adds a new part type, a Shared link hides it until someone adds it to the list on purpose.

Quiz

A future PR adds an audio part type and changes nothing else. Does a Shared link show it?

  1. Yes, every part is shown.
  2. Only its file name shows.
  3. No, it isn't listed.
  4. Only to signed-in viewers.

4A link lives as long as its Conversation

Both foreign keys of shared_link use onDelete: "cascade". Deleting the Conversation (or the user) deletes its Messages and its link together, and share.get then throws NOT_FOUND. Deleted content can't stay public by mistake, which is the main reason ADR 0004 chose a pointer.

The token is randomBytes(16) as base64url: 128 random bits, so nobody can guess it. The page also tells search engines noindex, nofollow.

Key takeaways

If you remember only one thing: a Shared link is a bookmark (leafMessageId) into a tree that never changes, so it never copies Messages.

  • One row per Conversation. Sharing again keeps the token and moves the leaf to the current Active Branch.
  • Allowlist redaction. Text and tool parts pass; thinking and file bytes don't; attachments become name-and-type chips.
  • It dies with its Conversation. Cascade deletes remove the row, and the URL answers 404.

Self-test: cover this box, say each point out loud, then draw the toy's tree and move the bookmark.

Go deeper: sources, side notes and a challenge

The ADR

"Messages are never mutated once written (edit and regenerate insert siblings, ADR 0001), so the path from a root to a given leaf is fixed for as long as the Conversation exists." (ADR 0004)

The ADR says the page walks up "with the same recursive query as the Active Branch". In today's code that walk is loadPath in chat/store.ts: it loads the Conversation's Messages and calls pathTo in JavaScript, not a SQL recursive query. The idea is the same: one shared walk.

Race with a send

upsertSharedLink locks the Conversation row with for("update") first, the same lock a send takes in handleChat (Lesson 3). So the Active Branch can't change between "read the leaf" and "save the link".
