The run

One loop drains the model, saves every second, and decides how the Message ends.

About 15 minutes · a browser · you'll write finalFields (how a run ends) and writeTimes (when it saves)

Words you'll need

Run
The work that writes one assistant Message, from startRun until its finally block ends.
Chunk
One small event from the model's stream, such as a few words of text. TanStack AI calls it a StreamChunk.
Snapshot
A save of the Message's parts so far into its row in Postgres.
Status
The state of a Message row: streaming, complete, stopped or error.

1One loop, two outputs

Think of the run as a cook with an order ticket. The cook finishes the dish whether or not a waiter is there to carry plates. In the picture, each chunk from chat() goes two ways: into the parts builder, which collects the Message's text, and into the chunk channel, which carries it to the browser.

startRun doesn't wait for the loop. It starts the loop with void (async () => { … })() and at once returns listener.chunks, which handleChat turns into the SSE response. It also puts its AbortController in deps.runs, so Stop can find it (Lesson 7).

2The chunk channel: one reader, then silence

The reader is the SSE response. When the browser closes the tab, the response calls return() on the channel's iterator, which sets detached and empties the buffer. After that, push drops every chunk, but the loop in section 1 never notices.

The iterator is written by hand on purpose. An async generator's return() waits for the pending next(), so a disconnect would hang until the model sent its next chunk.

Quiz

A reply has 10 chunks. The user closes the tab after chunk 3. What does the row hold when the run ends?

  1. Only three chunks, status stopped.
  2. No chunks, the row deleted.
  3. Three chunks, status still streaming.
  4. All ten chunks, status complete.

3A snapshot every second, if something changed

Each chunk sets changed = true. A timer fires every snapshotIntervalMs (1,000 ms in defaultLimits), and it saves only when changed is true, then sets it back to false. Here is the run in the picture:

  1. Chunks arrive at 200 and 500 ms, so the tick at 1,000 ms saves.
  2. No chunk arrives between 1,000 and 2,000 ms, so the tick at 2,000 ms skips.
  3. A chunk at 2,600 ms makes the tick at 3,000 ms save. At 3,100 ms the run ends, and finally saves once more.

Every save goes through write, which chains it onto the last one (writes = writes.then(…)). So a slow save can never land after a newer one, and the final save waits for all earlier ones.

4The finally block decides how it ends

The order matters. The cap ends a run by calling abortController.abort(), the same call as Stop, so a timed-out run is also aborted. That is why timedOut is checked first. errorReasonOf turns the Provider's code into a reason: "401" becomes invalid_key, and "429" becomes rate_limited.

Before the save, finally clears both timers and marks a running web search cancelled. After it, the run leaves deps.runs and closes the channel. Only a complete run starts a title, without waiting for it (Lesson 13).

Key takeaways

If you remember only one thing: the run drains chat() to the end on its own; the browser is only an optional reader.

  • Two outputs. Each chunk goes into the parts (saved to Postgres) and down the channel (sent to the browser).
  • Saves are cheap and ordered. At most one snapshot a second, only when something changed, chained so they land in order.
  • finally picks the status. Timed out, then stopped, then error, else complete; only complete gets a title.

Go deeper: sources, side notes and a challenge

The tests that pin this down

In handle-chat.integration.test.ts, read "keeps running to the end when the client disconnects" (it cancels the reader after one read and still expects complete with the full text) and "writes snapshots of the assistant Message while it streams". The tests set snapshotIntervalMs: 20 and runCapMs: 100 through deps.limits, so they don't wait seconds.

How the parts builder joins text

createPartsBuilder in parts.ts appends a text delta to the last text part when it has the same messageId; otherwise it starts a new text part. So text before and after a web search stays in two parts, with the search between them. Each snapshot also writes searchText, the plain text used to search history.

Async iteration

The loop is a for await...of over the stream. The channel is a plain object with next() and return(), which is all that for await needs.
