# Environment: this machine's gotchas

Shared by the orchestrator and every implementer. Each bullet cost a past run a retry. Add new ones at the end of a run, in the section they belong to (SKILL.md step 5), and delete any that a run proves wrong.

## Worktrees and git

- **Worktree paths:** ticket worktrees go in `.claude/worktrees/<N>` inside the repo (gitignored), and the integration worktree in `.claude/worktrees/integration-<spec>` (old runs leave undeletable folders behind, so a fixed name collides). The owner wants nothing in `hobby/` but `ai-chat` (2026-10-22): never create worktrees or scratch files beside the repo. Always pass agents **absolute** paths; a relative path once created a stray `hobby/hobby/`.
- **Line endings:** create every worktree with `git -c core.autocrlf=false worktree add …`. The Windows system gitconfig sets `autocrlf=true`, and a CRLF worktree fails `oxfmt --check` on every file. Check for real changes with `git diff --ignore-cr-at-eol`.
- **Merges too:** pass `-c core.autocrlf=false` to every `git merge` and `checkout` in a worktree. A plain merge once checked out 617 files with CRLF. To recover, delete those files and run `git -c core.autocrlf=false restore -- .`.
- **Stale-stat files block a merge:** after a CRLF repair, git can call identical files "local changes" and refuse the merge (17 files in the #587 run). Check that each file is really unchanged (`git hash-object --no-filters <file>` equals `git rev-parse HEAD:<file>`), then run `git -c core.autocrlf=false checkout HEAD -- <files>`.
- **Removing a worktree:** `git worktree remove` can fail on "Filename too long" (deep `node_modules`). It still deregisters the worktree, but the folder stays. Once the user has asked for it gone, `node -e "require('fs').rmSync('<abs path>',{recursive:true,force:true})"` removes it (long paths are fine) for one folder; `cmd rd` and PowerShell failed on the escaping from Git Bash in the #531 run. A bulk removal of many folders was denied even after the user asked, so write the loop to a script in `%TEMP%` and give the user `! node <script>`. Sometimes it only marks the worktree `prunable`; run `git worktree prune` before `git branch -d`.
- **Creation order:** create worktrees one at a time. Parallel `git worktree add` races on the `.git/config` lock.
- **Pre-made worktrees:** never give `isolation: "worktree"` to an agent that has one; it gets a second worktree under `.claude/worktrees` and its git commands on yours are refused.
- **What hooks block:** `git branch -D`, `git checkout -- .`, `reset --hard`, force-push and pushing to `main`. Use `git branch -d`, and to clear CRLF-only noise, use `git add -A`. Give the user `-D` commands to run. The hooks match the text anywhere in a command, even inside a sed or echo string, so write "force-delete" instead.
- **`-d` and ticket branches:** `git branch -d` checks against the current branch's upstream or HEAD, so it refuses a ticket branch that is merged only into the integration branch. Retry them after the integration PR merges (see below).
- **Formatting:** `pnpm check` runs `oxfmt --write` and rewrites line endings in every file. Use `pnpm exec oxlint` and `pnpm exec oxfmt --check` instead.
- **Scripted edits:** this machine has no `python`; use `node -e`.
- **Fresh worktrees:** the first `pnpm exec` in a worktree with no `node_modules` runs a `pnpm install`. Two at once can fail with `ERR_PNPM_LOCKFILE_RENAME_FILE`; retry once the install has finished.
- **Merged branches:** GitHub deletes the remote branch when a PR merges, so `git push origin --delete <branch>` fails afterwards with "remote ref does not exist" (#644). Run `git fetch --prune` and move on.
- **Repo name:** the GitHub repo is `Daanish2003/bot-sdk` (renamed from `Daanish2003/ai-chat`; old URLs redirect). `origin` points at it since 2026-10-20.
- **Main moves during the run (#624):** another session merged a PR touching the same eval files while #648 was open, so the PR showed `CONFLICTING` and CI never started (`gh pr checks` said "no checks reported"). After opening the PR, check `gh pr view <n> --json mergeable`; merge `origin/main` in (with `-c core.autocrlf=false`; the #624 run forgot it once and had to repair 61 CRLF files).
- **A fast-forward that skips verify can carry a stale test (#624):** #631 changed `bot.get`, its agent ran only the affected tests, and the next full verify failed on an untouched test in `bot.integration`. Skip the verify only when the agent ran the whole suite.
- **`-d` after the PR merges (#761):** once the integration PR is merged and `main` is pulled, `git branch -d` deletes every ticket branch, including ones `-d` refused mid-run. Delete them then, and hand the user only what still refuses.
- **A busy worktree folder (#761):** `rm -rf` of a worktree folder worked for most, but one failed with "Device or resource busy" because a process an agent started (the example's smoke server) still held it. Give that folder to the user to remove after a restart.
- **An unpushed base breaks the agent's review (#791):** an agent started from a local, unverified integration tip ran its `code-review` against `origin/feature/…`, which was behind its base. The review saw only older docs commits and none of the agent's code. When a worktree starts from an unpushed tip, put its SHA in the prompt and tell the agent to review `<SHA>..HEAD`.
- **Never merge into a worktree while a verify runs in it (#791):** a merge that landed mid-verify changed the files under the test run, so that result proved nothing and the verify had to be run again. Hold every merge until the verify reports.
- **Removing worktrees with `node_modules` (#791):** `git worktree remove --force` failed with "Filename too long" on every worktree in the run. Go straight to `git worktree prune` plus the `node -e "…rmSync…"` removal from the bullet above; it went through each time.
- **The spec's docs branch (#791):** when the spec branches from a `docs/<map>-…` branch, delete that branch and its worktree too once the integration PR merges (`git merge-base --is-ancestor docs/… main` first).

## Databases and services

- **Postgres:** port 5435 (5432 is another project's). Use `127.0.0.1`, never `localhost`: Node tries `::1` first and Docker's IPv6 forwarding hangs the handshake. The image must be `pgvector/pgvector:0.8.7-pg18-trixie`.
- **Test databases:** one per ticket, `TEST_DATABASE_URL=postgresql://postgres:password@127.0.0.1:5435/ai-chat_test_<N>`. The integration verify uses its own database (`ai-chat_test_int_<spec>`); a shared one breaks once one branch's migration has run on it. Drop the run's test databases at the end. Each run copies the migrated database once per vitest worker (`<database>_r<runId>_w<n>`) and drops only its own copies when it ends, so concurrent runs on one database don't collide. A run killed midway leaves its copies behind for good; the end-of-run drop below removes them.
- **No `psql` on PATH (#737):** Git Bash has no `psql`. Run it in the container: `docker exec ai-chat-postgres psql -U postgres -c '<sql>'`.
- **Redis:** 6379 is another project's and needs auth. Tests use ai-chat's compose Redis, `ai-chat-redis`, on `127.0.0.1:6380`, with one database number per ticket (`TEST_REDIS_URL=redis://127.0.0.1:6380/<1–15>`). The integration verify uses 0.
- **Concurrent runs:** another spec run (Bot step 7) used this machine at the same time as the #638 run. Before picking Redis db numbers and database names, list the ones in use (`redis-cli -p 6380 info keyspace`, `l` in psql) and choose free ones; drop only your own by exact name at the end.
- **Redis db 0 isn't free (#691):** it held 48 expiring keys from another session. The integration verify used db 12 (`verify.sh <wt> <suffix> 12`) and tickets used last digit + 1.
- **Starting the services:** from the **main checkout**, never a worktree, run `POSTGRES_PORT=5435 REDIS_PORT=6380 docker compose --env-file apps/web/.env up -d postgres redis`. By the #665 run, `apps/web/.env` no longer set the ports, and the containers came up on 5432 and 6379 until they were passed from the shell. Check `docker ps` shows 5435 and 6380 before a verify. A plain `docker compose up -d redis` recreated Redis on 6379, and verify then failed with 34 timeouts (#543 run).
- **Docker stops with the session (#691):** twice after a Claude Code restart, Docker Desktop was down (`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`). Start it with `"/c/Program Files/Docker/Docker/Docker Desktop.exe" &`, then loop on `docker info` until it answers (about a minute). The containers come back on 5435 and 6380 by themselves. In the #713 run, Docker went down mid-run, without a restart, while a review-fix agent was working. e2e then failed with `ECONNREFUSED 127.0.0.1:5435`. After Docker Desktop was up, `docker start ai-chat-postgres ai-chat-redis` brought the containers back.
- **Memory:** this is a 16 GB machine. Run only one heavy job at a time (a verify, an e2e run, or an agent's suite). Hundreds of leftover test databases once made Postgres hold 2.4 GB and got e2e killed. At the end of the run, drop every `ai-chat_test%` and `ai-chat_e2e%` database except `ai-chat`. The editor's tsserver (a child of typescript-language-server) can hold 2–3 GB (3.2 GB in the #463 run) and once got a verify reaped. When memory is low, `taskkill` it; the editor restarts it. The classifier denies that kill ("Interfere With Workloads") unless the user has said to free memory, and after the denial it also refused the next verify; ask the user first. An agent's e2e run was killed for low memory in the #486 run, so the orchestrator runs e2e for the slot holder.
- **Dropping databases:** an implementer in the #510 run dropped every `ai-chat_test%` database, the integration verify's included. Brief each agent to drop only its own database by its exact name; only the orchestrator runs the end-of-run sweep.
- **`pnpm check-types` in a worktree** fails on varlock ("config is invalid") because there is no `.env`. Export verify.sh's placeholder env first.
- **`.env`:** never copy the user's `.env` into a worktree. Tests and builds get CI's placeholder values (verify.sh carries them).
- **Local E2B Embed** (WSL `Ubuntu-24.04`, `~/e2b`): a template build uploads to `[::1]:5008`, which Node can't reach from Windows. Run a small TCP relay from `127.0.0.1:5008` to `[::1]:5008` during the build. When a build fails with "envd syncing" or an mmap memfd error, drop the page cache as root (`wsl -d Ubuntu-24.04 -u root -- bash -c 'sync; echo 3 > /proc/sys/vm/drop_caches'`) and rebuild.
- **Embed and memory:** the Embed distro holds several GB. Stop it (`wsl --terminate Ubuntu-24.04`) before a verify or an e2e run. In the #587 run, both were reaped for low memory until the distro and tsserver were stopped. Restart it with `wsl -d Ubuntu-24.04 -- bash -c 'cd ~/e2b && docker compose up -d --wait'`.
- **Concurrent evals:** give each eval run its own `EVAL_DATABASE_URL` database (for example `ai-chat_eval_ladder`). Two evals on one database truncate each other's rows.
- **A shared test database name (#761):** an implementer ran its suite against the plain `ai-chat_test` database. Brief every agent with its own exact database and Redis db.
- **Mailpit (#761):** its webhook is rate-limited to 1 per second and posts a summary without a signature. A probe that sets `MP_WEBHOOK_URL` leaves the container pointing at the probe's port. Recreate it (`docker compose up -d --force-recreate mailpit`) before using the web app.
- **An expired login stops every agent (#791):** "Login expired · Please run /login" ended all three running implementers at once, mid-edit. After the user ran `/login`, SendMessage to each agent resumed it with its uncommitted work intact. Tell each one which integration commits landed meanwhile.
- **A restart stops Docker and frees memory (#791):** after a Claude Code restart, Docker Desktop was down again, but free memory went from 450 MB to 6.4 GB because the restart ended tsserver. Restarting the session is a cheaper way to free memory than killing processes by PID, since the user's `taskkill` found the reaped verify's process already gone.
- **Memory, again (#761):** a background verify was reaped while the session was idle, with tsserver at 2.4 GB. The full verify takes about 12 minutes, longer than the 10-minute foreground limit, so it has to run in the background. Free memory first: ask the user to let you kill tsserver before the verify that gates the PR.

## Checks

- **Where vitest runs:** always from the **repo root**. From a package, it skips the root `globalSetup`, and tests fail with "database does not exist".
- **Integration files run in parallel**, one database copy per worker, with the module graph shared per worker (`isolate: false`). A file that calls `vi.mock` runs in the `integration-mocked` project instead (vitest.config.ts finds them). Other global state a file changes (fake timers, stubbed globals, env) must be restored by that file.
- **`expect.poll` defaults to 1 s (#624):** a crash-resume test polling the fake Model passed alone and timed out in a full verify. Bot integration tests pass `{ timeout: 10_000 }`; do the same in new ones.
- **New integration files need test timeouts too (#713):** `bot-skills.integration.test.ts` kept vitest's 5 s default. Two of its tests timed out in two full verifies, and both passed alone. The branch review set 30 s per test for the new Skills and Demonstration files. Put this in the brief for any ticket that adds a Bot integration file.
- **Read the exit code**, not only the summary. Vitest exits 1 on unhandled errors while every test passes. Also read the **skip count**: turbo's strict env drops variables missing from `passThroughEnv`, and the suites gated on them skip silently.
- **Runs stay in the foreground:** agents hand back with background runs still going, and those runs die with them. Stop an old verify (TaskStop) before starting a new one.
- **Timestamps:** tests that compare a Postgres-default timestamp (the Docker clock) with a JS one (the host clock) are flaky. Set timestamps explicitly. Test helpers that insert rows count too: `insertMessage` let `created_at` default to the Docker clock, which drifts from the host by seconds, and 5 tests failed on main (#510 run). Never hard-code "today" in a test either: a Bot list test dated 2026-10-17 broke once the real clock passed it.
- **Work that outlives a test:** a Run stopped mid-tool-call ends before the tool's write, so a test that returns then leaves a transaction that can deadlock the next file's `truncateAllTables` (CI on #495). A test that stops a Run must await the stopped write. Local runs rarely show it; 4 parallel `--repeats 400` loops did. A test that reads one event of `bot.send` and moves on leaves a server-side follower that queries on the next hint and deadlocks the truncate the same way (#510): close the stream and wait for the open-subscription count to drop.
- **CI is the last check:** CI's `check` failed on #495 after every local verify passed. Report the CI result before asking the user to merge.
- **No CI run yet:** `gh pr checks <n> --watch` right after opening a PR exits at once with "no checks reported" before CI registers the run. Wait for `gh run list --branch <branch>` to show the run before watching it. For PR #644, no run appeared at all and the user merged without it.
- **Verify time:** about 3–7 minutes since #454 (3 minutes in the #463 run), 8–9 minutes by the #665 run (290 files), and over 10 minutes by the #691 run (293 files, 3180 tests), past the Bash tool's 600 s foreground limit, so the call moves to the background on its own. Write the log to a file (`> "$TEMP/verify-<spec>.log"`) and read it when the background task reports. A verify that fails in a few seconds with `ECONNREFUSED 127.0.0.1:5435` means Docker is down, not a test failure.
- **Low memory reaps background runs (#665):** a background verify and a background worktree removal were both stopped "because the system is running low on memory" while the session was idle. Run the verify that gates the PR, and e2e, in the foreground with a 600000 ms timeout.
- **A reaped verify leaves its workers running (#691):** after Claude Code stopped a verify for low memory, its turbo, vitest and fork workers (about 750 MB) kept running alongside the editor's tsserver (3.2 GB). Free memory was 450 MB. List them with `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` (their command lines name the integration worktree), kill them and tsserver with `taskkill //PID <id> //T //F` once the user agrees, then re-run in the foreground.
- **apps/web's lib is below es2023 (#665):** apps/web typechecks the bot-sdk sources, so `findLast` and `toSorted` fail there (TS2550) while the package's own typecheck passes. Implementers run root `pnpm check-types` with verify.sh's env before reporting.
- **Anthropic system prompts are objects (#665):** since #673 they are `{content, metadata}`, so a fake Model that routes on `String(prompt)` misroutes Helper calls silently. Match on `.content`.
- **`bot.get` shape changes (#665, again after #624):** a new field on `bot.get` breaks the exact-match `toEqual` in `bot.integration`. Brief UI and data tickets to grep for it.
- **More load timeouts (#665):** webhook "cuts it once", bot-send "starts the next Turn when … ends error", bot-helper "ends error after 50 Steps" and bot-computer "a user delete during a Turn" timed out under 3–4 parallel agents and passed alone.
- **Verify under load:** a verify that runs while implementers run their own suites can fail on timeouts. In the #587 run, with 3 agents testing, 3 `bot-computer` and `bot-send` tests timed out, and both files passed alone (109/109). Before treating such a failure as real, re-run the failing files alone. Run the verify that gates the PR when no agent is testing.
- **generate-image flake:** `generate-image.integration.test.ts` ("records the flat price … for a stopped call") failed once in the #587 final verify under full-suite load and passed alone 3/3.
- **More load timeouts (#638 run):** the `migrate.integration` DROP DATABASE hook and the bot-computer test "a user delete during a Turn" timed out in a verify under load and passed alone.
- **More load timeouts (#691):** bot-memory-search "is absent with Memory off or with no computer plugin, and present otherwise" takes about 2 s alone and hit the 5 s default timeout in a full verify. It passed 3/3 alone.

## Slots

- **e2e:** Playwright's ports (3100, 3101, 11534) are fixed, so only one e2e run at a time. Run it from `apps/web` with both `E2E_DATABASE_URL` and `DATABASE_URL` set (`127.0.0.1:5435/ai-chat_e2e_<spec>`) and `--workers=2`. The webServer runs `pnpm build`, which needs `DATABASE_URL`. Whoever holds the slot runs the whole e2e suite, not just their own spec.
- **Migrations:** only one ticket at a time adds a migration. The SDK's migrator applies only migrations newer than the last one applied, so the dates must stay in merge order:
  - When merging, regenerate the later ticket's migration with drizzle-kit on top of the merged branch, then re-date it. Never hand-edit snapshot `prevIds`.
  - Update `LATEST_MIGRATION` and the migrate test's count.
  - Check: `pnpm exec drizzle-kit generate` in the SDK package must say "No schema changes".
  - **Two specs in parallel:** merge the spec with the earlier-dated migrations first. The other spec then merges main into its branch. drizzle-kit 1.0 rc reads the two snapshot chains as commuting branches: generate says "No schema changes", check says "Everything's fine", and no snapshot edit is needed. After steps 5 and 4, #561 merged before #583.
  - **Shared course numbering:** two specs can write the same lesson number. The spec that merges second renumbers its lesson file, the nav links, `names.js` `lesson:` and `data-upto`, and the later `counter-reset` values in `docs/learning/index.html`.
  - drizzle-kit writes `snapshot.json` in a shape that `oxfmt --check` can refuse. Run `pnpm exec oxfmt` on the new snapshot before committing.
- **SDK copy:** after a merge that touches the SDK, run the copy into the example Host visibly, never piped to `/dev/null`, and with an absolute destination: `node scripts/copy.ts <absolute dest>` from `packages/bot-sdk`. `pnpm run copy -- <dest>` passes `--` as the destination and creates a stray `packages/bot-sdk/--` folder. Confirm with `diff -rq --strip-trailing-cr` that only `VERSION` differs. A `VERSION` conflict is only a timestamp, and CI's drift check skips it. Resolve it by writing one side's file with `git show <branch>:<path> > <path>`. A commit whose only lint-staged file is `VERSION` fails, because oxfmt says "Expected at least one target file".
- **Copy destination:** the example Host’s copy lives at `examples/next-prisma/src/bot-sdk`; pass that absolute path to `copy.ts`, not `examples/next-prisma`.
- **Copy script gaps:** `copy.ts` never refreshes `extras/` once it exists and never removes a dropped plugin folder, and `ui/` is Host-owned after the first copy. Diff `extras/` by hand after a copy (the #486 run found a stale Trigger.dev import there). Because `ui/` is Host-owned, a copy does not carry over changes to an existing plugin's `ui/` files. In the #713 run, the Haiku copy ticket left `bot-conversation`, `computer-card` and `show-me-card` stale and had to be sent back. In the copy ticket's brief, list each `ui/` file the spec changed and say to sync it by hand, byte-identical.

## Permissions

- **Real-Model evals:** implementers have no Model key, and reading the user's `.env` with grep or cat is denied. The orchestrator runs the real-Model eval only after the user agrees to it. In the #510 run, the user allowed sourcing `apps/web/.env`, which holds their OpenRouter key; the root `.env` has no key. The eval judge takes an `openrouter:` Model. Leave the eval ticket open until that run is done.
- **Agent API errors:** an implementer can die mid-run on a network error (ENOTFOUND). SendMessage to the same agent resumes it with its context intact. That does not work for an agent the user stopped: in the #713 run, SendMessage refused to resume one. Once the user says to continue, launch a new agent and tell it which commits the stopped one already made on its branch.
- **Follow-up tickets skip the review (#713):** an implementer on a ticket added mid-run (#736) reported done without the required `code-review`. Check `checks` in every report before merging. If the review is missing, add its commits to the branch review instead of merging unreviewed.
- **Merging PRs:** auto mode blocks `gh pr merge` on an unreviewed PR, so the user merges. An explicit "merge it" got it through for #561 and #583, but in the #587 run "merge #609 once the verify passes" was still denied ("Merge Without Review"). Give the user `! gh pr merge <n> --merge`, and don't chain the merge with a push: the push was denied along with it.
- **Long paths:** `git worktree remove --force` failed with "Filename too long" on a worktree with `node_modules`. It unregistered the worktree but left the folder. `node -e 'require("fs").rmSync(<dir>,{recursive:true,force:true})'` removed it.
- **Haiku denials:** the classifier has denied Haiku agents a Playwright run and edits to `package.json`. The orchestrator runs e2e itself when asked, and dependency changes are owner decisions anyway.
- **Worktree removal can hang:** `git worktree remove` on a worktree whose agent left a background process ran past the 2-minute Bash timeout. Wrap it in `timeout 100` or run it in the background.
- **Removing folders:** the classifier denies `rm -rf` of worktree folders, and also denied a cleanup script. Give the user one short `!` command per folder. In the #665 run, `rm -rf` of the run's own unregistered worktree folders went through; try it once before handing it over.
- **Review comments:** the Write hook's formatter renumbers markdown lists, so a review comment that skipped a number ("Not fixed: 5") shifted, and an implementer skipped a real finding (#665). Label findings R1, R2… in bullets, never in a numbered list.
